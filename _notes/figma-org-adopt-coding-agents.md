# How to Get Your Org to Adopt Coding Agents (Without Shipping Garbage)

**講者：** Eyal Blum（Figma 軟體工程師）
**場合：** AI Engineer 大會，2026/08/28
**時長：** 17:42

---

## [核心摘要]

Figma 內部推動 AI Agent 採用時發現一個反直覺現象：**最強的工程師往往最晚採用**，因為他們是用「心智膠帶」撐起整個程式碼庫的人，最先看到 Agent 的失敗模式。Eyal 的解法不是說服他們用 AI，而是把這群懷疑者的抱怨轉化為「驗證路線圖」——當修復讓他們自己的工作變輕鬆，他們自然會跟上。整套方法論圍繞三件事：**左移驗證、規劃優於提示、注意力感知溝通**，核心痛點是「在不毀掉程式碼品質的前提下，讓組織規模化採用 Agent」。

---

## [詳細重點整理]

### 1. AI 採用的三幕劇 [00:00]

組織與個人採用 AI 都會經歷三個階段：

- **第一幕**：隨手試用，簡單任務獲得 10x 加速，建立初步信任。
- **第二幕**：把同樣做法套到更大的問題上，AI 大量出錯、產生 bug，信任崩塌。
- **第三幕**：從失敗中建立真正技能——正確的 guardrail、prompting、context 工程，實現規模化。

關鍵概念：**三幕劇採用曲線**（Three-Act Adoption Curve）。多數組織卡在第二幕的信任低谷，關鍵不是放棄，而是系統性地補上驗證與流程。

### 2. 採用不均勻：團隊必須共存 [02:28]

Figma 內部各團隊的 AI 成熟度參差不齊：有些團隊已全面改造工作流，有些仍在早期實驗或已失去信心。這些團隊卻必須協作交付同一個產品。

挑戰不在於「讓所有人都變快」，而在於建立一個能容納不同成熟度團隊共存的支撐體系，把所有人逐步推向第三幕。

### 3. 為什麼最強的工程師最晚採用 [03:35]

這場演講最具洞察的觀點：**最慢採用 Agent 的，往往是最好的工程師**。

- 他們腦中裝著所有未曾寫下來的機構知識（institutional context）。
- 他們用「心智膠帶」黏住所有 Agent 還處理不好的地方，擋掉最糟的程式碼進入主幹。
- 正因為他們第一手看到每個失敗模式，所以最不信任 Agent，也最快倦怠。

關鍵概念：**心智膠帶負載**（Mental Duct Tape Burden）。這群人不是阻力，而是組織最珍貴的「失敗模式地圖」——他們的抱怨就是一份按優先級排列的驗證缺口清單。

### 4. 投資驗證：最高價值的事 [04:45]

在程式碼庫中投資驗證，是 ROI 最高的事。核心原則是**左移**（left-shift）：凡是能從「需要人類做」變成「Agent 能自動驗證」的環節，就盡量往左移。

實例：Playwright + MCP 出現後，Agent 可以自己探索程式碼與 UI，不再需要人類手動導航，這對多個團隊是重大生產力解鎖。

關鍵概念：**左移驗證**（Left-Shift Verification）。

### 5. 把有效的模式編碼成確定性流程 [05:55]

當發現某個 Agent 行為反覆有用時，不要每次都靠 LLM 重新推理，而是把它**編碼成確定性流程**（deterministic flow）：

- 省 token、省時間，結果可重複。
- LLM 只在需要真正推理時才啟動；已知的東西就寫成測試或腳本。
- 這項投資「永遠會派上紅利」。

附帶技巧：要求 Agent 以 **TDD 紅綠循環**（先寫測試再寫實作）方式工作，幾乎總能得到更好的結果——因為先設目標再逼近，會迫使程式碼去符合驗證標準，而非事後把測試遷就程式碼。

關鍵概念：**確定性流程編碼**（Deterministic Flow Encoding）與 **TDD 紅綠循環**。

### 6. Agent 審查的測試金字塔 [07:04]

借用經典測試金字塔的概念，套用到 Agent 審查流程：

| 金字塔層級 | 內容 | 誰來做 |
|---|---|---|
| 底層（最多） | Linting、編譯器、Unit Test | 確定性工具 |
| 中層 | 已編碼的架構標準審查 | Agent |
| 頂層（最少） | 「這是不是對的東西」功能性判斷 | 人類 |

原則：**盡可能往下推**，只把人類保留在「必須由人類判斷」的頂端——也就是功能性與方向正確性。

關鍵概念：**Agent 審查測試金字塔**（Testing Pyramid for Agent Review）。

### 7. 規劃優於提示 [08:12]

這是恢復開發者「工藝樂趣」的關鍵。與其不斷 prompt、等輸出、再 prompt，不如：

- 花大量時間寫一份**極詳細的計畫**，把所有決策攤開、迭代、送隊友審查。
- 計畫完成、決策都拍板後，才丟給 Agent 做實作。
- Agent 實作完送回，開發者做 review。

Eyal 的親身數據：一份計畫涵蓋約 20 個 PR（每個 10～100 行），相當於過去六週的 coding 工作量，如今一週規劃 + 一夜 Agent 實作即可完成——**含 review 後約 5 倍加速**。

關鍵概念：**規劃優於提示**（Planning over Prompting）。

### 8. 什麼樣的計畫 Agent 才能遵循 [09:21]

一份「Agent 可遵循」的好計畫具備以下特徵：

- **頂部放「為什麼」**：如同 design doc 的 executive summary，防止 Agent 飄移；並明確禁止 Agent 回頭改動這段。
- **可拆成獨立可驗證的小單元**：每個單元對應一個 PR。判斷大小的標準——「這個 PR 我會不會想喝杯咖啡再來 review？」如果會，就代表太大。
- **每個階段都有驗證閘門或例外條件**：避免第一階段沒驗證、後續全部建立在錯誤假設上。
- 每個小單元可餵給獨立 sub-agent 並行處理，互不干擾。

關鍵概念：**獨立可驗證單元**（Independently Verifiable Units）與 **防飄移錨點**（Drift-Prevention Anchor）。

### 9. 把路線圖交給懷疑者 [11:45]

面對最抗拒的高手工程師，不要試圖說服他們用 AI，而是：

- 把他們的回饋視為「如何讓 Agent 在程式碼庫中變安全」的**路線圖**。
- 讓他們主導這份路線圖——當他們看到自己提出的改善真的讓日常工作變輕鬆，他們自然會跟上。
- 他們絕不會客氣告訴你哪裡要修。

這是把「阻力」轉為「品質守門人」的策略。

### 10. 注意力感知溝通 [12:55]

在 AI 時代，**人類注意力是稀缺資源**——你無法製造更多。因此溝通必須標記來源，讓讀者知道該把注意力花在哪：

- **PR 描述慣例**：第一行由人類親手寫（簡述這是什麼、做什麼），AI 生成的描述放在下方。讀者知道上方要認真看、下方可提高警覺。
- Slack、Email 同理：坦承用了 AI，並標明「哪段是我寫的、哪段是 AI 寫的、你需要給我什麼回饋」。

關鍵概念：**注意力感知溝通**（Attention-Aware Communication）與 **人類優先標記**（Human-First Marking）。

### 11. 未標記 AI 輸出的代價 [15:16]

Eyal 分享了一個真實教訓：他對幾位資深且高度懷疑 AI 的工程師，發送了一份用 AI 跑出的 PR 分析，但沒有標記哪些是人寫、哪些是 AI 生成。對方反應激烈——「我沒想到我這麼尊重的人會寄給我這種明顯是 slop 的東西。」

他立刻道歉，並建立新慣例：清楚標記「這是我寫的、這是 AI 寫的、我需要你的回饋，因為我沒有 context 判斷它是不是 slop」。

啟示：**文化慣例與工程挑戰同等重要**。

### 12. 在人們已經工作的地方與他們相遇 [16:29]

推廣 AI 最有效的方式之一，不是部署花俏工具，而是讓人在**原本的工作場域**自然使用：

- 在 Slack 訊息中 @tag 一個 Agent，請它「幫我做這件事」，讓 Agent 在同一個 thread 裡完成閉環。
- 對尚未完全買單的人，可以非被動攻擊地說「我們來看看 Agent 這次能不能搞定」——一次好體驗，就會讓他們主動在其他情境嘗試。
- 先在日常任務中常態化 AI 使用、降低摩擦，再往上疊加自動化。

關鍵概念：**原地降低摩擦**（Friction Reduction in Place）。

## [技術/數據對比]

| 面向 | AI 前工作流 | 規劃優先工作流 |
|---|---|---|
| 規劃時間 | 隨手開工，邊做邊想 | 約 1 週詳細規劃 + 跨團隊對齊 |
| 實作方式 | 人工撰寫全部程式碼 | Agent 依計畫連夜實作 |
| 產出規模 | 6 週 coding 量 | 約 20 個 PR（10～100 行/個） |
| 總週期 | ~6 週 | ~1 週（含 review） |
| 加速倍率 | 基準 | **約 5x** |

## [結論與行動建議]

### 啟發金句

> 「計畫給一週，Agent 給一夜。」

### 具體行動建議：P-V-M 法則

- **P**lan（規劃）：花一週把計畫寫到每個單元都能獨立餵給 sub-agent，先設「為什麼」防飄移，再拆可驗證小單元。
- **V**erify（驗證）：把所有能確定化的檢查左移到底層工具與 Agent，人類只留最頂端的功能性判斷；有效模式立刻編碼成確定性流程。
- **M**ark（標記）：所有 PR、Slack、Email 一律標記人寫 vs AI 寫，把稀缺的人類注意力導向真正需要判讀之處。

### 生活實踐建議

把「懷疑者即路線圖」套用到團隊協作：當同事質疑某個 AI 工具或流程時，不要急著反駁，而是把他的抱怨逐條記下，轉成「讓這個工具變安全」的改善清單，並請他主導驗收。同樣的邏輯也適用於個人——你對某個 AI 輔助流程的不信任點，往往正是你該優先補上驗證或 guardrail 的位置。先修好那個缺口，信任自然回來。
