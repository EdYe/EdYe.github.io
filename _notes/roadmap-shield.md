# When Your Product Roadmap Works Against You

## [核心摘要]

產品路線圖本質上是工程團隊與利害關係人之間的契約，帶來穩定性並隔絕雜訊。但當保護過頭，會形成「路線圖護盾」（roadmap shield）——由範圍、估算、時程溝通、交付壓力四層疊加，使新資訊無法改變團隊正在做的事。這會把課責從「我們做對了什麼」扭曲為「我們有沒有如期交付」，犧牲了產品工程的真正核心：邊交付邊探索的能力。 

## [詳細重點整理]

### 1. 路線圖的契約本質 

路線圖的運作邏輯：先決定要做什麼 → 排定建置順序 → 取得利害關係人簽核 → 專心交付。它的價值在於過濾雜訊與隨機的客戶承諾，因為工程確實需要不被打擾的專注時間。

關鍵概念：**產品路線圖 = 工程團隊與利害關係人的契約**

### 2. 路線圖護盾的形成 

當保護層層疊加到讓團隊「無法睜開眼睛看周遭世界」，護盾就不再只是隔絕雜訊，而是讓新資訊無法在建造過程中傳進來。它由四層組成，每一層都讓資訊更難穿透。

關鍵概念：**路線圖護盾（Roadmap Shield）**

### 3. 第一層：範圍 

優秀的團隊應把範圍縮減到接近 MVP——用最少的範圍交付最大價值，並寫成驗收條件（acceptance criteria）。一旦寫下並放上路的圖，這份範圍就成為可據以拒絕額外需求的契約，防範範圍蔓延（scope creep，例如「能不能順便加個匯出 PDF？」）。

關鍵概念：**範圍鎖定（Scope Lock-in）與 MVP 原則**

### 4. 第二層：估算 

範圍定案後，工程團隊估算工時。工程經理傾向給出自己能負責的務實數字，且投入大量心力確保可信。估算放上路線圖後，方塊的長度就是時間承諾——之後進來的任何資訊幾乎都無法改變它。

關鍵概念：**估算即承諾（Estimate as Commitment）**

### 5. 第三層：時程對外溝通 [06:13]

把「5 週後交付」告訴 GTM、行銷與面對客戶的團隊後，就很難收回。這層保護確實有用——遇到範圍蔓延時，團隊可以用日期承諾擋掉額外需求——但同一個承諾也在阻止團隊改變手上的工作。

關鍵概念：**對外溝通即定案（Communication as Commitment）**

### 6. 第四層：交付壓力 

專案後段，主管與利害關係人開始緊盯範圍與日期。這層是純心理層面：把團隊從「探索心態」（創意地解決問題）轉變為「執行心態」（壓力大，只想把東西做完）。

關鍵概念：**心態鎖死：探索模式 → 執行模式**

### 7. 護盾的複合代價

四層疊加的效應：把「這是我們該做的功能嗎？」變成「我們有沒有把功能完整交付？」這會觸發沉沒成本謬誤（範圍都寫好了，先照交付再說）。最終團隊只被以「路線圖執行得多好」課責，無法為成果指標負責。

關鍵概念：**課責錯位（Accountability Shift）與沉沒成本謬誤**

### 8. 案例：MCP Server 整合 

- 團隊決定透過 MCP server 引入第三方 AI 功能，談定 5 個工具、效能與測試要求（範圍），估算 5 週（時程），對外承諾 6 週上線（溝通），交付壓力隨之累積。
- 第 3 週時，新資訊出現：AI 世界正出現對「MCP 是萬用整合解方」的反彈，讓 LLM 直接寫 JavaScript 呼叫 API、或廠商提供 skills 直接與模型互動，可能更優。
- 但此時團隊已進入執行模式：MCP 範圍做了一半、日期已對外承諾、估算會被打斷、利害關係人施壓如期交付。四層護盾全部啟動，團隊根本無法花 2–3 週探索替代方案，新做法只能被推遙到遙遠的未來。

關鍵概念：**執行模式排斥探索（Execution Blocks Exploration）**

### 9. 解法一：縮小路線圖項目 

把 5 週的項目縮減範圍到 2 週交付——交付、打勾、然後花 1 週探索替代方案。用更短的承諾週期換取轉向空間。

關鍵概念：**小批量交付（Smaller Batch Delivery）**

### 10. 解法二：每一層護盾設退場機制 

在護盾的四層都明確宣告 **退場機制（exit ramp）**：

- 交付壓力層：與領導層建立有文件記載的信任——除非出現達到某門檻的新資訊，否則照承諾交付。
- 時程層：溝通時附帶但書——「5 週內交付，但若此領域出現重大進展，可能會改變」。
- 務實盤點期限：多數團隊把每個期限都當成不可移動，但真實情境中多數期限有餘裕。與行銷、面對客戶的團隊一起決定哪些可動、哪些不能動。

關鍵概念：**退場機制（Exit Ramp）**

### 11. 解法三：團隊內部打破承諾的心理許可

讓團隊在特定情境下被賦予打破承諾的許可，能自在地舉手說「我們要改變方向，理由是學到了新東西，多花 2–3 週值得，會交出更好的成果」。成果極少在路線圖終點自動出現，幾乎都需要修正方向與反覆迭代——允許在交付過程中迭代，才能更快回應市場與技術變化。

關鍵概念：**邊交付邊探索（Deliver & Explore Simultaneously）**

### 12. 結論：在可預測與創新之間找平衡 [19:51]

路線圖本身不是壞事——它仍保護專注時間。但承諾必須有退場機制，因為你永遠不知道新資訊何時進來。別把路線圖當成絕對聖經。

關鍵概念：**路線圖是工具，不是聖經**

## [結論與行動建議]

**啟發金句**：「真正的失敗不是轉向，而是遲遲不去試。」

**具體行動建議 — E-R-R 法則（Exit-Ramp Rule）**：

- **E**xplicit（明確標記）：在每個路線圖項目上標出退出點與觸發門檻（什麼樣的新資訊值得改變計畫）。
- **R**educe（縮小）：把大型承諾切小——5 週的項目縮成 2 週交付 + 1 週探索。
- **R**e-negotiate（重新協商）：事先與利害關係人、行銷、客戶團隊盤點哪些期限真的不能動、哪些有餘裕，並寫成有文件的信任。

**生活實踐建議**：

- 對 AI 應用開發者：採用 MCP server 等整合方案時，把「重新評估技術選型」排進每個迭代週期——AI 工具鏈（如 MCP vs. LLM 直接呼叫 API vs. 廠商 skills）變化極快，本集案例就是最佳警示。
- 對個人工作：年終規劃 2027 年專案或 YouTube 頻道方向時，為每個計畫寫下「如果出現 X，我就重新評估」的條件句，避免自己對去年的規劃產生沉沒成本謬誤。
- 對團隊管理：在 sprint 回顧會固定問一句——「如果有新資訊進來，我們能改變這個計畫嗎？需要調整時，我們能快速回應嗎？」

所以最後這一層基本上是心理層面的，它讓團隊從原本的探索心態，也就是「我們來發揮創意做點東西」，轉變成「我壓力很大，只要專心把東西做出來就好」。這就是路線圖護盾（roadmap shield）的四層：先是承諾的範疇，然後是時程，接著是範疇與時程的對外溝通，最後是交付過程中為了確保達標而產生的壓力。把這些加在一起，確實能保護團隊不受變動干擾，在交付你承諾過的東西上也相當有效。

[00:08:43](https://youtu.be/_45A1xOiW_E?t=523)  
問題出在新資訊需要進入團隊的時候。比方說，你原本決定的範疇，在交付完成前被發現並不正確。我們決定要做某個功能，但其實它應該有點不一樣的做法。這時，路線圖護盾的每一層都會啟動，阻止這個新資訊改變團隊實際在做的事。

[00:09:07](https://youtu.be/_45A1xOiW_E?t=547)  
範疇一旦談定並寫下來，就變得難以更動。這時會出現沉沒成本謬誤（sunk cost fallacy），你會想：「範疇都寫好了，驗收標準（acceptance criteria）也訂了，現在不想改變主意。先交付我們說過的東西，之後再改就好。」所以你已承諾的範疇量，可能會擋住新資訊進來，這有時是好事，但並非總是如此。估算與對外溝通的時程也一樣。如果錯過了對外溝通的時程，會影響團隊的聲譽，也會影響客戶和利害關係人對你們的觀感，帶來很多負面影響。它可能讓工程組織看起來不可預測、有點混亂。所以這些全都會形成壓力，阻止範疇變更與新想法進入團隊。

[00:09:55](https://youtu.be/_45A1xOiW_E?t=595)  
但這些層層疊加起來，對你快速創新的能力造成的複合效應，是把「這是我們該做的功能嗎？」這類問題，變成了「我們有沒有把這個功能完整成功地交付？」。而正如我們在這個 podcast 前幾集談過的，你不該總是只用「團隊把說好要做的東西做得多有效率」來課責他們，還必須讓他們為「產生了多少影響」以及「為產品帶來什麼成果」負責。但如果你的路線圖讓團隊無法轉向、無法納入新資訊，他們最後就會逼自己以「路線圖執行得多好」來被課責，而你會發現，要讓他們為任何成果指標負責，是非常非常困難的。

[00:10:41](https://youtu.be/_45A1xOiW_E?t=641)  
我舉個例子。假設你在做一個產品，想從第三方服務引進一些 AI 功能。現在你可能會想：我們就找一個 MCP server，把 MCP server 整合進我們的應用程式。這是相當常見的做法。如果你有第三方的 AI 應用，自己也有一個 AI 應用，那麼用 MCP server 把它放進你的應用程式，看起來很合理。

[00:11:10](https://youtu.be/_45A1xOiW_E?t=670)  
依照路線圖的步驟，你會先決定：這個 MCP server 上我們要用哪些工具、要引進多少功能，這就成了你的範疇。範疇上你可能還有一些效能要求、測試要求之類的。然後我們決定並寫下來：我們要整合這個 MCP server，使用這五個工具，要這樣測試，要這樣確保效能。這就是範疇。

[00:11:38](https://youtu.be/_45A1xOiW_E?t=698)  
接著工程團隊回來說：「對，大概要五週的工作量。」這五週就成了你的時程。你說：「這些是我們要做的東西，這是我們的時程。」然後對外溝通：我們有五週的工作量、談定的範疇，並向利害關係人說明，六週後（我們多加一週），你們就能在我們的 AI 應用程式裡用到這個 MCP server 的這五個工具。然後團隊開始交付，壓力也慢慢傳到團隊身上，他們開始想：「我們進度到哪了？這些工具已經做完幾個了？」

[00:12:14](https://youtu.be/_45A1xOiW_E?t=734)  
諸如此類。於是交付壓力不斷累積，形成路線圖護盾的四層。現在假設做到第三週，結果發現 MCP server 也許不是解決這個問題的正確方式。在變化快速的 AI 世界裡，這完全有可能。順便岔題一下，現在對於「MCP 是各種整合的萬用解方」這個說法，有一股逐漸增長但非常熱烈的反彈。許多打造 AI 產品的人開始想：「與其用 MCP server，何不讓 LLM 直接寫 JavaScript 去呼叫他們的 API？」這是另一種做法。團隊可能評估過這個做法，然後認為：「不，我們還是要用 MCP server。」

[00:12:59](https://youtu.be/_45A1xOiW_E?t=779)  
但假設交付進行到一半，讓 LLM 撰寫 JavaScript 的那種做法出現了新進展，也許有新模型發布，在這方面特別強，也許是你要整合的那家公司提供了一些技能（skills），幫助模型與他們的 API 互動。不管是什麼，總之有新資訊進來，在交付到一半時發現，這個 MCP server 整合可能不是最佳方案，或至少我們該評估別的做法，花點時間試試其他方式。

[00:13:26](https://youtu.be/_45A1xOiW_E?t=806)  
這時候，路線圖護盾（roadmap shield）的四個層次就會發揮作用，阻止這種事發生在團隊身上，因為到這個階段，團隊已經不是實驗或探索模式，而是執行模式。他們要為能否有效交付那些項目負責。他們已經完成一半約定好的 MCP server 範圍，也對外說明了何時會上線，路線圖也走到一半。在這個時間點，你不能直接改變團隊正在做的事，叫他們花兩、三週去研究另一種做法。

[00:13:58](https://youtu.be/_45A1xOiW_E?t=838)  
如果你真的這麼做，首先出現的就是來自利害關係人的交付壓力，他們會說：「等等等等，你在幹嘛？你不能說改就改，我們講好的日期一定要達成。」而且如果錯過那個日期，會損害團隊的信譽，也會讓人日後對工程團隊給出的日期更難信任。此外，原本 5 週的估算，是工程團隊根據一定的範圍做出的。所以，如果你對他們說：「你們現在要花一週去實驗一種解決問題的新方法。」

[00:14:31](https://youtu.be/_45A1xOiW_E?t=871)  
他們會回答：「不行，這樣會打破我們原本的估算。」再者，範圍已經白紙黑字寫在路線圖上、寫進某個功能裡，而這個新做法並不在其中。所以，路線圖護盾的這四個層次，最終會讓團隊在打造第一個東西的同時，根本沒辦法探索這個新做法。通常的情況是，他們把那個功能做完、交付之後，也許能空出一點時間去探索別的東西。如果他們真的探索了像 API first、先寫程式碼這樣的做法，接著又會把另一個功能放上路線圖並承諾交付。再過三週，可能又冒出另一種做法。所以這就是一個很好的例子：把太多時間投入單一路線圖項目、然後埋頭交付，

[00:15:16](https://youtu.be/_45A1xOiW_E?t=916)  
可能會阻礙新做法與新的實驗方式，或者至少把它們延後到太遙遠的未來。那麼，究竟該怎麼解決？如果路線圖妨礙團隊在執行期間轉向或探索新點子，你該怎麼辦？其實有很多方法，而這也正是我做這個 podcast 的核心原因。

[00:15:40](https://youtu.be/_45A1xOiW_E?t=940)  
因為打造能夠適應新資訊、能轉向、能探索的團隊，也就是在交付的同時不斷探索，才是產品工程真正的功夫。這需要大量的信任與協作，也需要一些流程上的改變。要跳出路線圖護盾，有幾種方式。其中之一是把路線圖項目切得更小：你仍然交付那個項目，但不是花 5 週，而是大幅縮減範圍，在 2 週內交付。這樣你就能交付、打勾完成，然後花一週探索替代方案。不過還有其他做法。我看過一個很有意思、也相當成功的做法，就是明確宣告在路線圖護盾的每一層都設有退場機制（exit ramp）

[00:16:25](https://youtu.be/_45A1xOiW_E?t=985)  
。以四個層次來說，先看交付壓力：你需要與領導層建立有文件記載、明確的信任，說明我們會交付所承諾的東西，除非出現達到某個門檻的新資訊，那種情況下我們就不會做原本說要做的事。而你得能坦然對利害關係人這麼說。交付估算和時程也一樣，你的時程裡也要有退場機制。你可以對人說：「我們會在 5 週內交付，但如果這個領域出現重大進展，可能會改變。」而且這件事要溝通清楚。但這並不是每次都做得到，並不是每次都能對人說「5 週內可以給你，但有個但書，我可能不會做」，特別是當

[00:17:12](https://youtu.be/_45A1xOiW_E?t=1032)  
周邊有行銷活動配合，或是有客戶迫切需要、指望 5 週後拿到東西的時候。所以不是每次都可行，但我鼓勵你去找找看，在你正在交付的功能中，哪些期限其實可以稍微挪動，並事先約定好哪些情況可以讓你調整期限。很多工程團隊，尤其是不了解某件事為什麼非得在特定日期完成的客戶背景時，就會把每個期限都當成不可移動。工程經理被告知一定要達成這些期限，但實際上，在大多數真實情境中，這些期限都有一些餘裕。你可以與面對客戶的團隊、行銷團隊合作，開始思考：如果我們在專案進行到一半時改變

[00:17:57](https://youtu.be/_45A1xOiW_E?t=1077)  
方向，因而延後 5 週，會發生什麼事？什麼可以動、什麼不能動？與他們一起務實地決定，哪些期限可以調整、哪些不行。所以，路線圖護盾的每一層都是可以拆解的，你只需要有意識地去思考，並且與你溝通路線圖的對象建立更多信任與溝通。

[00:18:20](https://youtu.be/_45A1xOiW_E?t=1100)  
你在團隊內部也需要這種信任。你需要讓團隊對打破承諾更自在。如果他們在特定情況下被賦予打破承諾的許可，就應該能自在地舉手說：「我們現在要改變方向了。我們不會交付原本說要交付的東西，原因如下：這是我們學到的新東西，這是我們認為多花兩、三週值得的理由。

[00:18:45](https://youtu.be/_45A1xOiW_E?t=1125)  
它會交付出更好的成果。」如果他們能習慣這麼做，也能累積利害關係人的信任，那就是正確的做法。這樣你最後會得到一支更靈活、更能解決問題的工程團隊，能在已經進行到一半的方案中改採另一個方案。這最終才是達成成果的方式，因為成果極少會在路線圖項目走到終點、交付之後就自動出現。

[00:19:13](https://youtu.be/_45A1xOiW_E?t=1153)  
成果幾乎都需要某種修正方向或反覆迭代才能達成。因此，只要你允許自己在交付路線圖的過程中進行迭代，基本上就能更快做出反應，更快回應市場變化與技術轉變，成為一支靈活得多、能反覆迭代的團隊。前提是你能自在地說：這些是我們必須達成的期限，而那些是我們有一點彈性的，只要我們有良好的基準，知道何時可以打破那些承諾。

[00:19:51](https://youtu.be/_45A1xOiW_E?t=1191)  
所以，請想想你自己的團隊：你們的截止日期、範圍承諾和估算，哪些是真的不能動，哪些其實還有一點彈性？如果有彈性，就告訴團隊：「要隨時留意。你們在這裡有一點彈性，比你想的有更多迴旋空間。如果有新資訊進來，而你們找到更好的解法，那不是失敗；真正的失敗，是遲遲不去試。」所以說到底，產品路線圖（product roadmap）並不是壞事。它仍然能保護團隊不受外界雜音干擾，也仍然能給你解決問題所需的專注時間。但很重要的一點是，你在產品路線圖上做出的承諾，必須要有退場機制，因為你永遠不知道什麼時候會有新資訊進來，

[00:20:38](https://youtu.be/_45A1xOiW_E?t=1238)  
也不知道什麼時候轉向或小幅修正方向會是對的選擇。每當有東西進來、可能改變你的解法是否正確時，幾乎都值得去探索。所以盡可能不要太死守路線圖。這一切永遠都是一種平衡，是在可預測、可靠，與創新、顛覆之間的平衡。所以要找到那個平衡點，別把路線圖當成你該做什麼的絕對聖經。

[00:21:03](https://youtu.be/_45A1xOiW_E?t=1263)  
試著在路線圖上明確標出退出點，並且時時問自己：「如果有新資訊進到團隊，我們能改變這個計畫嗎？如果需要調整，我們能快速回應嗎？」
