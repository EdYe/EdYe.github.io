# Ontology vs. Graph DB：為什麼兩者必須一起用？

**[核心摘要]**

企業資料長期只儲存「數值」本身，缺乏時間與空間的上下文，導致資料無法回答「該採取什麼行動」。本片主張：Ontology（本體論）負責定義資料的語意與關聯結構，Graph DB 則是讓這些結構可視覺化、可追溯、可持續演化的儲存引擎。核心痛點解法是「**動態本體論**」——本體不是建一次就完工，而是隨新資料持續進化的活結構。

**[詳細重點整理]**

### 1. 為什麼談 Ontology 就必出現 Graph DB？[00:01]

當企業討論本體論時，最常見的疑問是「用了 ontology 是否就必須有 Graph DB？」近年產業進一步強調 **動態本體論（Dynamic Ontology）**：企業的資料與商業規則持續變動，本體必須被視為會呼吸、會移動的結構，而非一次性的交付物。這正是 Graph DB 被綁定討論的原因——它是能承載「持續變動結構」的儲存形式。[[youtube](https://www.youtube.com/watch?v=U_YyqxUBNiQ)]

### 2. 資料缺上下文 = 無法決策 [00:42]

傳統資料儲存只記錄數值，不記錄語境。以設備溫度 100° 為例：同樣是 100°，正常或異常取決於它屬於哪個製程、連接哪些鄰近設備——這些**時空上下文資料（Temporal &amp; Spatial Context）**必須與數值一起儲存。人工無法每次手動補充，因此需要具備圖式（schema）結構的**圖資料庫（Graph Database）**來自動承載這類上下文。\[[youtube](https://www.youtube.com/watch?v=U_YyqxUBNiQ)\]

### 3. 可解釋性是信任 AI 的前提 [01:30]

AI 給出答案時，若能明確展示「這個答案依循了哪條推理路徑」「100° 這個值在哪一步被如何引用」，檢視者就能逐步理解結論如何被計算出來。即使未來幻覺降至趨近零，在 mission-critical 場景中，**中間推理過程的視覺化（Process Visualization）**依然是建立信任的必要條件。只存結果、不存推理路徑，企業未來將被迫回頭重新整理一切資料。\[[youtube](https://www.youtube.com/watch?v=U_YyqxUBNiQ)\]

### 4. 活的本體：從問題識別到執行後評估 [02:11]

資料持續湧入，既有 ontology 也會隨新資料改變。要讓本體持續正確回答問題，必須完整收錄四階段決策流程：**問題識別 → 原因分析 → 替代方案探索 → 最適方案選擇**，並由人執行最適或次佳方案。關鍵在於：執行當下的環境、執行後是否有實際商業影響（post-execution evaluation）、甚至執行失敗的紀錄，都要存回本體——如此才算**演化式本體（Living / Evolving Ontology）**。[[youtube](https://www.youtube.com/watch?v=U_YyqxUBNiQ)]

### 5. 製造業實戰：QMS 追溯閉環 [03:07]

製造業的 **QMS（品質管理系統）**核心是品質歷史追蹤，即 **Traceability（追溯性）**。客訴送達製造現場 → 反映到產品 → 回到客戶手上，這個循環若完整被追蹤，且客戶最終滿意，產品整體品質就會持續提升。企業想量化的正是「這個循環讓品質改善了幾分」。\[[youtube](https://www.youtube.com/watch?v=U_YyqxUBNiQ)\]

### 6. 服務業的 VOC 本體化 [03:40]

一般服務業的 **VOC（客戶聲音，Voice of Customer）**多半停留在客服留言管理或通話記錄層次。若能把 VOC 轉成本體、一路連結到服務品質指標，對服務業將產生巨大影響。大型設備產業尤其關鍵：產線一旦設定，變更產品需要重大決策，若以 ontology 為核心運轉 QMS，結合既有資料與客戶 VOC 追溯品質改善點，QMS 會運作得更好。\[[youtube](https://www.youtube.com/watch?v=U_YyqxUBNiQ)\]

### 7. 企業該準備什麼？[04:16]

業務端使用者應準備的素材是：內部決策過程所在的**報告與會議紀錄**，依照前述四階段分類整理，並附上背後的支撐資料。另一個尚未數位化的寶庫是**執行後評估**——把「某個決策是否真的產生影響」的資訊一起儲存，就能成為企業建立本體的資產化基礎，之後再進入技術選型階段。[[youtube](https://www.youtube.com/watch?v=U_YyqxUBNiQ)]

### 8. 顧問與技術商的分工 [04:50]

顧問公司（PwC）與技術公司（Infosyz）的協作模式：顧問負責圍繞關鍵業務議題建立框架並正確結構化，技術方案商則在顧客與框架之間提供技術解法。方法論（methodology）本身就是顧問價值所在。[[youtube](https://www.youtube.com/watch?v=U_YyqxUBNiQ)]

**[結論與行動建議]**

- **啟發金句**：「只儲存數值的企業，最終都要回頭重新整理一切；儲存上下文的企業，讓每一次決策都成為下一次決策的資產。」
- **具體行動建議（S-E-E 法則）**：**Structure（結構化）** 決策流程 → **Execute（執行）** 並記錄環境 → **Evaluate（評估）** 並回存本體。任何資料工程，先問自己：這筆資料的時空上下文和後續評估存進去了嗎？
- **生活實踐建議**：對 AI 開發者（如 MCP 與知識圖譜應用）而言，把這套思維套用到自己的知識管理系統：在筆記或知識庫中，除了記錄結論，也記錄「當時的環境脈絡」與「事後驗證結果」，讓個人知識庫也成為動態本體，而非死檔案。
