## [核心摘要]

Greptile 每天審閱 GitHub 上約 1% 的 Pull Request，本影片揭露自建 AI Code Review Agent 的完整藍圖。核心痛點：樸素的「sandbox + webhook + agent」架構會漏抓災難性 bug（僅千分之一的 PR 含重大 bug）、每個 PR 花費 3–25 美元、且產生大量 nitpick 註解。解方是六項系統性修正：精準提問、歷史事故資料集、**模型反轉**、程式碼庫上下文、自主測試與模型成本分層。

## [詳細重點整理]

### 1. Greptile 規模與自建動機 

數千家公司每日使用 Greptile，約占 GitHub 全部 PR 的 1%，涵蓋 Nvidia 的 CUDA 到 Coinbase 的錢包程式碼庫。部分企業需求過於特殊時，Greptile 會免費協助他們自建——既累積領域知識，也學習未來客戶樣貌。人們青睞它的三件事：codebase context（2023 年起他們原本就是 codebase 索引公司）、能在 sandbox 中實際執行程式碼並用 computer use 測試、以及高效的推理預算分配。

關鍵概念：**審驗瓶頸（Review Bottleneck）**——vibe coding 時代，寫程式不再是瓶頸，驗證才是。

### 2. 什麼樣的 Agent 算優秀 

評估自建 agent 的兩種情境：真的要自建，或是在選購時懂得辨別好壞。三大價值支柱：理解整個 codebase 的上下文、實際執行與壓力測試、依子任務分配模型與推理預算以達到最佳性價比。

### 3. 最簡版本：Sandbox、Agent、Webhook [02:38]

起手式：向 sandbox 供應商購買環境（或直接用 Firecracker），放入 agent（Codex 或 Claude Code；建議用 OpenCode 或 Pi 等模型中立的開源 harness），接上 GitHub/GitLab 的 PR webhook，把 PR 內容送給 agent，用一行 prompt「review this」再把結果透過 GitHub review API 回傳。多數人以為這樣就完成了——五分鐘後確實會收到回饋。

### 4. 會出什麼問題 

四大失敗模式：

- **漏 bug**：bugs 是「碎形無限」（fractally infinite）的，永遠抓不完，但系統至少必須攔截災難級事故
- **缺上下文**：不理解單一 library 的運作、不懂多倉庫微服務架構（「2010 年代微服務大災難」的後遺症）
- **昂貴**：每個 PR 花費 $3–25，token 悄悄累積
- **Nitpick 註解**：技術上正確但過度挑剔的意見。雙重傷害——人類讀者產生「狼來了」效應；更糟的是 coding agent 會照單全收並逐一「修復」，產出極度防禦性、痛苦冗長的程式碼

關鍵概念：**碎形無限 Bug（Fractally Infinite Bugs）**。

### 5. 修正一：優化 Prompt、剔除 Nitpick 

兩大 prompt 主軸：要求尋找**特定 bug 類型**——對自家 codebase 的歷史事故做資料科學分析，建立最高風險 bug 類型的目錄；以及明確定義什麼是 nitpick 並禁止尋找。陷阱在於：prompt 的小改動會對註解數量產生異常大的影響，而你無法得知反事實——審查者能告訴你 bug 的「存在」，卻無法證明 bug 的「不存在」。僅約千分之一的 PR 含災難性 bug，漏抓後你很久都不會發現。

### 6. 修正二：歷史 PR 資料集

若公司有完整的事故紀錄，就整理出曾造成 outage 的 PR 清單，讓每個版本的 agent 反覆跑這套資料集，量化抓取率後才能放心調 prompt。但 bug 的拓撲與本體論會隨時間演變——80–90% 的 bug 是舊錯重犯，但 coding agent 越強，就會產出前所未見的新型錯誤，需要即時更新的資料集。內部資料能走相當遠，但 Greptile 的優勢正是跨公司的大規模 PR 語料庫。

關鍵概念：**即時更新資料集（Living Dataset）**。

### 7. 修正三：模型反轉 

Claude 與 GPT/Codex 模型的 bug 指紋截然不同：Claude 產生 off-by-one 錯誤的機率約為 GPT 的三倍；GPT 則顯著更易產生 auth bypass。同模型寫、同模型審，會因「以同樣方式失敗」而漏抓。解法：**Claude 寫的程式碼用 GPT 審，反之亦然**，可提升約 10% 抓取率——以事故與 outage 計量，10% 是巨大的數字。實作上 80% 的情況可靠 coding agent 的指紋偵測（Codex 的 branch 命名格式、Claude 的 co-authored-by 標記），最後 20% 需要內部目錄或開發機遙測的啟發式判斷。

關鍵概念：**模型反轉（Model Inversion）**。

### 8. 修正四：Codebase 上下文

grep 並未解決上下文問題：它極不精確且昂貴——coding agent 的 token 消耗絕大多數是重複的「grep、file read、cache write」循環，等於一國 GDP 成長的某個百分比其實是 grep。解法是建立內部知識庫：掃描整個 codebase，編目每個部分（「這是認證模組，這是流程圖，這是所有相關檔案」）再精準索引。實例：偵測 auth bypass 需要具體理解「目前是否處於已認證環境」，grep 做不到。

### 9. 修正五：文件、Tickets 與 Living Wiki 

程式碼正確仍可能是錯的——人們越來越把 Slack 當 IDE 用，一兩句話的指令充滿歧義，agent 可能誤解意圖。最有效的兩類上下文：docs 與 tickets（Jira/Linear + Confluence/Notion），其中蘊含大量你低估了自己擁有的部落知識。Greptile 的做法是用一個 **living wiki** 中介所有上下文源——codebase、production telemetry、日誌、roadmap——形成公司運作的「世界模型」，讓 agent 絕不讀不必要的檔案。

關鍵概念：**Living Wiki（公司世界模型）**。

### 10. 修正六：自主測試與 Computer Use 

React 程式碼讀起來沒問題，渲染後卻可能在 iPhone 上被隱藏。解法：在依賴齊全、完全可組態的 sandbox VM 中啟動整個 stack，讓 agent 用電腦視覺端到端測試。這一代 GPT 與 Opus 模型的視覺能力已讓端到端 QA「近乎解決」。前提條件：完整紀錄所有應用流程，以及夠簡單的 build script 讓 agent 能自行啟動環境（dev box + PR branch 依賴 + flow map）。

### 11. 修正七：便宜模型處理多數子任務

做完上述一切，單次 PR 審查成本仍達 $3–20。對策是模型分層：約 20% 前沿模型用於最關鍵任務（bug 分析、審查流程、首次提交），其餘探索、檔案讀取等長尾 token 用小型模型。實務上 Greptile 有 20 個子任務，各有專屬模型組合，由小型研究團隊持續迭代。可再搭配便宜模型做上下文 re-ranking（可用 Java 決策模型或 Decisions API），決定什麼能進入最昂貴的前沿模型快取。做到這些約能走完 70–80% 的路。

## [結論與行動建議]

**啟發金句**：「審查者能證明 bug 的存在，卻永遠無法證明 bug 的不存在——所以你的防線必須靠資料集與反轉來補足盲區。」

**具體行動建議**：記住「問・據・反・脈・測・省」六字訣——

- **問**：prompt 指名特定 bug 類型、明令禁止 nitpick
- **據**：建立歷史事故 PR 資料集，量化每版 agent 的抓取率
- **反**：Claude 寫、GPT 審（模型反轉）
- **脈**：先建 codebase 知識庫與 living wiki，再讓 agent 搜尋
- **測**：sandbox 中啟動完整 stack，用視覺模型端到端驗證
- **省**：只有關鍵子任務用前沿模型，長尾全部換便宜模型

**生活實踐建議**：即使不自建完整系統，六字訣同樣適用於日常工作流。用 Claude Code 開發 Gitea/MCP 專案時，commit 前刻意換另一家的模型（或 Perplexity 等不同後端）做第二輪審查，就能免費獲得約 10% 的額外防護；把每次踩到的 bug 記進個人筆記形成「事故資料集」，讓未來的 prompt 直接指名你的高風險錯誤類型；在 LLM gateway 的 workflow 中，先派便宜模型過濾與 re-rank 上下文，再送前沿模型，token 帳單能大幅下降。

第二，你必須明確告訴它什麼是吹毛求疵，並要它別去找這些東西。吹毛求疵可以是任何事，例如質問為什麼這裡沒有三層防護，或為什麼錯誤處理寫得有點草率。不過，修改這些提示詞時你會碰到一個狀況：只要改動提示詞裡的一個小地方，代理在 PR 上寫出的評論數量就會出現異常大的變化。

[00:07:01](https://youtu.be/4UtrRVtUN_g?t=421)  
這相當可怕，因為這代表你其實不知道它有沒有漏掉錯誤，你不知道反事實（counterfactual）會是什麼。驗證代理，或其實任何審查者或測試者，都能告訴你錯誤存在，但很遺憾無法告訴你錯誤不存在，這算是這種形式本身的限制。而讓這件事特別困難的，是那些極度罕見、而且一天比一天更罕見的錯誤。事實上，根據我們的資料分析，大約每一千個 PR 只有一個含有真正災難性的錯誤，或者說大約每一千行程式碼才有一個災難性錯誤。

[00:07:30](https://youtu.be/4UtrRVtUN_g?t=450)  
因為這些錯誤非常罕見，你可能釋出一個自認很好的代理版本，但它其實悄悄漏掉了某個 PR 裡的災難性錯誤，而你會很久都不知道，因為你們並不常產生這類錯誤。這就帶到第二個改進：你需要一個歷史 PR 資料集。如果你的公司會把程式碼庫每次出錯的情況都好好記錄下來，這件事相對容易。有了這些紀錄，你就會有一份過去造成服務中斷與事故的 PR 清單。把它們整理成目錄，然後讓審查代理的每個版本都跑過一遍，看看它能以多高的頻率抓到這些錯誤。

[00:08:07](https://youtu.be/4UtrRVtUN_g?t=487)  
這能讓你更有把握地調整提示詞。但同時，錯誤有個有趣之處：在不斷變化的世界裡，錯誤的拓撲與本體（topology and ontology）也會隨時間改變。所以你需要一個即時更新的資料集。這很棘手，因為除非你有數以百萬計的 PR，否則其實很難讓錯誤類型達到夠高的覆蓋率。

[00:08:27](https://youtu.be/4UtrRVtUN_g?t=507)  
確實，你大約 80% 到 90% 的錯誤只是重複過去犯過的錯，但隨著程式碼代理越來越強，它們會開始犯新的錯誤，以我們從未預料過的方式失敗。這時你就會開始碰到極限。順帶一提，這大致就是我們在 Greptile 做的事，只不過我們實際上擁有來自許多不同公司的大量程式碼，能在非常非常龐大的 PR 語料庫上做測試，因此能很有把握地改進我們的代理。這也是我們能在邊際上擠出一點一點效能、而內部審查代理做不到的原因之一。不過，針對你自己的公司，用內部資料做這件事也能走得相當遠。

[00:09:02](https://youtu.be/4UtrRVtUN_g?t=542)  
下一件該做的事是模型反轉（model inversion）。如果有人參加過我今年稍早在舊金山 AI Engineer 的演講，我那時談了很多程式碼代理失敗的方式。我在那次研究中發現一個有趣的模式：Claude 模型和 Codex 模型產生的錯誤類型其實相當不同，而且在好幾個方面都不同。

[00:09:23](https://youtu.be/4UtrRVtUN_g?t=563)  
舉例來說，Claude 模型產生差一錯誤（off-by-one error）的機率大約是 GPT 模型的三倍；另一方面，GPT 模型產生驗證繞過（auth bypass）的機率則明顯高於 Claude 模型。就我所知，這些都只是後訓練（post-training）留下的痕跡。為了防範這點，你會發現如果用同一個模型去審查它自己寫的程式碼，抓到的錯誤會相對較少，因為它在審查時失敗的方式和產生程式碼時一樣。

[00:09:50](https://youtu.be/4UtrRVtUN_g?t=590)  
所以你要反轉模型。如果你用 Claude Code 寫程式碼，就用 GPT 模型來審查，反之亦然。要做到這點，前 80% 的情況相當直接，最後 20% 則相當棘手。如果你在用程式碼代理，會注意到它們會留下某種指紋，告訴你某個 PR 用的是哪個程式碼代理。例如 Codex 會用 `codex/分支名稱` 的格式命名分支。

[00:10:14](https://youtu.be/4UtrRVtUN_g?t=614)  
Claude 則會在 PR 描述和 commit 訊息裡寫上「Co-authored-by Claude」。大約 80% 的時候都是這樣。剩下的 20%，例如你剛好手動建立了分支名稱，或因為其他原因可能用了別的程式碼代理，就很難判斷產生程式碼時用的是哪個模型。你得發展出某些啟發式規則，找出各模型的特徵。通常你可能會有一份內部目錄，讓大家回報最近在用哪些程式碼代理，或從開發機和工程師的電腦收集某種遙測資料。

[00:10:41](https://youtu.be/4UtrRVtUN_g?t=641)  
我們發現，交換模型能讓抓錯率提高 10%。這聽起來可能很少，但要知道，以服務中斷和事故來說，10% 其實相當多。這代表如果你不做模型反轉，出問題的機率會高出 10%，而後果可能相當慘重。所以我們強烈建議你在流程中採用某種模型反轉。

[00:11:04](https://youtu.be/4UtrRVtUN_g?t=664)  
第三個改進是程式碼庫脈絡，這是我非常在意的事。在做程式碼驗證之前，我們做的是程式碼庫脈絡，試著找出更好的方法，在非常大型的程式碼庫上做檢索增強生成（RAG）。即使到了今天，大家還是認為 grep 實際上已經解決了所有程式碼庫脈絡的問題。我其實認為不是這樣，原因有幾個：第一，grep 極度不精確；第二，它非常昂貴。

[00:11:26](https://youtu.be/4UtrRVtUN_g?t=686)  
讓大家感受一下規模：去年 GDP 成長中有個位數百分點來自推論，而推論中很大一部分是程式碼代理。如果你真的去看程式碼代理的執行軌跡，它們用掉的 token 絕大多數都是同樣的東西：grep、讀檔，以及把檔案內容寫進快取。這代表 GDP 成長中有不小的比例是 grep、讀檔、寫快取。

[00:11:47](https://youtu.be/4UtrRVtUN_g?t=707)  
這非常糟糕。原因在於 grep 非常不精確，它會大量讀取檔案；而且，我不確定，按 token 收費的公司或許也有某種反向誘因，想辦法燒掉更多 token。即使如此，你會發現自己需要用更精準的方法來決定該讀哪裡。我們的做法是建立一個內部知識庫：基本上會檢查整個程式碼庫的所有部分，把它們分類整理，然後建立索引，例如：「好，這是身分驗證，它是這樣運作的。

[00:12:12](https://youtu.be/4UtrRVtUN_g?t=732)  
這些是流程，這是流程圖，這是所有相關的檔案。」程式碼庫脈絡很重要的一個例子，是當你想抓出驗證繞過時。要判斷是否發生了驗證繞過其實非常困難，因為你必須相當具體地了解，當你在程式碼庫的那個部分時，是否處於已驗證的環境中。這非常棘手。所以你會發現，你需要某種程式碼庫脈絡才能做到這件事。

[00:12:36](https://youtu.be/4UtrRVtUN_g?t=756)  
到目前為止我一直圍繞著「錯誤」這個概念在談，但程式碼即使沒有錯誤，也可能非常非常糟。第一，它可能品質很差；第二，它可能根本沒有實現作者表達的意圖。最近我看到一篇貼文說，越來越多人把 Slack 當成他們的 IDE。我覺得這有點好笑，但同時，一則 Slack 訊息裡表達的意圖其實沒有多少。

[00:12:58](https://youtu.be/4UtrRVtUN_g?t=778)  
你可能只說了一兩句話，甚至更少，就叫代理去修某個東西，這代表你的指示充滿模糊之處。結果你可能會發現，程式碼代理不是誤解了你的指示，就是指示太模糊，它不知道確切該做什麼。所以，正確的程式碼其實仍可能錯得離譜。我們對抗這個問題的方法之一，是給代理越來越多的脈絡。我們發現最重要的兩種脈絡是文件和工單，當然還有來自程式碼庫索引器或知識庫的程式碼庫本身。

[00:13:29](https://youtu.be/4UtrRVtUN_g?t=809)  
只要讓它存取你的 Jira 和 Linear，再加上 Confluence、Notion 或任何你存放文件的地方，就能走得出乎意料地遠。你會發現有很多部落知識（tribal knowledge）在潛意識中幫助你寫出更好的程式碼。當你讓代理做同樣的事時，會覺得它們好像完全搞不清楚狀況，那是因為你低估了自己擁有多深厚的知識。

[00:13:51](https://youtu.be/4UtrRVtUN_g?t=831)  
Greptile 處理這個問題的方式，是用一個活的 wiki 取代所有這些脈絡來源之間的中介。這個 wiki 本質上是一個關於你們公司如何運作的世界模型：包括它對你的程式碼庫所知的一切；透過正式環境遙測與日誌，對你的應用程式所知的一切；以及從你的文件、Linear 工單等來源，對你的產品路線圖所知的一切。

[00:14:14](https://youtu.be/4UtrRVtUN_g?t=854)  
它用這個 wiki 來提供脈絡，一方面讓代理更了解脈絡，一方面讓它的程式碼搜尋精準得多，因為它絕不會去讀不需要讀的檔案。最後一件該做的事，或者這可能是五件中的第四件，下一件該做的事是自主測試。（清喉嚨）我們常思考的一件事是：以 UI 變更為例，你也許可以讀完一堆修改過的 React 程式碼檔案，得出程式碼沒問題的結論；但實際渲染出來時，它可能在 iPhone 上被遮住了。

[00:14:47](https://youtu.be/4UtrRVtUN_g?t=887)  
這是技術上比較難解的問題之一。Greptile 的做法是建立這些依賴完整的沙箱，也就是完全可設定的虛擬機器，並和客戶合作，在這些沙箱裡把他們的整套系統跑起來。接著 Greptile 的代理會用電腦視覺做端到端測試。

[00:15:09](https://youtu.be/4UtrRVtUN_g?t=909)  
如果你最近沒在關注，電腦視覺已經變得非常強，新一代的 GPT 模型和 Opus 模型比上一代好得多。我認為端到端 QA 第一次接近被解決了。不過你需要做的是：第一，把應用程式中所有流程記錄成文件；第二，要有夠簡單的建置腳本，讓代理能在你的環境中把整套系統跑起來。

[00:15:30](https://youtu.be/4UtrRVtUN_g?t=930)  
我們有一支前線部署工程師（forward deployed engineer）團隊協助公司做這件事，我們發現這是比較棘手的部分之一。當然，如果你已經有非常好的開發機環境（dev box），那恭喜你在 Stripe 工作。喔，這就是我要給大家看的圖。沒錯，你需要一台開發機、執行應用程式時所需的 PR 分支依賴，還需要某種流程地圖，標明「這是驗證程式碼，這是註冊流程」等等。

[00:15:54](https://youtu.be/4UtrRVtUN_g?t=954)  
有了這些，你的代理現在就能端到端測試你的程式碼，並用視覺模型指出：「喔，這個按鈕技術上有出現，但在 iPhone 上其實被遮住了」，或「它在 iPhone Duo 上不在第一屏」等等。不過，就算把這些全做了，你會發現成本還是相當高。審查一個 PR 可能要花 3 美元到 15、20 美元不等。

[00:16:14](https://youtu.be/4UtrRVtUN_g?t=974)  
這時你要解決的，是在某些事情上改用比較便宜的模型。對我來說，前沿模型整體而言仍比開源模型更有能力。這種情況已經持續一段時間了，雖然兩者的差距正在縮小。所以我們目前大約 20% 用前沿模型處理最關鍵的任務；其餘長尾的 token，例如探索、讀檔等等，則用各種較小的模型。

[00:16:37](https://youtu.be/4UtrRVtUN_g?t=997)  
這麼做之後，你其實能大幅降低審查代理的執行成本。這是我們做法的示意範例：我們用小模型尋找脈絡，用非常輕量的電腦操作模型測試使用者流程，再用前沿模型分析錯誤、執行審查流程和首次提交。

[00:16:57](https://youtu.be/4UtrRVtUN_g?t=1017)  
實務上，我們其實有 20 個不同的子任務，每個子任務都有一組非常特定的模型。我們還有一個小型研究團隊，不斷反覆調整哪個任務該用哪個模型。你大概只要用類似這樣的方式，把非常簡單的任務換成非常簡單的模型，就能做到 70% 到 80% 的效果。這又是一個擁有超大資料集會很有幫助的例子。如果沒有好的資料集，你可能會很衝動地把許多子代理換成更小、更快的模型，卻不知道這個代理其實抓錯能力已經變差不少，直到它漏掉某個問題、造成服務中斷或事故時，你才會發現。

[00:17:34](https://youtu.be/4UtrRVtUN_g?t=1054)  
你也會發現，可以用一個便宜的模型來對抗過度讀檔的問題：讓它檢視所有脈絡片段，判斷哪些真的應該納入。理論上，你應該能用某種決策模型或決策 API 來做這件事，對所有不同的內容做有效的重新排序（re-ranking），決定哪些該載入、哪些不該載入前沿模型的快取，而這在某種程度上是你最昂貴、也最稀缺的資源。
