## [核心摘要]

這支影片示範如何用 Claude Code 打造 V2 版「軟體工廠」：以 GitHub issues 為輸入、PR 為輸出，由單一協調者平行派發多個子代理（受理、規格、建置、審查、核准），並以 shell 腳本構成**確定性骨幹**貫穿整條流水線。核心貢獻在於解決「代理式開發不可靠、不可觀測」的痛點——透過關卡測試、風險分級路由（Haiku/Sonnet）、成本耗時追蹤與可重啟的耐用性設計，讓代理流程從 Demo 級走向可長期運維的工程系統。

## [詳細重點整理]

### 1. V2 工廠的整體流程設計

V2 相較 V1 的升級：新增 Fable 受理步驟、Haiku 動態路由、更多確定性測試、GitHub issues 為輸入、PR 為輸出、單一協調者平行處理多工作。完整流水線為：**受理→ 規格撰寫→ 建置→ 確定性關卡→ 多審查者平行審查→ 核准者→ 自動合併或人工審查**。

**關鍵概念：代理式流水線**——把軟體開發拆解為多個專責子代理串接的生產線。

### 2. 受理步驟：用 Fable 做前期把關 

Fable 在流水線最前端評估功能是否值得做：界定範圍、評估風險、可拒絕功能或向人類索取更多資訊。風險標籤會一路傳遞，決定後續審查者的模型選擇（低風險用 Haiku、高風險用 Sonnet）與審查步驟的組合（如中等難度才加資安審查者）。

**關鍵概念：風險分級路由**——用前端代理的判斷，最佳化後續步驟的成本與深度。

### 3. 確定性關卡與審查退回機制

建置完成後必須先通過低成本關卡（Gate），執行測試、lint、型別檢查、建置等確定性檢查；失敗直接退回建置者，不需消耗審查代理。審查者（程式碼、UX、UI、資安）全部平行執行，任一審查失敗會帶著回饋退回建置者重跑，形成**遞迴自我修正**的閉環。

### 4. 安裝與實際操作 

安裝方式：在 Claude Code 中貼上提示詞並附上原始碼 repository 連結，Claude 會在專案中生成 `.claude` 資料夾（agents、skills/[SKILL.md](http://SKILL.md)）與 `factory` 資料夾（bin 腳本、設定檔、儀表板），並依專案調整 [`check.sh`](http://check.sh) 與 [AGENTS.md](http://AGENTS.md)。操作指令：`factory run`（處理所有已標籤 issue）、`factory run n`（處理特定 issue）。

**關鍵概念：factory 標籤安全機制**——issue 必須手動加上 `factory` 標籤才會進入佇列，避免任意 issue 觸發代理處理。

### 5. 單一 issue 完整走完工廠 

示範中 dark mode 功能從受理、規格、建置、通過關卡、審查退回、重審到核准者判定自動合併，全程約 8 分鐘、估計成本 3.40 美元，最終在 GitHub 上留下完整軌跡：PR 建立、合併、issue 關閉。

### 6. 並行處理與人類介入 

工廠預設並行數為 3（記錄於 `factory.config.json`，可調整）。工作進入「needs human」狀態時會暫停並空出名額；人類可透過協調者對話或另開 Claude Code 實例（使用 factory skill）回答問題，回饋會被持久寫入（如 [`feedback1.md`](http://feedback1.md)），工作隨即恢復推進。

**關鍵概念：Human-in-the-loop**——代理流程中設計暫停點，讓人類只處理真正需要決策的環節。

### 7. 耐用性與可觀測性設計

關閉協調者工作階段（Control+C）會中止所有背景子代理，但工廠是**耐用**的：重新執行 `factory run` 會掃描佇列與既有狀態，將工作重新啟動。關鍵設計在於 `job.json` 由 `factory/bin/job` 腳本獨佔寫入，Claude Code 只能呼叫腳本更新、不能任意改寫，以程式化方式保證工作生命週期的一致性。工作資料（各輪審查、代理日誌、決策記錄）存於本機 `factory/jobs/`，被 git 忽略，可另行備份到雲端。

**關鍵概念：確定性骨幹**——用 shell 腳本（[checks.sh](http://checks.sh)、gate、route、jobs）而非 LLM 自由發揮來驅動狀態轉移。

## [技術/數據對比]


| 面向    | V1 工廠 | V2 工廠                                |
| ----- | ----- | ------------------------------------ |
| 輸入／輸出 | 專案內指令 | GitHub issues → PR                   |
| 前置把關  | 無     | Fable 受理（可拒絕、可提問）                    |
| 路由    | 靜態    | Haiku 動態路由，依風險分派審查者與模型               |
| 可靠性   | 較少測試  | 整條流水線內建確定性關卡                         |
| 可觀測性  | 有限    | 每個工作的成本與耗時（如 dark mode：8 分鐘、3.40 美元） |
| 並行    | 單一    | 最多同時 3 個工作（可設定）                      |


模型選擇的成本辯證：在審查階段用 Haiku 省錢可能適得其反——較弱的審查者反覆退回工作，重跑建置者的總成本反而更高；核准階段是否該交給 Haiku 決定「能否合併進程式碼庫」也值得質疑。

## [結論與行動建議]

**啟發金句**：軟體工廠的可靠性不是來自更聰明的代理，而是來自代理繞不過的確定性骨幹。

**具體行動建議**（D-S-G 法則）：

- **D**eterministic spine：所有狀態轉移交給腳本，不讓 LLM 自由改寫
- **S**ingle writer：每份狀態檔（如 job.json）只有一個程式化寫入者
- **G**ate before agents：便宜的確定性檢查放在昂貴的代理審查之前

**生活實踐建議**：

- 把 D-S-G 法則用在任何 AI 工作流（如 Gitea + MCP + Actions 自動化）：用 webhook/腳本當骨架、讓 LLM 只負責判斷與生成，系統就能從 Demo 變成可運維的服務
- 善用「標籤觸發」模式：任何系統（如正式環境監控）偵測到問題時自動開 GitHub issue 並加 factory 標籤，工廠即自動接手，不必另建整合層
- 複雜度是成本：安裝後先問「哪個步驟可以拿掉仍保有可靠性」，動態 DAG 的效率收益需與維護成本權衡
