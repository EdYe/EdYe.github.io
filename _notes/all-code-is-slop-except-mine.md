# All Code Is Slop (Except Mine) — Lauren Tan

## [核心摘要]

AI 代理人時代，軟體工程師的核心工作不再是「寫更多程式碼」，而是打造一個能讓你**信任代理人產出**的環境。講者（SpaceX SI / Grokbot 負責人 Lauren Tan "Potato"）分享如何透過「倒金字塔」投資法——從程式碼庫、靜態分析、執行期驗證到形式驗證——把代理人產出的「垃圾程式碼（slop）」變成黃金，實現一個月 11,000 個 PR 上正式環境、回退率僅 0.5% 的高品質高速出貨。

## [詳細重點整理]

### 1. 痛點：代理人讓人人都成為「寫程式機器」

有代理人之前，工程產出數量差異極大，只有少數像 Brett Taylor（一個週末重寫 Google Maps）這樣的「寫程式機器」能產出誇張的程式碼量。現在有了代理人，**任何人都能成為寫程式機器**，但數量暴增帶來品質崩壞的風險——講者上個月把 3,000 個 PR 送上正式環境，很多還是在睡覺時完成的。軟體工程的「玩法」變成：在大幅提升生產力的同時，維持甚至提升程式碼品質。

**關鍵概念：寫程式機器（Code Machine）**——代理人把頂尖工程師的超高產出能力民主化，但前提是你能控制品質。

### 2. 核心方法論：從低信任到高信任的倒金字塔

不要稱之為「軟體工廠」，真正的問題是**信任**。講者提出一個倒金字塔模型，決定把時間投資在代理人環境的哪一層：

- 底層（最確定性）：良好的 **API 設計、架構、重構**——用程式碼本身限制代理人
- 中層：**lint 規則、型別系統、編譯器、測試**——迫使代理人預設做對的事
- 上層：**驗證（執行期驗證與形式驗證）**——找出錯誤、檢查不變量（invariant），確認代理人理解你的意圖
- 頂端（僅一點點）：**文字說明**——規則、技能、[agents.md](http://agents.md) 這類需要判斷力的東西

投入六個月才能達到送出數千 PR 的程度，但後進者花的時間會少得多。

### 3. 程式碼庫即最大輸入：花園比喻

代理人根據輸入產生輸出，而**程式碼庫就是最大的輸入**。核心法則：**每當你糾正代理人時，把這個糾正變成確定性的檢查，而不是在 [agents.md](http://agents.md) 裡多加一行**——寫成程式碼可重現性高得多。

**關鍵概念：程式碼庫即花園（Garden Metaphor）**——2024 年每位工程師每天審 3 個 PR，現在是 300 個。程式碼像連續不斷的水流、像活的東西，你的架構限制與護欄是混凝土地基，新程式碼圍繞它生長。任何權宜之計、反模式、技術債都會被下一個代理人當成「既定模式」直接複製，像雜草在察覺前蔓延。當軟體工程師的工作越來越像園藝。

### 4. 實例一：Dune 框架——用約束根治 useEffect

Dune 是 Grokbot 的用戶端框架（可想成 Electron 版的 Next.js），技術上不有趣，有趣的是它把打造桌面應用學到的教訓**編譯進限制與 lint 規則裡**。

核心教訓：**任何需要細膩拿捏才能用好的東西，往往導致垃圾程式碼**。經典例子是 React 的 `useEffect`——有人開玩笑說要用好它得有博士學位，而代理人不擅長細膩拿捏。解法：直接在產品程式碼中**禁用** `useEffect`，只允許在 Dune API 內部使用。結果這個問題被徹底根除，程式碼審查時再也不用抓它。

### 5. 實例二：用目錄結構提供脈絡 [06:10]

Cursor（Electron 應用）上的反模式：代理人常把主執行緒程式碼匯入渲染執行緒，造成長任務與卡頓。解法：約定俗成的頂層目錄 `electron-renderer` 與 `electron-main`，兩者之間的匯入被**相依圖分析器與 lint 規則禁止**。設定簡單，但審查時又少一件要人腦檢查的事。

**關鍵概念：用目錄結構提供脈絡（Structure as Context）**。

### 6. 實例三：禁用 99% 的程式碼註解

代理人把 Markdown（文件、註解、規則）當成寫下「為什麼不做對的事」的逃生口，或對小糾正矯枉過正變成鐵律。實際案例：代理人大量使用 `setTimeout`、`requestAnimationFrame`、`requestIdleCallback` 這類**命令式計時器**作為快速修補，掩蓋 VS Code 命令式風格與 React 宣告式風格之間的架構衝突；大量計時器快速建立銷毀造成主要垃圾回收，導致延遲卡頓，最糟的是代理人還寫註解合理化這些修補，計時器蔓延到各處。

Grokbot 的教訓：**禁用 99% 的註解**，因為註解容易過時、人類懶得讀、給代理人合理化逃避的逃生口，而且**註解無法強制執行**。改用會給出清楚錯誤訊息的 lint 規則，逼代理人修正根本原因而非打補丁。

### 7. 驗證層：讓代理人自主的關鍵

當你把足夠多的糾正變成確定性檢查後，審查時需要留意的事越來越少，最終可以讓代理人**自己合併大部分 PR**。此時程式碼審查縮減成主要看**驗證產物**：影片、截圖、圖表、形式驗證結果。

- **執行期驗證（Runtime Verification）**：讓代理人自己執行程式碼，使用人類開發者也用的除錯工具（如 Chrome DevTools Protocol）
- **功能地圖（Feature Map）**：從使用者角度列出所有可用功能，像網站地圖，提供共同詞彙——說「左側邊欄那個東西」時代理人不用猜
- **自訂 CLI**：代理人重複使用同一組 CLI 與驅動程式，減少 token 用量且可被測試
- **形式驗證**：用 TLA+ 對主要使用者流程（如跨裝置通知）做模型檢查；用 Lean 證明自寫虛擬化函式庫不出現閃爍抖動；用 Bombadil 做 UI 的基於性質測試（property-based testing）

呼應 Cindy 的推文：六個月前她無法信任代理人（細微錯誤一直被合併），缺口在驗證流程；現在**每天 70% 的 token 都花在驗證上**——與講者自身觀察一致。這些工具都不是新技術，只是良好軟體工程，以前因成本高而卻步，代理人把成本大幅降低了。

**關鍵概念：軟體測試與驗證的黃金時代（Golden Age of Testing & Verification）**。

### 8. 應許之地：11,000 PR / 月的實績

投資換來的成果：開發速度起飛，上個月團隊把 **11,000 個 PR** 送上正式環境；約**每天切一個穩定版本**；10 月約 **227 人**至少貢獻一個 PR。品質同時提升：被回退的 PR 比例反而**降至約 0.5%**；Grokbot 效能比剛推出時更好——啟動、打字、開新對話、切換對話全都變快。

### 9. 行動順序：先內圈後外圈

在一頭栽進打造「軟體工廠」之前：

1. 先從**改善程式碼庫**著手：每糾正代理人一次，就寫一條 lint 規則防反模式再現，並清理舊模式
2. 確保**驗證機制扎實**——這些工作本來就是自動化的前提
3. 警告：**如果你的內層開發迴圈產出垃圾，把它自動化只會產出更多垃圾**，你得投入越來越多昂貴的 token 去解決問題
4. 基礎打穩後，才打造外層迴圈：Grokbot 的連接器、例行任務（routine）、專案功能可協調數百甚至數千個代理人

實例：每當切出新版本，Grokbot 自動建立 Cursor 專案對整個應用程式做**模糊測試（fuzzing）**，像真實使用者一樣操作找錯，針對每個錯誤開出修正 PR 並**自動合併**——因為程式碼庫夠好，PR 預設就是好的，大部分產品程式碼已不需人類深入審查。

## [結論與行動建議]

**啟發金句**：「把垃圾自動化，只會得到更多垃圾——先把內圈修好，再放大規模。」

**具體行動建議（D-L-C 法則）**：

- **D**eterministic（確定性）：每次糾正代理人，先想能否變成 lint 規則、型別或測試，而不是加文字規則
- **L**ibrary（程式碼庫）：把程式碼庫當花園照料，禁用需要「細膩拿捏」的 API（如 useEffect）、禁用大多數註解、用目錄結構提供脈絡
- **C**ertify（驗證）：token 預算的大部分投在驗證——執行期驗證、功能地圖、形式驗證（TLA+ / Lean）、性質測試

**生活實踐建議**：這套「先修內圈再自動化」的原則同樣適用於任何 AI 工作流——例如你用 Claude Code + MCP 建構的自動化管線：與其在 prompt 裡不斷補規則（等同 [agents.md](http://agents.md)），不如把重複出錯的步驟抽成帶有明確錯誤訊息的 CLI 工具或 lint/測試（確定性檢查）；在 Gitea Actions 的 webhook 流程中，先讓單次執行的品質穩定，才值得排程夜間批次放大。審查產出時，看「驗證產物」（測試報告、截圖、log）而非逐行讀程式碼，就能在品質不墜的前提下把產出量放大一個數量級。

還有一件讓我意外的事，是代理人使用 Markdown 的方式，像是文件、程式碼註解、規則或技能。它們把這些地方當成寫下「為什麼不做對的事」的理由的地方。又或者，不知道你有沒有看過，它們會對你某個小小的糾正矯枉過正，把它當成一條永遠不能打破的鐵律。

[00:07:22](https://youtu.be/O_zcc6Xl12g?t=442)  
這是另一個來自 Cursor 的例子。代理人非常愛用命令式的計時器，像是 setTimeout、requestAnimationFrame、requestIdleCallback。它們把這些當成快速修補，因為它們其實是在掩蓋 VS Code 的命令式風格與 React 的宣告式風格之間的架構衝突。

[00:07:44](https://youtu.be/O_zcc6Xl12g?t=464)  
所以我們選擇的架構其實讓用戶端和代理人的表現都變得更差。如果你做過 JavaScript 的效能調校，就會知道當大量計時器被快速建立又銷毀時，會造成大量的主要垃圾回收，進而導致延遲和卡頓。但最糟的是，代理人寫了很多程式碼註解，就像這裡紅色標示的，解釋為什麼這個快速修補是合理的。

[00:08:12](https://youtu.be/O_zcc6Xl12g?t=492)  
不知不覺間，計時器就蔓延到各處，應用程式的效能也大受影響。在 Grokbot，我們學到了教訓，決定直接禁用 99% 的註解，因為註解很容易過時。而且說實話，人類根本懶得讀那些垃圾註解。

[00:08:33](https://youtu.be/O_zcc6Xl12g?t=513)  
再說，註解給了代理人一個逃生口，讓它可以因為「這很難」而合理化不做對的事。但註解最糟的地方在於它們無法強制執行。所以看似出於好意的做法，像是「我要告訴下一個代理人不要做某件事」，最後從來都不會變成你真正能信任的東西。

[00:08:54](https://youtu.be/O_zcc6Xl12g?t=534)  
所以在 Grokbot 和 Dune 裡，我們現在有一些 lint 規則，會給出清楚又有幫助的錯誤訊息，告訴代理人去修正根本原因、真正的問題，而不是繞過去打補丁。我們的大原則是：每次糾正代理人，都要把它變成這類確定性的檢查，或者思考如何透過更好的 API 設計、更好的架構，在程式碼中徹底根除這個問題。

[00:09:23](https://youtu.be/O_zcc6Xl12g?t=563)  
只要你這樣做夠多次，就會發現程式碼審查時需要留意的事情越來越少。到了某個時候，你會發現已經沒什麼好審查的了，可以讓代理人自己合併大部分的拉取請求。好，接下來，驗證也是讓代理人更自主、提升我們對其成果信心與信任的一大關鍵。

[00:09:50](https://youtu.be/O_zcc6Xl12g?t=590)  
我們的程式碼審查流程現在已經縮減成主要在看驗證產物，像是影片、截圖、圖表、形式驗證。最基本的例子是執行期驗證（runtime verification），這只是一種比較花俏的說法，意思是讓代理人能自己執行程式碼，並使用人類開發者也會用的除錯工具，例如 Chrome DevTools Protocol。

[00:10:16](https://youtu.be/O_zcc6Xl12g?t=616)  
在我們的執行期驗證技能裡，有個東西我們稱為「功能地圖（feature map）」。它基本上就像網站地圖，從使用者的角度列出應用程式中所有可用的功能。有了它，當你說「左側邊欄那個東西」時，代理人就不需要用猜的，它提供了一套共同的詞彙。

[00:10:37](https://youtu.be/O_zcc6Xl12g?t=637)  
我們也在這些技能裡使用自訂的 CLI，讓代理人每次都能重複使用同一個 CLI 和驅動程式，這能減少 token 用量，也可以被測試。最近我們也開始研究形式驗證，現在用 TLA+ 對主要的使用者流程做模型檢查，例如跨多個裝置與平台的通知。

[00:11:03](https://youtu.be/O_zcc6Xl12g?t=663)  
我們也用 Lean 來證明某些演算法。例如我們自己寫了一個虛擬化（virtualization）函式庫，就用 Lean 來檢查不會出現閃爍或抖動的問題。整體來說，我們還在實驗這種做法，看起來非常有前景，我們已經透過形式驗證找到不少錯誤。

[00:11:25](https://youtu.be/O_zcc6Xl12g?t=685)  
但它當然不是萬靈丹，我們把它當成另一個工具，代理人環境中的另一層。然後這段影片播得很快，不過我們最近也開始研究針對 UI 的基於性質的測試（property-based testing），用的是一個叫 Bombadil 的函式庫。

[00:11:45](https://youtu.be/O_zcc6Xl12g?t=705)  
它也已經幫我們抓到幾個 UI 錯誤了。好，把視角拉遠一點。我看到 Cindy 的這則推文，六個月前她談到自己無法信任代理人，因為有些細微的錯誤一直被合併進去。真正讓她無法信任代理人的缺口，在於驗證流程。而六個月後的現在，她說她每天 70% 的 token 都花在驗證上。我會說這跟我觀察到的一致，我大部分的 token 用量也都花在驗證上。

[00:12:22](https://youtu.be/O_zcc6Xl12g?t=742)  
如果你仔細看她的流程，這裡沒有任何一項是我們以前沒有的新穎技術。它們都只是良好的軟體工程工具，只是以前可能因為難以理解、撰寫或維護而成本高得讓人卻步。但代理人大幅降低了這個成本。

[00:12:43](https://youtu.be/O_zcc6Xl12g?t=763)  
我們真的正在進入軟體測試與驗證的黃金時代，因為代理人讓我們能以遠超過去經濟上可行的程度去測試一切。形式驗證也能幫你更好地推敲產品應該如何運作，以及代理人是否真的理解你的意圖與目標。我在我的外掛 pstack（potato stack）裡做了一個新技能叫 state chart，可以從使用者的角度把狀態機視覺化。

[00:15:11](https://youtu.be/O_zcc6Xl12g?t=911)
