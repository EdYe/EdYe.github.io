# How to Actually Code with AI (ft. Matt Pocock) — 結構化筆記

**來源**：NetworkChuck｜長度 02:02:36｜上傳 2026-11-20

## [核心摘要]

AI agent 極擅長「戰術性」寫程式、極不擅長「戰略性」思考，因此開發者的新職責是經營 agent 的運作環境：用共通詞彙表與 ADR 建立溝通、用「grill → spec → ticket → review → retro」迴圈出貨、用深模組與自動化檢查約束 agent，逐步爬上信任階梯。痛點：vibe coding 會讓程式碼庫持續惡化，而你不修正環境、只換更強的模型也無解 。

## [詳細重點整理]

### 1. 戰術 vs 戰略：AI 時代的新分工 

引用 John Ousterhout《A Philosophy of Software Design》：戰術型程式設計是打贏眼前戰鬥的中士，戰略型是打贏整場戰爭的將軍。AI 在基準測試中只針對單一任務計分，重心百分之百是戰術；戰略錯誤通常要九個月後才反噬，所以模型天生不會在乎長期。結論：戰術交給 AI，戰略由你掌握 。

**關鍵概念：戰術型／戰略型程式設計（Tactical vs Strategic Programming）**

### 2. Vibe Coding 的盡頭：環境惡化

vibe coding 一詞已出現**語義擴散（semantic diffusion）**，原始定義是「不看、不想程式碼」。純 vibe coding 從來沒有行得通：戰術型 agent 只解決眼前問題，而程式碼就是 agent 的居住環境——環境持續惡化，就像「這樣很好」的著火狗迷因，agent 看著房子倒塌仍想把工作做完。不用 AI 才是荒謬的，因為戰術性工作如今可用低於最低工資的成本外包給模型 。

### 3. 策略性程式設計的第一步：在乎

軟體工程一直比大家想的容易，策略性程式設計的核心就是「比你旁邊的人多在乎一點點」——在乎產出品質、在乎 agent 的環境。能分辨團隊中誰是策略性工程師的指標，就是誰更在乎 。

### 4. Grill with Docs：用領域語言盤問需求

以 course video manager repo 示範。第一步是謹慎思考與 agent 合作使用的語言，概念來自 **領域驅動設計（Domain-Driven Design）**。grill with docs 技能會先探索程式碼庫、讀取**詞彙表（glossary）**（course、section、course version、lesson、draft version、pending version 等），再反向盤問你：「提詞機讀什麼內容？朗讀時螢幕上還有什麼？」——強迫 agent 跨越溝通落差、在動工前對齊需求。agent 像失憶的《記憶拼圖》主角，且溝通落差不會因模型變聰明而消失，因為問題出在人這一邊 。

### 5. 詞彙表與 ADR：agent 的長期記憶

- **詞彙表**：所有技能內建「請參考詞彙表」，規格與模組都使用同一套語言，讓 agent 像住在你腦袋裡。從零開始也可直接開始拷問，在熱點區域慢慢長出詞彙，像在爛程式碼裡開出理智的小窗 。
- **架構決策紀錄（ADR）**：記錄「無法用程式碼記錄的事」——昂貴、難以回頭的決策。沒有它，agent 會重複犯同樣的錯。該 repo 累積約 31 份 。

### 6. 聰明區與笨蛋區：上下文偏執

**上下文視窗**並非均質：token 越多、token 間關係以平方級增加，注意力退化，決策變笨。約 15 萬 token 就開始緊張——早於帳面規格、且省錢省延遲。重點不是數字，而是「上下文偏執」的直覺。超過門檻就把拷問對話轉成**規格（spec）**（markdown 或 GitHub issue），再拆成工單 。

**關鍵概念：聰明區／笨蛋區（Smart Zone / Dumb Zone，出自 Dex Hy）**

### 7. Effort 設定：探索用 medium 就夠

「高 effort 流行病」：探索程式碼庫不需要 xhigh——它只需讀對的檔案並回報，開高 effort 只是在不該花 token 的階段燒 token，更快掉進笨蛋區。預設 Opus 5.5 medium；研究網路資料、效能測試、需要嘗試多種做法的除錯才調高。真正值得高 effort 的時機是 agent「驗證自己工作」的時候 。

### 8. 規格 → 工單 → 平行實作 → 對抗式審查

implement spec 技能以平行 sub agent 在 work tree 實作所有工單再合併成大型 PR；每張工單約 15 萬 token、以 GitHub sub-issue 追蹤。之後自動觸發 code review，分兩軌：**規格審查（spec review）**核對是否做對事、有無過頭或不足；**標準審查（standards review）對照 [coding-standards.md](http://coding-standards.md)（禁用 any、Effect 庫規範等）做對抗式審查（adversarial review）**。與其等下一個模型解決所有問題，何不直接把問題解決掉 。

### 9. 人工審查：單向門 vs 雙向門

PR 技能產出視覺化摘要、可運作證據（截圖／執行結果），以及合併風險評估：

- **單向門（one-way door）**：合併後無法回頭（資料遺失、email 寄給 10 萬人）——必審查，而且要試著把它弄壞
- **雙向門（two-way door）**：可逆、**影響範圍（blast radius）**小——可直接合併甚至正式環境驗證

### 10. Retro：讓審查意見回流成標準

retro 技能回顧整個 session 與 PR 審查留言，提出改進建議：怎麼改善環境，才能「再也不用寫這則留言」。每次執行 Retro，自動化檢查的威力就升一級，最終 agent 像穿上拘束衣、幾乎不可能犯錯 。

### 11. 信任階梯與回饋迴路

Lauren Tan（Grokbot）每月出貨約 2,500 個 PR 的關鍵是**信任階梯**：不信任 agent 就永遠無法擴展超過約 4 個同時運作的 agent。好程式碼庫的收斂定義是「容易修改的程式碼庫」，需要大量**回饋迴路（feedback loop）**讓 agent 替自己的工作打分數。個人軟體可抽樣信任（每 5 個 PR 檢查一次）；金融、醫療等單向門場景則燒大量 token 在驗證上 。

### 12. 自動化檢查三本柱

- **嚴格型別**：TypeScript 取代 JavaScript，型別能極快告訴 agent 它錯了；any 是作弊
- **執行期測試（runtime test）**：驗證執行時真的做了該做的事
- **Linter**：檢查正確的函式、模組匯入、避開壞模式

### 13. 深模組與 improve codebase architecture

測試難寫對，因為容易寫出「只是重複實作」的測試（如檢查字數上限是 240）。解法是 John Ousterhout 的**深模組（deep modules）**：模組內部對測試隱藏，只透過窄小進入點測試，改內部不必改測試。improve codebase architecture 技能產出 HTML 報告（實例：找出 150 行重複程式碼，建議合併依賴單一深模組），並以 cron job 每天「拉桿一次」——因為都是雙向門，不必太擔心，持續對抗 slop 浪潮 。

### 14. teach 技能：把報告變課程

看不懂架構報告時，丟給 teach 技能說「教我」，它會建立工作區、測你懂多少、出題考你、產出循序漸進的 HTML 課程（曾用它學會解魔術方塊）。審查報告使用共通語言，例如**局部性（locality）**：修改一段程式碼時，所有相關修改有多大機率落在同幾個檔案裡。領域專家與模型的協作優勢就在語言：說「修 hydration error」遠比描述症狀有效 。

### 15. DevOps 已被抽象化

過去 10–20 年 DevOps 從自架 Linux 主機演進到 serverless 平台（Vercel、Netlify）。新手建議：資料不知道放哪就用 Postgres（Supabase、PlanetScale 代管），部署用 Vercel，push 到 GitHub 即自動部署，不必碰 AWS 的 foot gun。安全面則在 code review 中加入資安審查（多數 harness 內建）即可 。

### 16. Skills 的 Eval：使用者就是評測

skills 極難做傳統 **eval**（基準測試）：如何評測 grill with docs 是否選對術語？優勢在於數百萬使用者與活躍 Discord 就是「以人為本的評測」——傾聽、回應、持續改進。Issue 處理也自動化：agent 在假 repo 重現問題、過濾垃圾 issue、建立 PR，排程每日執行 。

### 17. 開源協作與 agent 工作流

以自身 18 歲參與開源的經驗對照今日：agent 可處理 issue 重現（repro）、npm changeset 管理、GitHub Actions 上的 PR 流程與 AI triage；討論了 HonoJS 貢獻、BDFL（Benevolent Dictator For Life）治理模式，以及 5 → 100 → 200 個 agent 的擴展願景 。

### 18. 經典書單與課程 

策略性程式設計的知識源頭：Ousterhout《A Philosophy of Software Design》、Thomas & Hunt《The Pragmatic Programmer》、Michael Feathers《Working Effectively with Legacy Code》、Fowler《Refactoring》、Kent Beck《Extreme Programming》。搭配 improve codebase architecture 與 teach 技能內化。課程以 cohort 形式推出（趕在寶寶 11 月底出生前）。

### 19. Slop Cannon 與日常自動化

談 agent software factory 的日常 routine：cron job 排程、grilling 與 merge 流程；提出 **slop cannon** 一詞形容無約束的 agent 產出洪水，對策是 harness 層面的 loop engineering。也展示個人內容產線：Gemini API、[Frame.io](http://Frame.io)、Adobe Premiere XML 整合，以及用 wiki 加 cron job 匯整 Discord/Slack/Gmail 資訊的知識管理（提及 Karpathy 與 LLM 觀點）。

### 20. 結尾資源

資源入口：[aihero.dev/skills](http://aihero.dev/skills)（技能完整文件）、AI 程式開發辭典（GitHub repo 可供 agent 指向）、Discord、Twitter、YouTube 。

## [結論與行動建議]

**啟發金句**：「與其等下一個模型來解決你的所有問題，何不直接把你的問題都解決掉？——策略性程式設計的全部，就是比旁邊的人多在乎一點點。」

**具體行動建議（G-S-I-R-R 迴圈）**：下一個功能照走五步——**Grill**（用 grill with docs 盤問對齊）→ **Spec**（超過 15 萬 token 就寫規格）→ **Implement**（implement spec 平行工單）→ **Review**（規格＋標準雙軌對抗式審查）→ **Retro**（回顧意見回流成 coding standards 與自動化檢查）。

**生活實踐建議**：

- 把 glossary/ADR 概念搬到個人知識管理：為常用 AI 工具建立一份自己的詞彙表，讓每次對話說同一套語言
- 用「單向門 vs 雙向門 + 影響範圍」評估任何決策（購物、部署、發布影片）：可逆的小事快速行動，不可逆的大事才慢審
- 對自己的內容產線（YouTube、逐字稿、剪輯）執行 retro：每次結束後問「我要怎麼改環境，才能不用再手動處理這件事」
- 仿效每日 cron job 的改善迴圈：每天只要求一個最小改進，用複利對抗熵增
