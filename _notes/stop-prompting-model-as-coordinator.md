# Stop Prompting — Head of Claude Code Uses Opus 5.5 + Graphs + Harness

## [核心摘要]

Anthropic Claude Code 負責人 Boris 與 AMD 高層 Mark 的對談，揭示 AI 時代工程範式的根本轉移：**模型即協調者**（Model as Coordinator）。當模型智慧超越人類，價值不再來自更好的 Prompt，而是來自「把 AI 放在每個流程的中心」。Anthropic 透過逐一根除瓶頸，達成**每工程師程式產出 8 倍提升**；並以「信任漸增 → 平行擴展 → 自動化驗證」的路徑，從 1 個 Agent 走向數千個 Agent 的規模化協作。

## [詳細重點整理]

### 1. 指數曲線與 Claude Code 的誕生 

模型能力遵循**縮放定律**持續上升，甚至加速中。Anthropic 預見模型將從補全單行程式碼，進化到寫整個函式、檔案、功能乃至整個專案，年底前甚至能建構整個事業。Claude Code 前六個月表現不佳，直到 **2025 年 5 月的 Opus 4** 才真正開始發揮作用，自此產品成長曲線轉為指數型。最新迭代是長駐型非同步代理，像同事一樣互動、懂得何時該介入。

- 關鍵概念：**縮放定律**

### 2. 從確定性流程到模型驅動

過去的「Agentic Workflow」實為確定性系統——每一步呼叫 LLM 做運算，但流程由人寫死。現在的範式是反轉：**模型擔任協調者**，你只給目標、起點與工具（含讀取 Context 與互動外部世界），讓它自行編排步驟，不再逐步下指令。Claude Code 團隊也從早期「餵食 Context」轉向 **Skills、Tools 與 MCP**——讓模型自己決定何時載入、如何載入，取代每個 Session 固定載入的 [CLAUDE.md](http://CLAUDE.md)。

- 關鍵概念：**模型即協調者**

### 3. Claude 位於一切中心：Anthropic 的內部實踐 

在 Anthropic，新人的任何問題——辦公室在哪、程式碼庫怎麼存取、差旅費怎麼報——都不查 Wiki、不問同事，而是問 Claude。Claude 負責寫程式、Code Review、安全審查、腦力激盪產品點子、彙總用戶反饋、事件分級，滲透 SDLC 每一環，並擴及產品、設計、行銷、GTM 所有職能。最成功的採用者都是把 Claude 放在**每個流程的中心**，而非邊角。

- 關鍵概念：**AI 流程中心化**

### 4. 8 倍產出的方法論：逐一根除瓶頸 

引用 90 年代 Harvard Business Review 經典文章：把電腦放辦公室角落、保留紙本流程的公司看不到生產力提升；把檔案櫃丟掉、讓電腦居於每個流程中心的公司才解鎖生產力。Anthropic 今年以來**每工程師程式產出提升 8 倍**（業界常態僅每年個位數百分比），方法是**系統性逐一移除瓶頸**：編碼是瓶頸就讓 Claude 寫碼，接著 Code Review 是瓶頸就讓 Claude 審查，再換 GTM 素材產製，一步一步打通。

- 關鍵概念：**瓶頸根除法**

### 5. 抽象層躍遷與「一人軍隊」

工程抽象層不斷上升：硬體 → 打孔卡 → 原始碼 → **Agent → 迴圈與例行程式**，最後兩步竟發生在兩年之間。工程不再是瓶頸後，真正稀缺的是產生好點子並安全上市的速度。最有效的人是**一人軍隊（CEO 原型）**：自己想點子、跟用戶談、看數據、建置、迭代、上市。工程背景有幫助但已非必要；領導者的職責是**創造安全的實驗空間**，並給予團隊業務與產品 Context。

- 關鍵概念：**抽象層躍遷**

### 6. Agent 規模化階梯：1 → 10 → 100 → 1000 

企業的自然演進路徑：每位工程師跑 1 個 Agent → 10 個 → 100 個 → 1000 個。多數公司仍在第 1–2 階，Anthropic 平均在第 3 階（數十到數百個 Agent）：

- **1 個**：單執行緒，緊盯著它工作
- **10 個**：信任建立後，利用同一 Repo 的多個 Checkout，**輪詢各 Agent** 邊跑邊切換——桌面版已原生支援平行 Session
- **100+**：讓 Agent 啟動 **Sub-agent**，Claude Code 支援**最多五層巢狀**；搭配雲端執行，Boris 現在常直接從手機發起編碼
- **1000**：以**動態工作流**做分而治之。Stripe 用它完成 10,000 行 Scala → Java 遷移，原本需數月的工程僅花 4 天；Anthropic 也用此將 Bun 從 Zig 遷移到 Rust [14:54]
- 關鍵概念：**Sub-agent 巢狀編排**

### 7. 測試時運算與 ROI 的正確順序 

傳統縮放定律（網路規模、資料量、算力）之外，模型表現如今也是**測試時運算**的函數——丟多少 Token 決定結果多好。模型內建 **Effort Levels** 可配置投入上限；多 Agent 與動態工作流本質上是測試時運算的另一種形式。談 ROI 時多數公司只顧「I」（成本）：Plan mode、Advisor models、改用 Haiku/Sonnet、寫 Evals。但更重要的是「R」——先給團隊**實驗自由**找到機會，成功且用 Token 多的用例才回頭優化。順序錯了，你永遠不知道**效能上限**在哪。

- 關鍵概念：**測試時運算**

### 8. 謙遜課題：讓 Claude 開車 

Boris 自述反覆學到同一課：他手動用 Profiler 除錯時，新同事直接請 Claude 處理，**20 分鐘內找到他找不到的正解**。與模型的關係應從「微管理」演進為「與資深工程師共事」——給 Context、給目標、設定**護欄**後放手，信任度越低檢查越頻繁。AMD 也有對照案例：資深團隊數週未解的晶片 Bug，被初級工程師用平行 Agent 流程破解，當場折服所有資深工程師。

- 關鍵概念：**信任校準**

### 9. Evals 與 Vibes 的分工 

兩種度量工具各有定位：會重複數千到數百萬次的工作流，必須有 **Evals**，以便新模型上線時換入 Harness 驗證是否真的變好；產品體驗類則靠 **Vibes**（直覺）即可，因為寫 Evals 有成本。至於多方案並行的分歧問題——有模型在，合併程式碼極容易，直接叫 Claude 把其他呼叫點遷移到選定的做法即可。

- 關鍵概念：**Evals 優先原則**

### 10. 信任與驗證的多層防禦 

隨模型深入業務核心，安全是前提而非選項，防線分多層：

- **模型對齊**：含真實性，以及**反諂媚**——好模型會反駁你的爛點子，這反而增加信任
- **反提示注入訓練**：Opus 4.7、4.8 等是業界最難被提示注入的模型，領先 5–10 倍；再疊加執行時分類器，實務攻擊成功率趨近於零
- **自動模式**：工作流跑數天到數月，人工點「Yes」最終會產生**核准疲勞**——人會停止閱讀只按確認。解法是把核准路由給分類器決策，經 Evals、紅隊、滲透測試驗證後更安全，Anthropic 內部全面採用 
- 關鍵概念：**核准疲勞**

### 11. 未來六個月預測 

Agent 平均運行時間更長、每人平均 Agent 數量更多、與意圖對齊更好——更少導正與手把手。跑**數天到數週的 Agent** 將從少數工程師的玩法變成常態。年底前 Claude 將從建構功能進展到建構產品，甚至可能出現**整個新創由 Claude 建成**。

- 關鍵概念：**長駐自主 Agent**

## [結論與行動建議]

**啟發金句**：「與模型的關係，就是從微管理演進為信任一位資深工程師——給目標、給 Context、設好護欄，然後放手讓它工作。」

**具體行動建議（B-B-G 法則）**：

- **B**ottleneck（找瓶頸）：每次只攻一個最痛的瓶頸，交給 Claude
- **B**oldly（放手實驗）：給自己與團隊實驗自由，先找機會再優化成本
- **G**uardrails（設護欄）：用 Evals + 自動分類器取代人工點 Yes，防止核准疲勞

**生活實踐建議**：

- 開發上，把 [CLAUDE.md](http://CLAUDE.md) 的靜態餵食改為 **Skills + MCP 工具**，讓模型自行決定何時載入知識——這正是你正在研究的 MCP 架構方向
- 平行工作時，用同一 Repo 的多個 Checkout 實踐輪詢式多 Agent，先從 2 個 Session 開始建立信任，再逐步擴到 5–10 個
- 對重複執行的自動化流程（如影片筆記、設備比價腳本）寫 Evals，一次性探索則相信直覺
- 注意自己何時開始「無腦按核准」——那是要導入分類器自動化的訊號
