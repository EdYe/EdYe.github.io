## [核心摘要]

這場工作坊示範如何把「憑感覺上線」的 AI agent 轉成可量測、可迭代的生產系統。核心貢獻是建立一條完整閉環：**埋點→取得 trace→親自讀資料→分類失敗→三層評估（程式碼／LLM 評審／人工）→元評估校準裁判→資料集與實驗迭代**，解決非確定性輸出無法用傳統單元測試驗證、也無法在 CI 中執行的痛點 。 

---

## [詳細重點整理]

### 1. 心智模型：eval 與 trace 的本質 

- **eval 是 AI 的測試，trace 是 AI 的日誌**：eval 對應單元測試，trace 對應 log。因為輸出永遠非確定性，所以要發明新名稱。
- trace 的組成單位是**跨度**：樹狀結構，一次 LLM 呼叫、一次工具呼叫、一整輪 agent 回合各是一個 span，記錄輸入、輸出、耗時與 token 數。trace 告訴你「發生了什麼」，eval 告訴你「結果好不好」[00:08]。
- 關鍵概念：**Observability（可觀測性）**

### 2. 憑感覺問題（Vibes Problem）

- 目前最普遍的 AI 上線方式是「跑三次查詢、看起來不錯就上線」，隨後在沒測過的輸入上失敗。
- 單元測試在此失效：輸出非確定性，兩個不同回應可能都正確，無字串可斷言。人工審查無法擴展、抓不到回歸、無法進 CI。
- 沒有 eval 就無法安全地改提示詞（改語氣可能弄壞事實性）、無法切換模型（新模型每幾個月出現，靠感覺需要好幾週手動測試）。這是「憑感覺飛行 vs 依靠儀表飛行」的差別 [00:10]。
- Dcript、Bolt、甚至 Anthropic 的 Claude Code 都走過同一條路：先 vibes 出貨 → 發現無法擴展 → 才建立評估 [00:11]。
- 關鍵概念：**Vibes Problem／憑感覺問題**

### 3. 三種評估的分工 

- **程式碼評估**：確定性函式，毫秒級、零成本、可重現（如：輸出是否為合法 JSON、是否少於 500 token）。類似單元測試，但可能脆弱。
- **LLM 評審**：用第二個 LLM 依**評分標準**打分，能處理語意問題（正確性、忠實度、語氣）。缺點是花錢、本身非確定性，需人工校準。
- **人工評估**：品質黃金標準，但慢、貴、且人類標註者會因疲勞漏掉多達 **50%** 的缺陷。
- 關鍵概念：**LLM as a Judge／Rubric（評分標準）**

### 4. 為什麼 agent 更難評估 

- **複雜度階梯**：agent 每一步工具呼叫與決策都增加出錯機會，必須評判中間步驟（有沒有選對工具、傳對參數、知道何時停止）；多代理系統又多了**交接**問題。
- **連鎖失敗**範例：查詢 Tesla 汽車公司，代理搜到十八世紀發明家的資料並寫出漂亮報告——每一步都「沒錯」，卻整體錯誤，單元測試抓不到。
- 反向案例：Anthropic 的 **Tau-squared Bench** 中，代理找到政策漏洞（經濟艙升級頭等艙後可改期）而完成了「理論上不可能」的任務，反而被判失敗——「有創意的正確」與「錯誤」是兩回事，評分要針對結果而非路徑 [00:16–00:17]。
- 關鍵概念：**Cascading Failure（連鎖失敗）**

### 5. 能力評估 vs 回歸評估 

- **能力評估**：預期大多失敗的低分評估，給 agent 一座可攀爬的山丘；爬上後轉為**回歸評估**（預期每次通過），隨時執行確保不退步。
- 關鍵概念：**Capability Evals vs Regression Evals**

### 6. 評估結果三要素與解釋的價值 

- 每筆評估產生**分數（0/1）＋標籤＋解釋**。解釋是 LLM 評審獨有的，能告訴你具體缺了什麼（如「使用者要預算航班，卻沒有費用估算」）。
- 同樣的解釋在 50 條 trace 重複出現 → 系統性問題，優先修。把解釋分類稱為**編碼**，最終可把大量解釋餵回 coding agent 自動改進應用。
- 完整迴圈：**埋點 → 追蹤 → 評估 → 迭代**。
- 關鍵概念：**Coding（失敗分類編碼）**

### 7. 兩行程式碼完成埋點 

- 只需 `register()` 加上 SDK 的 instrument 呼叫：底層是 **OpenTelemetry**（可觀測性業界標準）＋ **OpenInference**（LLM 專屬屬性層）。因為是開放標準，Claude、OpenAI、LangChain、CrewAI、Mastra 等 SDK 都已內建支援，開啟即亮。
- notebook 中傳 `batch=False` 讓遙測即時送出；Arize skills 可在 Claude Code、Cursor、Codex 中用一條 `npx` 指令安裝，讓 coding agent 代勞全部流程 [00:26–00:28]。
- 關鍵概念：**OpenInference 自動埋點**

### 8. 示範 Agent：財務分析師 

- 用 Claude Agent SDK 打造兩回合 agent：研究回合（網路搜尋）＋撰寫回合（產出報告）。底層模型用 **Haiku**（故意會犯錯、快且便宜），評審則用更強的 **Sonnet 4.6**——「大而慢的模型評判小而快的模型」。
- agent 自行判斷要搜尋幾次才「足夠」，執行路徑設計上就是非確定性的，同輸入可產出不同的報告 [00:32–00:33]。
- 預埋的陷阱：agent 試圖把報告寫成 markdown 檔到磁碟，但 Colab 沒有可寫的檔案系統，寫入無聲失敗——典型的「看似有幫助、實際不正確」的失敗，只有讀 trace 才看得到 [00:33]。
- 關鍵概念：**無聲失敗**

### 9. 錯誤分析：寫 eval 之前先讀 trace 

- 12 個測試查詢刻意追求**多樣性**：明顯查詢、邊緣案例（雙代號比較 Apple vs Microsoft、重複代號看非確定性、Rivian 資料稀少、Coca-Cola 股息 vs 成長股）。
- 「在撰寫評估之前，先讀你的追蹤紀錄」是全場最重要的實踐。Anthropic 團隊每天花大量時間就是看 transcript。定義「成功」需要領域專家（PM、QA、客服）參與——「人員管理技能就是 AI 技能」。
- 13 筆中 3 筆出現把報告寫到不存在的磁碟、1 筆陷入無窮網路搜尋迴圈（Microsoft）、Rivian 報告含大量無法驗證的「自信錯誤」[00:42–00:45]。
- 結構化閱讀法：**開放式編碼**（自然語言逐筆寫下問題，不要預設分類）→ **軸心編碼**（歸類出根本原因：檢索失敗／推理錯誤／幻覺／範圍違規）。不同根本原因指向不同修法。
- 修復優先序 = **嚴重程度 × 頻率**（「教做炸彈」發生率 1% 也要最先修）。
- 多層防禦：**瑞士起司模型**——每層防線都有孔洞，疊足夠多層，孔洞就不會對齊 [00:48]。
- 關鍵概念：**Error Analysis／瑞士起司模型**

### 10. 程式碼評估：第一道防線

- 最簡單有用的 eval：檢查股票代號是否出現在報告中（五行 Python）。實測 **12 過 1 敗**——敗筆是問 Amazon AWS 時報告只談 AWS、通篇沒提 Amazon 母公司代號 [00:54–00:55]。
- 程式碼評估不必只是字串比對：可查資料庫、呼叫真實股價 API 驗證沒有幻覺——只要評分邏輯對相同輸入永遠給出相同答案即可。
- 核心原則：**評分針對結果，而非路徑**——對路徑評分是在懲罰創意 [00:57]。
- 關鍵概念：**Code Eval（確定性評估）**

### 11. 內建評估實測：正確性 vs 忠實度 

- LLM 評審三要素模組化分離：**評審模型 × 提示範本 × 資料**。
- **正確性評估全軍覆沒（13 筆 0 過）**：評審 LLM 依訓練資料判斷真偽，而 agent 做的是即時網路搜尋，談的是評審模型知識截止後的事——「來自未來的內容」。
- 改用**忠實度評估**：把 agent 搜集到的同批研究上下文交給評審，雙方站上公平起跑線。實測 **忠實 6 筆、不忠實 7 筆**——一半時間在幻覺。這是理想的能力型評估：有山丘可爬 [01:04]。
- 關鍵概念：**Faithfulness（忠實度）**

### 12. 自訂 Rubric 的寫法 [01:06–01:15]

- 內建評估不含「可行動性」，必須自訂。好 rubric 五要素：
  1. 定義評審角色（效果其實不大，重要的是讓它知道在看什麼）；
  2. 通過／失敗準則必須具體且可觀察，能回答是或否（「包含具體建議」✓，「有幫助且準確」✗——對 LLM 毫無意義）；
  3. 用 **XML 標籤**標示資料（Anthropic 模型對 XML 特別友好）；
  4. 輸出選項定義在提示詞之外，用工具呼叫回傳標籤，不要叫它輸出特定字串；
  5. 放入好與壞的輸出範例（有過擬合爭議，但 LLM 最擅長複製範例）。
- 標籤保持二元（0/1）；1–5 分量表 LLM 不擅長。要求評審先推理再打分的**思維鏈**可觀提升準確度 [01:13]。
- 線上評估可設**取樣率**（如只評 1% 流量）控制成本 [01:14–01:15]。
- 關鍵概念：**Actionability（可行動性）**

### 13. 三大反模式 

- **把評估提示詞當程式碼**：對用字極度敏感，需版本管理；若 LLM 裁判與人工標註在 40% 案例上不一致，錯的是你的評估。
- **上帝評估器**：一個超大提示詞檢查五件事，失敗時不知是哪件事——該拆成就多個專注的評估器。
- **混淆護欄與北極星指標**：捏造股價是護欄（退步要半夜叫人起床處理）；「總是推薦互補投資」是北極星（週報看看即可）。
- 關鍵概念：**Guardrail vs Northstar Metric**

### 14. 元評估：評估你的評估器

- 心智模型：**LLM 裁判就是一個分類器**，可拿人工標註當真實答案衡量其表現。在 AX UI 裡為每個 span 加 `human actionable` 標註（非技術同事也能做），建立**黃金資料集**。
- 方法論（此段之後的逐字稿僅存綱要，時間戳如下）：區分開發集與測試集 [01:24]、用黃金資料集比對裁判表現 [01:25]、進行元評估與 rubric 迭代 [01:26]、以 precision／recall 檢視假陽性 [01:26]、留意 LLM 裁判的已知偏誤——位置偏誤、長度偏誤、信心偏誤、**自我偏好** [01:27–01:28]，以及評審者間信度問題 [01:28]。
- 關鍵概念：**Meta Evaluation／黃金資料集**

### 15. 閉環：資料集、實驗與 Claude Code 

- 把失敗案例（`eval.actionability.label = not actionable`）建成資料集，用**實驗**做受控比較：固定資料集、只改一個變數（提示詞、few-shot 範例、temperature、top-p 等超參數），比較各實驗分數 [01:38–01:40]。
- 示範用 Claude Code 做資料驅動的提示詞工程：把元評估與 eval 回饋交給 coding agent，自動迭代改進 agent 提示詞，eval 分數隨迭代顯著提升 [01:33–01:39]。
- 定性總結：**eval-driven development 就是 agent 時代的 test-driven development**——先寫評估，再改程式 [01:41]。
- 關鍵概念：**Eval-Driven Development**

### 16. 邁向生產環境 

- 上線時把 eval 移到線上：護欄型評估接 monitor 與警示、回歸資料集持續把關；用取樣率控制 LLM 評審成本 [01:42–01:45]。
- Arize skills 讓 Claude Code、Cursor 等 coding agent 直接代操作 AX 的評估與資料集 API，完成評估驅動的自動改進迴圈 [01:46–01:47]。
- 收尾回顧：兩行程式碼埋點、多層評估、元評估校準、資料集與實驗——把 vibes 變成可出貨的系統 [01:48–01:51]。

## [結論與行動建議]

**啟發金句**：

> 「你無法評估你看不見的東西——在寫下任何一個 eval 之前，先讀你的 trace。」

**具體行動建議：R-E-I-A 法則**（好記四步）：

- **R**ead：先讀 10+ 條 trace，用開放式編碼→軸心編碼找出失敗根因；
- **E**val：能確定性的用程式碼評估，需要語意的用 LLM 評審，各面向一個評估器，永不寫「上帝評估器」；
- **I**terate：失敗案例建成資料集，一次只改一個變數做實驗；
- **A**lign：用人工標註的黃金資料集元評估你的裁判，才值得信任。

**生活實踐建議**（套用到你的工作流）：

- 在自己的 Claude Agent SDK／MCP 專案中，加入兩行 OpenInference 埋點，先取得 trace 再談評估——這是零成本的起手式。
- 把 eval 的失敗解釋直接餵給 Claude Code（或安裝 Arize skills），讓它根據回饋自動改提示詞，形成「eval 驅動開發」的閉環，取代手動調提示詞的打地鼠。
- 評估選擇上的教訓可直接複用：任何做即時網路搜尋／RAG 的 agent，用忠實度而非正確性評估，否則評審會用過時的訓練知識否決你的最新資料。

總之，我們來談談這些基礎概念。這場工作坊有很多理論，正好讓你有時間跟上進度。心智模型是這樣的：eval 是 AI 的測試，trace 是 AI 的日誌（log）。為什麼我們得為這兩樣東西想出兩個全新的名稱？我也不知道。你會為自己的程式碼寫測試：給定這個輸入，我預期得到這個輸出。eval 做的是同樣的事，只是對象是 AI 的輸出，而這些輸出永遠不會兩次完全相同。就像日誌記錄你的伺服器在執行階段做了什麼，trace 記錄的是你的 AI 做了什麼。所以，每一次 agent 呼叫、每一次工具呼叫、每一次 LLM 調用，連同每一步的輸入與輸出，都會被記錄下來。

[00:08:15](https://youtu.be/qZj7sqmidqA?t=495)

trace 的組成單位稱為跨度（span）。在這張小截圖中，你可以看到 Arize AX 裡的一條 trace，它由許多 span 組成，具有樹狀結構，每個 span 代表執行過程中的一個步驟。一次 LLM 呼叫是一個 span，一次工具呼叫是一個 span，而一整輪完整的 agent 回合也是一個 span，裡面還包含其他 span。每個 span 都會記錄它的輸入、輸出、耗時、token 數量，以及一大堆中繼資料，也就是你要理解那一步發生了什麼所需的一切。trace 告訴你發生了什麼，eval 告訴你結果好不好。這就是我們今天的心智模型，這並不是什麼高深的科學。

[00:08:54](https://youtu.be/qZj7sqmidqA?t=534)

不過，讓我來談談我們為什麼需要 eval，這就是所謂的「憑感覺」問題（vibes problem）。AI 功能通常是這樣上線的：做出一個 AI 功能，跑幾個查詢，然後問自己「這看起來對嗎？嗯，看起來不錯」，接著就上線了。這是目前迄今最普遍的 AI 應用程式上線方式。而問題在於，它隨後會在你沒有測試過的輸入上失敗。

[00:09:18](https://youtu.be/qZj7sqmidqA?t=558)
問題是，它大概在你的測試查詢上看起來都很好，但你只跑了三次。三次不能算是測試套件。修正不穩定軟體的慣用方法是單元測試（unit tests），但在這裡行不通，因為輸出是非確定性的（non-deterministic）：同樣的提示詞每次執行都會產生不同的文字，所以兩個不同的回應可能都是正確的，也就沒有一個預期字串可以拿來斷言（assert）。因此團隊只好退回人工審查：看它跑一遍，覺得沒問題就上線。這種做法無法擴展，抓不到退步（regression），而最重要的是，它沒辦法在 CI 中執行。

[00:09:54](https://youtu.be/qZj7sqmidqA?t=594)
以下是沒有評估（evals）就做不到的幾件事。假如你為了修正語氣問題而更改系統提示詞，語氣確實會變好，但現在你的機器人卻開始捏造產品功能。沒有評估的話，要等到使用者回報才會發現。有了忠實度評估（faithfulness eval），你在上線前就會看到這個數字飆升。而且每一個提示詞都可能影響使用者送來的每一種輸入，所以你可能只是為了某件事改了提示詞，卻在應用程式中某個完全不相干的地方造成意料之外的影響，因為提示詞就是你送給 AI 的一大段文字。

[00:10:28](https://youtu.be/qZj7sqmidqA?t=628)
你不可能手動測試每一種組合，所以沒有評估的話，你就是在打地鼠：修好一個問題，卻在別的地方弄壞另一個。評估則給你一個可以追蹤、比較並據以行動的數字。沒有評估，你也無法切換模型。這點越來越重要，因為這個領域變化太快，每隔幾個月就有新模型問世。沒有評估，切換模型就意味著好幾週的手動測試：它比較好嗎？比較差嗎？有東西壞掉了嗎？你不知道。有了評估，你執行整套測試、比較分數，幾小時內就能知道答案。這就是憑感覺飛行與依靠儀表飛行的差別。

[00:11:08](https://youtu.be/qZj7sqmidqA?t=668)
而且這並非紙上談兵。Dcript、Bolt，甚至 Anthropic 自己的 Claude Code，這些真實的團隊都走過同一條路：先憑感覺（vibes）出貨，接著發現感覺無法擴展，然後才開始建立評估。這也是我們今天工作坊要遵循的同一條路。如同我稍早提到的，評估大致有兩種類型。程式碼評估（code evals）是確定性的函式，執行只需幾毫秒、不花任何成本，並且立刻給出明確的答案，例如輸出是否能被解析為 JSON？

[00:11:39](https://youtu.be/qZj7sqmidqA?t=699)
輸出是否少於 500 個 token？它有沒有提到我問的那件事？程式碼評估的最大優勢是快速、便宜，而且完全可重現：給它相同的輸入，每次都給出相同的答案。這讓它們非常類似老式的單元測試。缺點是，和老式單元測試一樣，它們可能很脆弱（brittle）。我們有一些策略可以避免這個問題，我稍後會介紹，因為兩個完全正確的答案，措辭可能截然不同，你必須調整對單元測試的期待，才能處理這種情況。

[00:12:14](https://youtu.be/qZj7sqmidqA?t=734)
第二種評估是以 LLM 當裁判（LLM as a judge）的評估。這類評估使用第二個 LLM，依據評分標準（rubric）來為你的輸出打分。「rubric」又是我們自己發明的一個詞，意思其實就是規則：你放在提示詞裡、說明什麼算好的那組規則。LLM 評估靈活得多，可以處理程式碼評估回答不了的問題，例如：這個回應在事實上正確嗎？它有沒有忠於來源資料？以客服情境來說，語氣對不對？LLM 裁判的長處在於它理解語意，而不只是看輸出裡的字串。

[00:12:51](https://youtu.be/qZj7sqmidqA?t=771)
但 LLM 裁判也有取捨。缺點是執行要花錢，而且它們本身也是非確定性的，所以可能出錯，這代表你需要拿人類的判斷來校準它們，我們今天稍後會做這件事。還有第三種評估，就是人工評估（human evaluation）。領域專家可以閱讀你的輸出並評分，這是品質的黃金標準，但它又慢又貴，而且人會疲勞，所以我們不能隨時都用。一個不太有趣的冷知識：人類標註者會因為疲勞而漏掉多達 50% 的缺陷，所以人也不完美。因此當你建立了 LLM 裁判，覺得「它並不是每次都能抓到我的錯誤」時，請記住，如果由人來評判，人同樣不會每次都抓到你的錯誤。

[00:13:37](https://youtu.be/qZj7sqmidqA?t=817)
不過這些方法是互補的。大多數真實的應用都會混合使用程式碼評估、LLM 裁判與人工評估。那麼什麼時候用哪一種？答案是確定性的時候用程式碼評估，例如格式驗證、長度限制、禁用詞句、必填欄位。需要語意理解時用 LLM 裁判，例如正確性評估（correctness eval）檢查回答是否準確，忠實度評估則問：它有沒有緊扣來源文件而沒有產生幻覺（hallucination）？至於你從未見過的失敗模式，以及用來驗證你的 LLM 裁判是否真的判得正確，則應該讓人類參與其中（human in the loop）。

[00:14:19](https://youtu.be/qZj7sqmidqA?t=859)
LLM 裁判可能出錯，拿人類判斷來檢驗它們，你才知道能不能信任它們。以上這些對任何使用 LLM 的應用都成立，但代理（agent）在某些方面讓事情變得更困難，值得特別點出來。你可以把它想成一座複雜度的階梯。單一一次 LLM 呼叫相對簡單：給一個輸入，得到一個輸出。但代理會進行一連串的工具呼叫與決策，這意味著在鏈條的每一個步驟，它出錯的機會都在升高，也就更有可能偏離軌道。所以你也必須評判中間步驟。

[00:15:03](https://youtu.be/qZj7sqmidqA?t=903)
你得檢查代理有沒有使用正確的工具、有沒有傳入正確的參數、知不知道何時該停下來。陷入迴圈是代理真實存在的失敗情況。如果你打造的是多代理系統（multi-agent systems），又會再增加一層複雜度，因為多了交接（handoff）：一個代理決定把工作交給另一個。分流代理（triage agent）有沒有正確地路由？專家代理（specialist agent）有沒有妥善處理這次交接？每多一層，就多一些出錯的方式。再加上非確定性，錯誤可能層層連鎖，所以你需要更多的評估。

[00:15:38](https://youtu.be/qZj7sqmidqA?t=938)
以下是連鎖失敗（cascading failure）的一個例子。假設你查詢關於 Tesla（指汽車公司）的資料，你的代理上網搜尋，找到一大堆關於十八世紀發明家的資訊，把這些傳回給代理，代理便寫出一份漂亮、格式完整、關於十八世紀發明家的報告，再交給你的老闆。這中間它沒有任何一步做錯：你叫它搜尋 Tesla，它就搜尋 Tesla，得到了 Tesla 的資訊，並寫了一份關於 Tesla 的報告。那它到底是哪裡出了錯？這比明顯的失敗更糟，因為你必須實際閱讀輸入與輸出才看得出來，沒有任何單元測試能抓到這種問題。

[00:16:19](https://youtu.be/qZj7sqmidqA?t=979)
但代理也可能反過來：以你的測試沒預期到的方式把事情做對，結果卻被判為錯誤。Anthropic 在執行一個名為 Tau-squared Bench 的基準測試時就遇到這種情況，這個測試模擬多輪的客戶服務任務。他們要求代理訂機票，並要求它做一件他們認為不可能的事：改期一張經濟艙的機票。但結果是，他們給代理的政策允許代理先把機票升級成頭等艙，而頭等艙機票可以改期，經濟艙機票卻不行。於是代理找到了改期經濟艙機票的辦法，卻因此未通過測試，因為照理說它應該做不到這件事，而它卻做到了。

[00:17:05](https://youtu.be/qZj7sqmidqA?t=1025)
而它真的做到了。這個例子說明，代理（agent）很有彈性，會找到你沒想過的做法，而你的測試必須把這點考慮進去。「有創意的正確」與「錯誤」之間是有差別的，稍後談到如何評分你的代理，或者說如何評分你的評估（evals）時，我們會再回頭談這一點。

[00:17:25](https://youtu.be/qZj7sqmidqA?t=1045)
還有第二種把評估分成兩類的方式：能力評估（capability evals）與回歸評估（regression evals）。能力評估問的是：我的代理到底能不能做這件事？能力評估預期大多會失敗，你的代理預期只會拿到很低的分數，因為它們給你一座可以攀登的山丘。

[00:17:47](https://youtu.be/qZj7sqmidqA?t=1067)
它給你的代理一個可以努力進步的目標。一旦你爬上了這座山丘，那個能力評估就會變成回歸評估。回歸評估是你預期代理每一次都能完全通過、或幾乎完全通過的評估。所以隨著代理逐漸成熟，你會一個接一個地給它能力評估，慢慢把它們變成一整套回歸評估，隨時執行，確保先前的行為沒有退步。

[00:18:17](https://youtu.be/qZj7sqmidqA?t=1097)
這就是一筆評估結果的樣子。每個評估都會產生一個分數和一個標籤。在這個例子裡是數值分數，通常就是 0 或 1。二元分數對 LLM 來說非常容易處理。它還會附帶一個人類可讀的標籤，例如正確或不正確、有效或無效。LLM 評審（LLM judge）還多了第三樣東西，就是解釋。程式碼評估（code eval）因為只是程式碼，所以不會產生解釋；但 LLM 擔任評審時，不只會說某件事不正確，還會說明它為什麼判定某件事正確或不正確。這一點極其有價值，因為如果你身處有程式碼代理（coding agent）的世界，你可以把大量評估產生的一大堆解釋，交回給你的程式碼代理，並對它說：這是你在上一次測試中搞砸的所有原因，

[00:19:03](https://youtu.be/qZj7sqmidqA?t=1143)
你可以怎麼做才能變得更好？然後你的程式碼代理就會說「好，謝謝你的回饋」，去改進你的應用程式，下一次就會做得更好。這是我今天的工作坊要示範給你們看的，也就是如何把一個失敗的評估變成提示詞（prompt）的改進。這是一則真實的評審解釋。這個例子是一個旅遊規劃代理，你在執行正確性評估。評審不會只說「不正確」，它會明確告訴你缺了什麼。你要求的是預算航班，但它沒有提供預算明細。評審說，這個代理給了目的地資訊和推薦，

[00:19:41](https://youtu.be/qZj7sqmidqA?t=1181)

[00:56:53](https://youtu.be/qZj7sqmidqA?t=3413)
程式碼評估器不只是玩具範例。你常常會想確認輸出是 JSON，或是有一定的長度，或是想避免出現禁用的措辭，例如「身為 AI 語言模型」。這些都是對正式環境至關重要的檢查。程式碼評估器不必只是簡單的字串操作，它的意思是評分邏輯是確定性的，但可以做很複雜的事。它可以幫你查詢資料庫，也可以呼叫 API 取得真實的股價，確保 agent 沒有幻覺（hallucinate）出一個股價。只要評分邏輯對於相同輸入永遠給出相同答案，就可以是一個程式碼評估器。

[00:57:29](https://youtu.be/qZj7sqmidqA?t=3449)
一個重要原則是：評分要針對 agent 產出的結果，而不是它走過的路徑。我之前提過這點。很多人有個直覺，就是檢查 agent 是否依照特定的步驟順序執行，例如是不是先呼叫這個工具、再呼叫那個工具。但實務工作者發現，這在實務上太僵化了。agent 經常會找到評估設計者沒預料到的有效做法。所以如果你對路徑評分，就是在懲罰創意。你應該對 agent 產出的內容評分：輸出是否包含正確的資訊？最終狀態是否符合你想要的？我們的股票代號檢查並不在乎 agent 是怎麼找到資料的，它只檢查輸出裡有沒有那個代號。這對大多數程式碼評估器來說，就是正確的抽象層級。

[00:58:15](https://youtu.be/qZj7sqmidqA?t=3495)
接下來我們來談內建評估（built-in evals）和 LLM 評估。這裡開始變得更有趣了。程式碼可以檢查股票代號有沒有出現，卻無法檢查分析好不好：財務數據是否正確？報告是否完整？建議是否推論得當？這些都是語意上的問題，而語意問題需要一個評審（judge）。每個 LLM 評審（LLM as a judge）都有三個部分：評審模型（judge model），也就是替你評分的那個 LLM；提示範本（prompt template），我提過它也叫評分標準（rubric），也就是評審所套用的準則，定義什麼是好；以及資料（data），也就是被評估的範例。Arize AX 把這三樣東西分開，所以你可以自由搭配組合。你可以用相同的準則，搭配不同的評審模型來嘗試，

[00:59:01](https://youtu.be/qZj7sqmidqA?t=3541)

……可以搭配不同的評審模型，也可以用同一個評審模型搭配不同的評估準則。它在設計上就是模組化的。好消息是，Arize AX 內建了一批現成的評估（eval），所以你不必自己從頭寫。有幾類評估幾乎適用於大多數 AI 應用，我們已經把這些提示詞寫好了，你不需要自己動手。舉例來說，正確性（correctness）會檢查回應在事實上是否準確；忠實度（faithfulness）會檢查回應是否緊扣來源資料；另外還有針對工具選擇的評估：代理（agent）有沒有挑對工具？以及工具呼叫的評估：它傳給工具的參數對不對？此外還有文件相關性、拒答偵測等等，在代理式應用裡你會想檢查的許多項目，都是開箱即用。

[00:59:48](https://youtu.be/qZj7sqmidqA?t=3588)

我們要跑的第一個評估是正確性評估，先劇透一下：它不會成功。設定起來非常簡單，我們給它一個大型語言模型（LLM）。這裡我選的是 Anthropic 的 Sonnet 4.6，因為它比實際幹活的 Haiku 更強。你通常會想挑一個更大、更慢的模型來當評審。然後我把這個 LLM 交給正確性評估，並在這裡執行。

[01:00:35](https://youtu.be/qZj7sqmidqA?t=3635)

就像我說過的，我們用 evaluate data frame 來執行評估，同時也開啟了抑制追蹤（suppressed tracing），這樣評估本身就不會再往 AX 送出一堆多餘的追蹤。它會輸出一堆評估結果列，這些可讀性不太高，這也是為什麼你需要 AX 來查看它們。評審會讀取每個 span 的輸入與輸出，並依照評分標準打分。我們可以看到，每一個分數都是零。

如果我往右捲動，可以看到狀態是 completed，名稱是 correctness，分數是零。會這樣是因為，正確性評估是依據 LLM 自己對「什麼是對的、什麼是真的」的定義來判斷，也就是說它仰賴的是 LLM 的訓練資料。而我們這個代理做的是大量即時的網路搜尋，去取得目前的股價和最新的財經資訊，這表示代理談的是 2026 年發生的事，但負責評審的 LLM 所掌握的資訊只到一月為止。所以，如果你在 AX 裡讀我們這個正確性評估的解釋說明……

[01:01:57](https://youtu.be/qZj7sqmidqA?t=3717)

……你可以捲動到評估（evaluations）頁面，點開 correctness，會看到它被判定為不正確。我就幫你省下閱讀那一欄密密麻麻文字的時間：它基本上是在抱怨，裡面有一堆來自未來的內容，它不可能知道。所以我們這裡的正確性評估完全失敗了，這不是你想要的結果。因此我們改用忠實度評估。忠實度對我們這個使用情境是更好的評估，因為評審實際上拿得到上下文。在忠實度評估中，你會把代理所依據的資訊提供給擔任評審的 LLM，然後問：根據我的代理所蒐集到的同樣這批資訊，它報告寫得好不好？

[01:02:40](https://youtu.be/qZj7sqmidqA?t=3760)

這樣一來，雙方就站在公平的起跑線上，兩者擁有同樣多的資訊，而你那個又慢又複雜的評審代理，就可以判斷你那個又快又輕的工作代理做得好不好。接著來看忠實度的儲存格。就像其他所有東西一樣，這些評估既可以線上進行，也可以離線進行。AX 有內建的忠實度評估器（這個畫面裡沒有顯示），你可以把它叫出來，然後把輸入、輸出和上下文交給它。同樣地，你也可以用程式碼來做。

[01:03:25](https://youtu.be/qZj7sqmidqA?t=3805)

而如果你是使用技能（skills），多半就會是這樣：你的技能會說「我不用介面，我直接用程式碼」，所以我在這裡示範程式碼的做法。我們首先要做的是從追蹤中擷取研究上下文。你應該還記得，我們採用的是兩步驟流程：我取出第一步（做研究的那一步）的輸出，把它附加到我所有的 span 上，作為評審判斷時使用的上下文。接著我執行忠實度評估器。這裡你可以看到帶有上下文的 span，它們就是我剛剛從 AX 拉出來的那些 span，我在欄位層級把所有上下文都附加上去，然後呼叫……

[01:04:11](https://youtu.be/qZj7sqmidqA?t=3851)

……evaluate data frame，傳入這些 span，並給它我的忠實度評估器，這個評估器的建立方式跟剛才建立正確性評估器一樣。這次得到的資料有趣多了：不忠實 7 筆，忠實 6 筆。也就是說，依照 Sonnet 的判斷，我這份非常簡單的報告大約有一半的時間在產生幻覺，它編出了來源資料裡沒有的內容。而這是一個有用的評估，一個我們有一半時間會失敗的評估。這是一個能力型評估（capability eval），我們可以一步步爬坡：修改提示詞，讓它更擅長寫出有根據的報告。這正是你想要的那種評估。

[01:04:58](https://youtu.be/qZj7sqmidqA?t=3898)

所以，這是兩個內建評估，帶來兩種截然不同的訊號。這裡有個很重要的教訓：正確性評估給我們的是 13 筆中 0 筆通過，而忠實度評估告訴我們，報告大約有一半的時間沒有紮根於來源資料。差別不在於哪一個評估比較好，而在於使用情境。有很多使用情境，我先前展示的那種正確性評估其實運作得很好，只是不適用於我們這個做即時研究的特定情境。

[01:05:32](https://youtu.be/qZj7sqmidqA?t=3932)

所以，清楚知道你真正要問的問題是什麼，這一點很重要。內建評估是你的起點，不需要任何提示詞工程就能立刻得到訊號。但即使是像忠實度這樣好的內建評估，仍然有很多東西它檢查不了。我們的財務分析師代理應該要產出可行動的建議，而不是只彙整資料。也就是說，不只是給你一份財務報告，還要告訴你該拿這份報告怎麼辦：該買、該賣，還是該持有？沒有任何內建範本會檢查這件事。

[01:06:07](https://youtu.be/qZj7sqmidqA?t=3967)

AX 並不涵蓋每一種使用情境，所以你必須自己建立一個專門檢查可行動性（actionability）的評估。你必須針對自己的領域建立自訂評估。如果你在寫的是真正的評估，你絕對會需要寫一個自訂評估，裡面有我們沒想到的「好」的定義。這就帶我們進入下一步：撰寫自訂評估的評分標準（rubric）。

[01:06:28](https://youtu.be/qZj7sqmidqA?t=3988)

這是你讓評估真正貼合自己應用的地方。要寫出好的評估很不容易，所以我要花一點時間談談什麼樣的評分標準才算好。我們建議自訂評分標準包含四個部分：第一，定義評審的角色；第二，明確寫出通過與失敗的準則；第三，用 XML 標籤來標示資料；第四，把輸出選項定義在提示詞本身之外。除此之外，我還要再加一項，這一項在實務工作者之間其實頗有爭議，就是我傾向放入好與壞的輸出範例。有些實務工作者認為，放入範例會讓你的評估過擬合（overfit）。不過讓我們把這些逐一走過一遍。

[01:07:14](https://youtu.be/qZj7sqmidqA?t=4034)

這些我們都會逐一走過。第一部分是定義角色。你會注意到這句如今已經有點老套的話：「你是一位專業的財務分析評估員。」但這不是重點。測試顯示，這句話對評估是否有效只有非常小的影響。重要的是讓它知道自己正在看什麼：你正在看的是一份財務報告，而我期待的是財務分析。這些才是你要提供給 LLM（大型語言模型）的重要脈絡。你也要告訴它，你想要的是「可執行」的內容。這就帶到第二部分，也是大多數人投入不足的地方。不要只說「好的回應」，因為那只是

[01:08:00](https://youtu.be/qZj7sqmidqA?t=4080)

一種期望，不是一項標準。「好的回應是有幫助且準確的」聽起來像是多加了細節，但你其實仍然一樣含糊，因為「有幫助」和「準確」這些詞對 LLM 來說沒有任何意義。你應該列出到底什麼樣的報告才算可執行，什麼樣的又不算。每一項標準都應該具體且可觀察：如果你是一個人在看這份報告，你能夠判斷它有沒有出現，並且回答「是」或「否」。例如「包含具體建議」。

[01:08:32](https://youtu.be/qZj7sqmidqA?t=4112)

這絕對是可以回答是或否的。又如「包含前瞻性分析，而不只是歷史資料」，這是一個清楚的區別，同樣可以回答是或否。這裡重要的是，每一項標準都對應到我們在分析中看到的現象。當我們閱讀這些報告時，或至少是當我閱讀我們的追蹤紀錄（traces）時，我們實際觀察到這些報告正是以這些方式出錯。這並非巧合。

[01:09:00](https://youtu.be/qZj7sqmidqA?t=4140)

你的錯誤分析（error analysis）會告訴你該寫哪些標準。你不是憑空想出它們，因為憑空是想不到的。你是從閱讀追蹤紀錄中得到這些資料，然後說：「喔，它沒有做到這件事。」我的軸心編碼（axial coding）顯示它會犯這個特定的錯誤。所以，具體的標準會產生一致的判斷，而含糊的標準只會產生擲硬幣般的結果。

[01:09:22](https://youtu.be/qZj7sqmidqA?t=4162)

在評分準則中，第三件該做的事，是用 XML 標籤標示資料，尤其是當你使用 Anthropic 的模型時。Anthropic 很喜歡 XML，也覺得它非常容易理解。你的評分準則有變數，也就是輸入和輸出，而你要確保它能分辨哪些是你的指示、哪些是輸入與輸出，XML 標籤是做到這點的絕佳方式。所以，在輸入外面加上 user query 標籤，在輸出外面加上 financial report 標籤。清楚的界線能降低評審混淆問題與答案的機率。

[01:09:52](https://youtu.be/qZj7sqmidqA?t=4192)

如果你有放入範例，用 XML 標籤標示範例尤其重要，否則它會說：「喔，這正是我該寫的內容」，然後直接把範例原封不動吐回給你。這就帶到範例了。這是很多人會跳過的部分，但我認為它是最能提升品質的部分。LLM 在遵循指示方面還可以，而且越來越好，但它們真正擅長的，是複製你已經給它們的範例，並把與當前情境相關的部分替換掉。所以，如果你給它一個完全符合你想要的那種報告的範例，它就會精確地遵循那個格式。這在你的領域中可能是好主意，也可能不是。如果你的範例

[01:10:38](https://youtu.be/qZj7sqmidqA?t=4238)

太僵化，LLM 就會永遠給出同一份報告，你等於縮小了它的創意空間。但另一方面，如果它太不穩定、報告變得離譜，那麼給它一個範例，就能讓它扎根於你確切期待的內容。以下是範本中「可執行」範例的樣子：它什麼都有，包括營收成長百分比、本益比（PE ratio），它指出一項具體的風險並附上數字佐證，還給出一個具體的建議。這就是可執行的樣子。再來是一個不可執行的結果。它沒有錯，它說的每件事都是正確的，

[01:11:15](https://youtu.be/qZj7sqmidqA?t=4275)

但它沒有說出任何有用的東西。它沒有任何具體資料，沒有任何具體風險，只是說投資人應該考慮各種因素。那不是建議。如此一來，評審就有了一個具體的參照，知道你給它的那些標籤實際上是什麼意思。這可以大幅提升一致性，特別是在邊緣案例上，也就是那些報告原本會落在中間地帶的情況。

[01:11:40](https://youtu.be/qZj7sqmidqA?t=4300)

接下來這點很重要。在撰寫這份評分準則時，很容易會想加上一句「現在請輸出『正確』或『不正確』這個詞」，因為那正是你想要的結果。但你不再需要這麼做了。實際運作的方式是，我們給 LLM 一個工具，告訴它做完時呼叫這個工具，它就會帶著「正確」或「不正確」來呼叫該工具。所以你不需要告訴它要輸出什麼；事實上，要求它輸出特定字串，反而更可能讓它混淆，導致你的評估失敗。因此，只要在 UI 中設定好選項，或者以程式方式建立時設定好選項，然後讓 LLM 自己去處理就好。在你

[01:12:26](https://youtu.be/qZj7sqmidqA?t=4346)

設計這些選項時，最好保持簡單。二元最理想，也就是兩個清楚的標籤。像 1 到 5 分這類數值量表很誘人，但 LLM 並不擅長。3 分和 4 分的差別是什麼？你得寫一大堆規則，LLM 才會知道，它不會自動知道。相對地，你給它通過與否，它就能相當準確地判斷什麼是通過、什麼是不通過。如果你真的需要更多類別，可以設一個部分結果，例如 0.5 分代表它只做了一半、敷衍了事。但預設請選擇 0 或 1。

[01:13:08](https://youtu.be/qZj7sqmidqA?t=4388)

還有一個實用的小訣竅，是讓評審使用思維鏈（chain of thought）。要求評審在打分數之前先推理，先解釋它的思考。這能可觀地提升準確度。當評審必須說明為什麼某件事可執行或不可執行、為什麼正確或不正確時，它犯的錯會比不先思考、直接選標籤時更少。這段解釋對你也很有幫助，但同時也幫助評審思考得更好。這就是 LLM 的奇妙之處之一。

[01:13:38](https://youtu.be/qZj7sqmidqA?t=4418)

[01:18:27](https://youtu.be/qZj7sqmidqA?t=4707)

第二個反模式是「上帝評估器」（god evaluator）。人們很容易想建立一個大而全的超級評估器，在單一提示詞中同時檢查準確度、語氣、完整性、政策遵循和格式。不要這樣做，因為它校準起來是場惡夢。當你的上帝評估器說「失敗」時，這五個面向到底是哪一個失敗？你不知道。於是你突然想：「那我讓它輸出標籤好了。」結果它吐出 15 種不同的標籤，一下子就變得太複雜，你無法據此判斷，也無法據此評分。把它拆開、每個面向各用一個評估器，要簡單容易得多。我今天已經這樣做了：我有 ticker 檢查、有忠實度、有可執行性。

[01:19:11](https://youtu.be/qZj7sqmidqA?t=4751)

三個各自專注的評估，每一個都告訴你特定的事情。組合起來給你的全貌，比任何單一評估所能提供的都更豐富。如果你發現自己寫的評分標準列了六件回應應該做到的事，就停下來，那是六個評估器，不是一個。第三個反模式是不清楚你的護欄（guardrail）和北極星指標（northstar metrics）。有些評估是護欄，它們是阻止上線的條件。

[01:19:36](https://youtu.be/qZj7sqmidqA?t=4776)

如果代理（agent）捏造了股價，那就是嚴重失敗，不要在這種狀況下上線。其他的則是北極星指標，它們是理想目標。例如「總是推薦互補性投資」在這個案例裡是加分項，不是致命傷。所以要知道你的評估各屬於哪一種，它會改變你處理結果的方式，之後也會改變你如何設定生產環境的監控。護欄的退步應該要在半夜呼叫某個人起床處理；北極星指標的下滑，則是你在每週報告裡看一下就好。

[01:20:06](https://youtu.be/qZj7sqmidqA?t=4806)

接下來進入下一個段落：你能信任你的裁判嗎？這個問題我們一直在繞著談，我也提過幾次。現在是評估你的評估器的時候了。我們建了一個 LLM 裁判，它告訴我們有些報告不可執行，但我們能信任它嗎？我們怎麼知道裁判是對的？這裡的關鍵心智模型是：你的裁判就是一個分類器，所以你可以把它當成分類器來看待。它接收一個輸入，在這個案例中是一份財務報告，然後做出預測：可執行或不可執行。

[01:20:37](https://youtu.be/qZj7sqmidqA?t=4837)

這個預測可能對也可能錯。所以就像任何分類器一樣，你可以把它的預測與真實答案（ground truth）比較來衡量它的表現，在這裡真實答案就是人的判斷。你可以檢查裁判的作業。不過，做人工判斷是一件非常費工的事。你得真的讀過每一個輸出，認真思考並貼上標籤。AX 盡力提供協助，讓你直接在 UI 裡定義標註（annotation）並附加到 span 上。讓我示範給你看那是什麼樣子。

[01:21:11](https://youtu.be/qZj7sqmidqA?t=4871)

[01:21:42](https://youtu.be/qZj7sqmidqA?t=4902)

[01:22:54](https://youtu.be/qZj7sqmidqA?t=4974)

現在我們要把我標為可執行與不可執行的結果，與裁判標為可執行或不可執行的結果做比較。不過在那之前，再多談一些黃金資料集：讓你的任務保持明確無歧義。

[01:23:25](https://youtu.be/qZj7sqmidqA?t=5005)

如果你的 agent 一直拿到 0 分，那幾乎都是任務本身壞掉了，多半是你把評分標準（rubric）寫錯了。如果你設計的任務只有人類才做得到，甚至根本沒有人做得到，那你就只會得到零分。所以，每個任務都要建立一份參考解答（reference solution），也就是一個已知可行、能通過你所有評分器（grader）的輸出。這能證明該任務是可解的。你也應該雙向測試：要有「某個行為應該出現」的案例，也要有「某個行為不該出現」的案例。舉例來說，如果你只測「它有沒有搜尋網路」，最後就會得到一個無論需不需要都一律搜尋網路的 agent。所以你也應該有一個測試來檢查：它有沒有在答案顯而易見、不需要搜尋的情況下，沒有去搜尋網路。

而且如果你是認真要把這件事做起來，就應該把剛剛建立的標註資料拆成開發集（development set）和測試集（test set）。例如用大約 75% 的標註來反覆調整你的評測，包括修改標準、調整範例，直到評審（judge）跟你的判斷一致；然後保留其餘 25%，用來執行評審，看它是否真的拿到你預期的分數。

[01:24:40](https://youtu.be/qZj7sqmidqA?t=5080)

[01:25:01](https://youtu.be/qZj7sqmidqA?t=5101)

我已經用一些範例跑過這個評審，它產出了一份雙方一致與不一致的清單。先劇透一下：我是隨機亂點「可行動」與「不可行動」，這樣才會得到大量的不一致，因為實際上 Sonnet 在這類事情上相當厲害。結果是一致率 46%，13 次裡有 6 次一致。

在真實情境中，這正是你要深入追查的地方。你會問：是我的評分標準錯了，還是我的人工標註錯了？當評審和你意見不一致時，你應該閱讀它的解釋，判斷是評審對還是你對。這是後設評估（meta evaluation）最有價值的產出，它通常會揭露你所訂規則中的模糊之處。要修正評分標準，你應該閱讀不一致案例的解釋，找出模糊之處，並收緊標準。所以，與其只寫「包含前瞻性分析」，我會改寫成「包含前瞻性分析，並附上具體的建議或指引」。

[01:26:05](https://youtu.be/qZj7sqmidqA?t=5165)

這樣更精確，因為它排除了報告談到未來、卻從未告訴評審該怎麼做的情況。接著我會在同一批範例上重跑評審，看看不一致是否消失。這就是評分標準的迭代（rubric iteration）。你的評測提示詞（eval prompt）本身就是一個應用程式，也是另一個 LLM 應用，所以它也需要像你的 agent 一樣接受測試和迭代。這就是我之前說「要把評測當成程式碼來對待」的意思。

[01:26:32](https://youtu.be/qZj7sqmidqA?t=5192)

接下來我要非常簡短地談一個機器學習的概念：精確率（precision）與召回率（recall）。精確率問的是：當評審說「不可行動」時，它有多常是真的不可行動？召回率問的是：在所有確實不可行動的報告中，評審抓到了多少？像 12 個範例這種極小的樣本，這些數字會大幅跳動。但即使只有我手上這 12 個，你也能看出評審是大致在合理範圍內，還是完全偏離。在大多數情境下，你會想優先考慮召回率。這兩個指標是互相拉扯的。如果你優先考慮召回率，就會得到一些偽陽性（false positive），也就是評審說有問題、但其實沒有問題。這比不小心放過真正有問題的東西要好得多。

[01:27:18](https://youtu.be/qZj7sqmidqA?t=5238)

不過在某些調校情境下，你會說：其實我要的是精確率，我希望它說對的時候絕對是對的，漏掉一些東西我不在乎。有些領域確實需要這樣的輸出，但大多數時候你會想優先考慮召回率。

[01:27:43](https://youtu.be/qZj7sqmidqA?t=5263)

使用 LLM 當評審有幾個已知的陷阱。第一個是位置偏差（position bias）。如果你給它兩個選項要它評判，評審往往會偏好排在前面的那個。這取決於模型，有時模型偏好排在最後的，但無論如何它總會對位置有某種偏好。還有長度偏差（length bias）：LLM 喜歡比較長的回應，傾向給它們較高的分數、認為它們比較好，即使多出來的長度只是廢話。最後一個我很喜歡，就是自信偏差（confidence bias）：評審會被聽起來很有自信的回應騙過，就像人類一樣。如果你的 LLM 說了錯誤的內容，但語氣非常自信，

[01:28:30](https://youtu.be/qZj7sqmidqA?t=5310)

你的 LLM 評審就更有可能相信它。另外還有自我偏好偏差（self-preference bias）：如果你用同一個模型來生成和評審，它們往往會喜歡自己的輸出。所以如果可能的話，同時使用，比方說 OpenAI 和 Anthropic，一個用來跑你的 agent，另一個用來當評審，這樣它們就比較不會彼此一致。

[01:28:53](https://youtu.be/qZj7sqmidqA?t=5333)

自我偏好偏差正是我用 Sonnet 來評審 Haiku 所生成輸出的原因。不過如果完全改用另一家實驗室的模型，效果會更好。還要記住，這裡的基準是人類的表現。人類在判斷東西是否可行動時，也不會是完美的，而且常常會判錯。你要做的，是設計出一個與人類判斷相當接近的評測。人類的判斷也會因人而異。人類評分者間信度（inter-rater reliability），也就是兩個人判斷同一件事的一致性，往往低到 0.2 或 0.3。也就是說，兩位專家面對相同的輸出和相同的規則，意見不一致的時間多到令人驚訝。

[01:29:39](https://youtu.be/qZj7sqmidqA?t=5379)

所以，如果你的 LLM 評審達到比人類更高的一致性，那它就是比人類做得更好。評審有時和我意見不同，本身並不是不信任它的理由。你要提防的，是一個總是和你意見不同的評審，那才是危險訊號。一個有時和你意見不同的評審，是在正確地處理一個真正模糊的任務。

[01:30:06](https://youtu.be/qZj7sqmidqA?t=5406)

還有，失敗應該讓人覺得公平。這是 Anthropic 評測團隊的一項原則，我想留給大家。當一個任務失敗時，應該要能清楚看出 agent 錯在哪裡、為什麼錯。如果你看著一條失敗的追蹤（trace），心想「這個答案看起來沒問題啊」，那問題很可能出在評測，而不是 agent。好，現在我們已經建好評測、也測試過了，接著就來用它們真正改進我們的 agent。

[01:30:34](https://youtu.be/qZj7sqmidqA?t=5434)

這就是如何形成閉環（close the loop）。一次性修正有個問題：你找到了一些失敗案例，讀了一些解釋，知道該改進什麼，於是修改提示詞，然後呢？你怎麼知道這個修正真的有效？你怎麼知道它有沒有破壞原本正常運作的東西？如果你只是在幾個範例上重跑 agent，然後用眼睛看看，那你又回到憑感覺（vibes）了。你需要一種結構化的方式來比較修改前後。正如我先前提到的，這就是實驗（experiments）的用途。

[01:31:06](https://youtu.be/qZj7sqmidqA?t=5466)

[01:31:53](https://youtu.be/qZj7sqmidqA?t=5513)

以確保當你修改了評分標準（rubric）時，沒有不小心讓原本成功的地方變成失敗。而且你的資料集並不是靜態的。在上線之前，你還沒有使用者的時候，資料集大概會是你自己生成的合成查詢（synthetic queries），或是請 LLM 幫你生成的查詢。這樣完全沒問題，它能讓你起步。但一旦真實流量開始進來，你就應該把它們變成你的評估資料集。

[01:32:28](https://youtu.be/qZj7sqmidqA?t=5548)

真實的失敗案例應該取代想像出來的案例。你的失敗案例與通過案例的聯集，就是大家所說的黃金資料集（golden data set）：一套經過整理、已標註、你信任它作為衡量品質基準真相（ground truth）的資料集。接下來我們要改進我們的代理（agent），但我們不打算手寫修正。

[01:32:49](https://youtu.be/qZj7sqmidqA?t=5569)

就像我提過的，這一切都可以用技能（skills）來完成，也都可以用程式碼代理（coding agent）來完成。我假設在 2026 年，所有人都已經在用程式碼代理處理他們所有的程式開發工作了。那麼，既然可以讓 Claude Code 去拉下你的失敗追蹤紀錄、幫你修改程式碼、幫你改進你的應用程式，你為什麼還要自己修改提示詞呢？

[01:33:11](https://youtu.be/qZj7sqmidqA?t=5591)

這就是我們在這裡要做的事。Claude 會拉下所有失敗的追蹤紀錄，閱讀所有的解釋，然後把這些解釋轉化為對你的程式碼庫採取的行動。而重點在於：這裡沒有任何東西是猜的。Claude 不是憑空發明改進方案，你並不是只對它說「在這方面做得更好」。

[01:33:33](https://youtu.be/qZj7sqmidqA?t=5613)

你也不是只對它說「不要犯任何錯」。它提出的每一項修改，都能追溯到某一則具體的失敗解釋。所以，如果評審（judge）說它缺乏具體建議，Claude 就會讀到這點，並重寫提示詞讓它做到；如果評審說它提出風險卻沒有佐證，那它也會重寫提示詞來修正這一點。這就是資料驅動的提示詞工程（data-driven prompt engineering），而現在我們可以把它自動化。請注意我們傳入了什麼：我們傳入了我們的需求，也就是我們想要完成的事，還傳入了一份改進提示詞，告訴它應該處理什麼、以及如何變得更好。這又是另一個 LLM 應用，又是另一個非確定性的東西，也又是另一個可能出錯的環節。

[01:34:18](https://youtu.be/qZj7sqmidqA?t=5658)

[01:34:50](https://youtu.be/qZj7sqmidqA?t=5690)

所以在這個案例中，我們拿這個提示詞，接進我們的兩階段流程。我們把 Claude 根據拉下的失敗追蹤紀錄所給出的建議，傳回給 Anthropic，並說：根據這些解釋，寫出一份更好的研究提示詞、一份更好的寫作提示詞，然後我們再把它們餵回我們的代理。接著，我們要執行一次實驗（experiment）。所以在介面上，我們有資料集和實驗。我們有我的 demo financial fails 資料集，我們可以，假設我能捲動畫面的話，

[01:35:37](https://youtu.be/qZj7sqmidqA?t=5737)

接上一個使用這些新的改進提示詞的改良版代理。你可以看到改進後的研究提示詞和改進後的寫作提示詞，除此之外，這個代理與先前完全相同。然後你可以用實驗建立一個評估器。我們在這裡做的，是給它一個任務（task）。任務可以是任何東西，例如它可以是你的代理所做事情的某個子元件。所以如果我們執行的是一個關於工具呼叫的評估器，那你的任務就可以只是呼叫這個工具，看看工具的輸出是什麼，然後評估它。在這個例子裡，我的任務是從頭到尾把整個代理再跑一遍，但

[01:36:22](https://youtu.be/qZj7sqmidqA?t=5782)

它並不一定要這樣。然後我們對這次新的任務執行，跑同樣的評估。所以，我們改了代理、重跑了代理，也重跑了評估，並把這一切變成一次實驗。實驗長這個樣子：Experiments.run。我們給它一個名稱。

[01:36:44](https://youtu.be/qZj7sqmidqA?t=5804)

我們給它它該處理的資料集，給它任務，給它評估器，然後告訴它執行。這會給我們結果，就在這裡。對於每一次執行，我們都有它得到的輸出，以及新的評估分數。如你所見，如果你還記得，這個資料集先前的所有案例都是「不可行動」（not actionable）的。評估跑完之後，你可以看到其中有一些現在是可行動的了。所以我們進步了，而如果看整體分數，其實我完美達成了，因為我有很多次機會把它做對。我一次就把我的提示詞調好了，從原本有 50%

[01:37:32](https://youtu.be/qZj7sqmidqA?t=5852)

的時間是錯的，變成 100% 的時間都是對的。真實的評估不會這樣運作，真實的迭代也不會進行得這麼順利。這就是為什麼它是一張圖表。你預期要做的是一次又一次地跑實驗，然後看著圖表隨著你的評估越來越強大而慢慢攀升。這就是我所說的、你正試圖攀爬的那座山丘。

[01:37:54](https://youtu.be/qZj7sqmidqA?t=5874)

所以，實驗背後的關鍵抽象是：任務就只是一個 Python 函式。它接收資料集中的一個範例，執行你想執行的任何東西，然後回傳一個輸出。所以 AX 並不在意任務內部做了什麼。它可以執行完整的代理，或者就像我說的只執行其中一個元件，或者也可以呼叫某個 API，只要它接收一個輸入並回傳一個輸出即可。

[01:38:17](https://youtu.be/qZj7sqmidqA?t=5897)

你就可以對它執行實驗。實驗的威力在於受控比較（controlled comparison）。你使用相同的輸入、相同的評估器，唯一改變的只有代理的提示詞。這意味著分數上的任何差異都可歸因於你的改動。你不必納悶：它分數比較高，是因為我改了提示詞，還是因為這次網路搜尋剛好回傳了比較好的結果？

[01:38:41](https://youtu.be/qZj7sqmidqA?t=5921)

嗯，其實你還是會有一點這樣的疑慮，因為代理是非確定性的，它可能做了 10 次網路搜尋而不是 5 次。但你已經排除了一個主要的變異來源，也就是測試案例。就像我說的，我的代理在這裡只有一次機會，這很棒，但現實中不會這麼簡單。我們在這裡談的評估迭代循環（eval-iterate cycle）：跑一次實驗、修改提示詞、再跑一次實驗，一遍又一遍地重複，真正的價值就在這裡，不在於分數本身，而在於這個循環。你跑評估，查看失敗案例，閱讀解釋，找出模式，然後調整你的提示詞，或者

[01:39:26](https://youtu.be/qZj7sqmidqA?t=5966)

就像這個案例中，讓 Claude 幫你調整提示詞。「它有變得更好嗎？」這個問題，只有評估能夠回答。你已經把「好」的定義用一種極其有用的方式寫成了規則。這讓你能夠從「我覺得它有效」走到「我能證明它有效」。

[01:39:48](https://youtu.be/qZj7sqmidqA?t=5988)
一個很快就會冒出來的實際問題是：到底需要多少樣本？像今天這種工作坊規模的實驗，12 到 20 個範例就能給你方向性的訊號。但如果是要做實際上線的決策，你會需要更多，大約 200 到 400 個是不錯的目標。不過要注意，200 到 400 仍然是一個人力可及的數量，你大概花幾週就能累積起來，並不像訓練機器學習（ML）模型那樣需要數萬甚至數百萬筆。這裡也有邊際效益遞減的問題：要把誤差範圍縮小一半，你得把樣本數增加為四倍。所以到了某個程度，你就已經有足夠的訊號可以往下進行了。

[01:40:30](https://youtu.be/qZj7sqmidqA?t=6030)
在迭代的時候，你該把心力投資在哪裡？這裡有一個優先順序。資料品質的修正影響最大。如果你的 agent 搜尋到錯誤的來源，或是你的知識庫裡有過時的資訊，那麼再怎麼反覆調整提示詞（prompt）都沒有用，你應該先修正資料。接下來是提示詞的改進，例如少樣本範例（few-shot examples）、明確的指令，也就是我今天提到的那類東西，還有對 agent 該做與不該做什麼所設下的限制。這些通常是對你的 agent 投資報酬率最高的改動。第三是模型選擇。有時候能力更強的模型能解決提示詞解決不了的問題，但它也會更貴、更慢，所以這是你必須做的取捨。至於不該花太多時間的，是超參數調校（hyperparameter tuning），像是 temperature 和 top p 這類東西。它們非常

[01:41:17](https://youtu.be/qZj7sqmidqA?t=6077)
容易讓人忍不住去動，因為很好調整。但它們很少像提示詞或提升資料品質那樣帶來高槓桿的改變，所以你可以試試，但它們應該是你最後才嘗試的東西。有一個值得知道的做法叫評估驅動開發（eval driven development）：在打造功能之前，先寫好評估。舉例來說，如果你希望你的 agent 在處理退款之前一定要先驗證客戶身分，那就先寫出檢查這件事的評估。這讓你對「好」是什麼樣子、「完成」是什麼樣子，有一個清楚可衡量的定義。然後你就可以持續開發功能，直到評估通過為止。這與測試驅動開發（test-driven development）是同樣的哲學。

[01:41:59](https://youtu.be/qZj7sqmidqA?t=6119)
我很喜歡評估驅動開發的一點是：最貼近產品需求的人，最適合來定義什麼是成功。所以產品經理、客服人員，甚至業務人員，都可以為評估任務做出貢獻。他們可以告訴你，實務上什麼樣子算好、什麼樣子不好。他們不需要寫程式，只需要用自然語言描述對他們來說「好」是什麼樣子。

[01:42:23](https://youtu.be/qZj7sqmidqA?t=6143)
然後你可以把這些濃縮成你的評估準則（eval rubric）。到目前為止，我已經向你展示了如何做離線和線上兩種方式，我們都是在 notebook 裡進行。但是，當你的開發實驗通過時，你並不算真的完成；當你的 agent 在面對你從未見過的流量時，仍能在正式環境（production）中持續表現良好，才算完成。即使我們這次工作坊還是會留在 notebook 裡，我仍然值得花幾分鐘談談這件事。第一件事是線上評估（online eval），就像我先前說的、也像我之前示範的，線上評估就如字面所示：它把你今天寫的評估器，像是 ticker 檢查、

[01:43:09](https://youtu.be/qZj7sqmidqA?t=6189)
忠實度（faithfulness）、可執行性（actionability），自動執行在進來的正式環境追蹤（trace）上，也就是同樣的評估跑在新的資料上。我之前示範過如何對單一追蹤執行。AX 讓你可以在三種範圍（scope）執行。你可以在 span 層級執行，也就是指定這一個 LLM 呼叫、這一個工具呼叫，每一次都對它執行評估；或者在 trace 層級執行，它能看到完整的樹狀結構，從頭到尾評估整個流程。你選擇符合你所問問題的範圍即可。而且你不需要對每一筆正式環境追蹤都執行評估。LLM 評審是要花錢的，在正式環境的規模下，這些成本會不斷

累積。所以你可以抽樣 10% 或 1% 的流量，這樣就能得到方向性的訊號，而不必對你應用程式的每一次執行都跑一次昂貴的 LLM 評審（LLM as a judge）。如果你不想手寫評估，我們有個好消息：我們在 AX 裡面內建了一個 agent，叫做 Alex。你可以用白話英文描述你的評估，或是請你的非技術同事用白話英文描述「好」的定義，Alex 就會替你實際操作介面：建立評估、撰寫準則、把所有分數設定正確、把所有設定都弄好，然後

[01:45:42](https://youtu.be/qZj7sqmidqA?t=6342)

[01:46:26](https://youtu.be/qZj7sqmidqA?t=6386)
所以這就是那個模式：你把失敗的追蹤連同它們的解釋，從 AX 匯出，然後把整批資料作為上下文，交給 Claude Code、Cursor 或其他程式開發 agent。這正是我一開始提到的 Arize skills 外掛發揮效果的地方，因為你不必知道如何呼叫我們的 API，也不必知道那些細節。你把這些技能（skills）交給它，然後告訴 Claude Code：「嘿，把一些追蹤拉下來，看看哪裡有問題，然後讓我的應用程式變得更好。」這樣就行得通了。不過這個做法應該有兩道護欄。首先，你應該把你的需求也一併餵給它，而不只是失敗的解釋。因為目標不是「讓評估通過」，否則它會作弊：它會把你所有的測試資料都放進它的評估裡，然後自動通過你所有的評估。

[01:47:12](https://youtu.be/qZj7sqmidqA?t=6432)

它會把所有的測試資料都塞進自己的程式碼裡，然後自動讓你所有的評測（eval）全部通過。所以你必須確保給 Claude Code 的需求寫得清楚：你不是只要它讓評測通過，而是要它去做某件具體的事，然後讓評測因此通過。第二，你應該告訴它去找出共通主題，而不是追著個別的失敗跑。Claude Code 很容易只看某一條失敗的追蹤紀錄，就寫了一大堆程式碼去修那一條，但實際上可能有 10 條失敗的追蹤紀錄都是同一個原因，它應該把焦點放在那個原因上。這些我沒辦法全部示範，因為我只剩 12 分鐘了。不過，一旦你有了評測，這是你能用它們做的最高槓桿的事情之一，

所以我們退一步來看整體的樣貌。正式環境產生追蹤紀錄（trace）；線上評測對它們評分並產出解釋；程式開發代理（coding agent）讀取這些解釋並提出修正；實驗驗證這些修正確實有效，然後上線。回流的正式環境流量，會再被當初啟動這個循環的同一套線上評測評分。這就是軟體開發生命週期自己閉合成一個圈：你的 AI 軟體正在幫你改善你的 AI 軟體，而 AX 就是把這一切串在一起的基底：你的追蹤紀錄、評測、解釋、資料集、實驗、線上評測，以及監控。

評測是基礎設施，不是事後才補的東西。有些團隊在開發一開始就建立評測，有些則是等到規模變大之後才加。但無論哪種，重要的是把評測視為系統的核心部分。它們應該像單元測試一樣例行，而價值會不斷累積，但前提是你持續投入。每當一次退化（regression）在觸及使用者之前、而不是之後被發現，你就會明白為什麼做這一切是值得的。不要寄望於「很棒」，你可以有系統地達到很棒：把它明確定義、衡量它、並朝它持續改進。
