## [核心摘要]

Matt Pocock 完整示範如何用其開源的 skills 系列，在 Claude Code 上交付一個 21,000 行的縮圖圖表編輯功能。核心貢獻在於展示一套「人機分工」工作流：人類主導前期領域建模（grill-with-docs 拷問）與後期品味審查（retro 回顧），把中間的規格、工單與實作全部壓縮進代理的決策真空區，解決「AI 寫碼品質不可控、方向漂移」的痛點。

## [詳細重點整理]

1. 技能選擇決策樹 

新工作開始時先問：我要的東西本質上是一個 diff。diff 很小就 one-shot；diff 大就用 grill-with-docs；如果比想像大很多再轉向 wayfinder（把拷問延伸到多個 session）。本次功能（縮圖產生器中直接繪製圖表）明顯偏大，故選 grill-with-docs。執行環境為個人 home repo + Claude Ultra（Opus 5.5、medium effort），多數 skill 開源於 [aihero.dev/skills](http://aihero.dev/skills)。

**關鍵概念：diff 評估** — 以改動規模決定流程重量，避免流程過重或不足。

2. 拷問的藝術：給「為什麼」而非「做什麼」

用 Wispr Flow 語音輸入描述痛點（附圖表流程繁瑣、無法就地編輯），刻意只講問題與動機，不指定解法。這讓 agent 有自主空間產出更有創意的方案。agent 回覆一連串拷問問題（繁瑣流程具體是什麼？縮圖圖表與影片圖表是否同一張？能否從零開始畫？），過程中 agent 同時派背景子代理查找佐證、修改問題。

**關鍵概念：why-driven prompting** — 給「為什麼」讓 agent 自行探索解法，比下達「做什麼」得到更好的結果。

3. 領域建模：[glossary.md](http://glossary.md) 是程式碼庫的憲法

560 行的 [glossary.md](http://glossary.md) 定義了專案所有核心詞彙：圖表（diagram）是一組隨片段變化的快照、作用中圖表、還原至最新、保留快照等。拷問本質上是把新功能往這片既有版圖上「補位」。本次新增三個詞：縮圖、去背人像（cutout）、縮圖圖表（thumbnail diagram）。ADR（架構決策紀錄）記錄這些籬笆為何而立 — 典型的切斯特頓籬笆問題：在知道用途前不要拆掉它。用語之所以重要，是因為**用語形成資料模型**：有了正確名稱，就有資料表名稱、模組與參照結構。

**關鍵概念：領域驅動設計（DDD）** — 搞清楚語言就搞清楚了應用程式；拷問理想狀態像跟一位極度熟悉程式碼庫的同事做小黃鴨除錯。

4. 命名之爭與情境測試

Agent 擅自新增「縮圖繪圖」條目與 ADR，被 Matt 糾正：決策權應留在人手上。之後透過情境測試（scenario testing）比較三個候選詞：縮圖圖表快照、縮圖圖表、縮圖場景。逐一測試「從快照開始做縮圖」「playground 時間軸會出現嗎」「快照是不能改的」等句子是否說得通。結論選「縮圖圖表」：它是 Matt 自然會說的話（符合心智模型），且詞彙表中「場景」一詞已被占用。配套寫一份 ADR 說明「它叫圖表但技術上不是圖表」。

**關鍵概念：情境測試** — 用真實句子檢驗領域語言，而非抽象討論命名。

5. 原型迭代：用失敗的版本學習

Prototype skill 同時產出三個變體：A（臉在畫布內、可左右移動、幽靈臉功能）、B（臉太大、檢視條礙眼）、C（分割檢視需手動對齊手指，最差）。做出你不喜歡的東西往往比做出你喜歡的更能提供資訊。選定 A 後口述回饋迭代：降低臉部移動靈敏度、移除白線、預覽移到編輯器下方、補上命令面板與搜尋插入既有圖表。原型階段的價值在於**縮小代理的決策空間**，之後 AFK 執行時代理只需把 UI 與資料模型接起來。tldraw 內建復原歷史到資料模型中，使移動臉部與重拍免費獲得 undo 功能。

**關鍵概念：人機迴圈縮窄決策空間** — 原型先行把模糊地帶在人類在場時清光。

6. 聰明區與笨區：上下文的平方爆炸

token 增加，模型需追蹤的 token 間關係數量以平方級膨脹，幻覺風險升高。Dex Horthy 提出、Matt 引用的洞見：舊模型約 120K（Sonnet 3.5 約 80K）就需清上下文；現代模型已是成本與最佳化問題 — 笨區的問題不是幻覺，而是產出品質變差，且快取過期後所有 token 會被重新計費。解法是 compact（壓縮），尤其當對話已轉成文件時幾乎零代價；自動壓縮時機仍不可靠。

**關鍵概念：聰明區／笨區** — 上下文越少代理越聰明，管理的是產出品質與成本，不只是幻覺。

7. to-spec 與 to-tickets：目的地文件與範圍切分

to-spec 產出規格（GitHub issue 形式）：約 47 個使用者故事、實作決策、不在範圍內項目，並引用本地分支上的原型。to-tickets 把規格拆成 9 張工單，每張標註被哪些工單阻擋，可平行處理。Reducer 是代理擴充前端狀態的絕佳載體。之後 compact 對話、執行 implement-spec skill 在 AFK 狀態下平行實作全部工單，合併為單一 PR，耗時約 45–60 分鐘。核心原則：**不給代理任何決策空間** — 給它的選擇越多，選到糟糕選項的機率越高。

**關鍵概念：規格即目的地、工單即邊界** — 長時間 session 的一切所需，壓縮成文件後交棒。

8. 巨型 PR 的人工審查 

implement-spec 附帶自動 code review（對照 coding standards），找到一項嚴重違規與數處範圍蔓延。之後指示把巨型 PR 拆成堆疊式差異：一連串雙向門（可合併、可 revert 的 PR）以單向門（feature flag 開關）收尾，模擬正式環境漸進部署。審查中 Matt 標記的問題包含：大段註解（增加代理需更新的表面積）、TypeScript 的 as 關鍵字、Pick + 交集型別、fetch 忽略回傳、useSearchParams 魔術字串。審查不是為了擋合併，而是為了對「產出程式碼的系統」建立假設 — 每個不喜歡的模式都要變成 lint 規則逐步收緊（ratchet）。

**關鍵概念：雙向門／單向門 PR 拆分** — 把一大塊風險變成多扇可還原的門。

9. retro 回顧：把審查意見變成系統改進

retro skill 讀取本機磁碟上全部約 30 個 session 紀錄與 12 則審查留言，回傳排序過的改進清單。發現：12 則留言全部源於同一根本原因 — 書面規範沒涵蓋這些點，且 docs 展示的正是被否決的模式，main 分支上已有數千個實例（如 as 逾 2,000 個、useEffect 230 個分布於 140 檔案）。行動：把留言轉為逐步收緊的 lint 檢查、修正教錯誤模式的文件、針對自己的 skills 開 issue（prototype 程式碼被直接複製而非重寫、code-review skill 400 字限制）。本次 retro 約可產出 20 個 issue，後續不需拷問、直接交給 agent。

**關鍵概念：retro 飛輪** — 回顧的產出回頭改進 skills 與規範，讓下一輪 session 更好。

10. 註解稽核與收尾

約 2,000 行註解中：940 行可立即刪除、約 1,000 行解釋程式碼看不出來的原因、7 則已過時。新功能 diagrams 資料夾 18% 行數是註解，全 repo 平均 12%。Lauren Tan（poteto）的做法是完全禁止註解。註解是變通做法的遮羞布：禁止寫註解可能讓你不走變通的路。被要求更激進後，agent 提出 22 則可直接刪、18 個變通做法需改寫，tldraw 與 Command K 的怪癖應變成轉接器包裝層，競態條件限制應變成測試名稱。最終功能上線運作，Matt 的定位：他在前期對齊（拷問）與後期品味（審查、QA）最有價值。

**關鍵概念：註解即程式碼異味** — 註解標示著程式碼本該設計得不同的地方。

## [結論與行動建議]

啟發金句：「你給代理的模糊空間越多，它就越有可能選到糟糕的選項 — 人類的價值在於把決策空間壓到零。」

具體行動建議：**G-S-R 法則（Grill → Spec → Retro）** — 開工先拷問（用領域語言鎖定模型），中場壓縮成規格與工單後 AFK 執行，收工用 retro 把每次審查意見變成 lint 規則與 skill issue，讓系統逐輪升級。

生活實踐建議：

- 對自己的 side project 建立 [glossary.md](http://glossary.md)：先寫下核心詞彙再寫碼，agent 與未來的自己都能讀懂。
- 審查 AI 產出時不只問「能不能動」，而問「這個模式我願不願意看到 2,000 次」— 不願意就寫成 lint 規則逐步收緊。
- 在 Claude Code 中實測 Matt 的開源 skills（[aihero.dev/skills](http://aihero.dev/skills)）：grill-with-docs 處理需求發散、prototype 並列多個 UI 變體做 A/B 感受測試。
- 大型改動一律拆成雙向門 PR + feature flag 收尾，模擬正式環境的漸進部署。
- 遇到子代理變笨（token 堆積）時開新代理而非硬撐，compact 前先把對話沉澱成文件。
