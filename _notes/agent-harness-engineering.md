# 代理人框架工程（Agent Harness Engineering）

**核心摘要**

多數 AI 代理人的失敗不是模型問題，而是**框架（Harness）**問題。框架涵蓋所有非模型本身的元素——提示詞、工具、沙盒、鉤子、情境策略與回饋迴路。一個普通模型配上出色框架，勝過出色模型配上糟糕框架。Viv Trivedy 的實驗證明：僅更換框架，同一個 Claude Opus 4.6 模型在 Terminal Bench 2.0 上能從前 30 名躍升至前 5 名。這篇文章的核心貢獻是：將代理人錯誤從「等待下一個模型版本」的被動宿命，轉化為可透過框架工程主動修復的「技術問題（Skill Issues）」。

***

## 詳細重點整理

### 1. 框架的定義與組成 [導言]

> **核心概念：代理人 = 模型 + 框架**

模型只是輸入項之一，框架才是讓模型成為「能完成任務的代理人」的關鍵。框架包含：

- **系統提示詞**：CLAUDE.md、AGENTS.md、子代理提示詞
- **工具層**：技能、MCP 伺服器及其描述
- **執行基礎設施**：檔案系統、沙盒、瀏覽器
- **協調邏輯**：子代理生成、交接、模型路由
- **確定性鉤子**：壓縮、延續、語法檢查、預提交守衛
- **可觀測性**：日誌、追蹤、成本與延遲計量

***

### 2. 「技術問題」的重新框架 [核心論點]

> **核心概念：框架差距（Harness Gap）**

工程師習慣在代理人出錯後歸咎模型，並等待下一個版本。框架工程的思維完全相反：

| 失敗現象 | 框架層解法 |
|---|---|
| 提交了被注解掉的測試 | AGENTS.md 新增規則 + grep 鉤子阻擋 `.skip(` |
| 執行破壞性指令 | 前置鉤子攔截 `rm -rf`、`DROP TABLE` |
| 40 步任務中途迷失 | 拆分為規劃器（Planner）+ 執行器（Executor） |
| 輸出有錯誤卻標記「完成」 | 接入型別檢查作為迴路反壓信號 |

***

### 3. 棘輪機制：錯誤 → 永久規則 [方法論]

> **核心概念：棘輪式框架強化（Ratchet Mechanism）**

每一個真實的代理人失敗，都應轉化為三層防護：
1. **文件層**：更新 AGENTS.md 規則
2. **鉤子層**：預提交腳本自動攔截
3. **審查層**：子代理將該行為標記為阻擋項

原則：**只有見過真實失敗才添加約束；只有模型能力使其冗餘才移除它。** AGENTS.md 每一行都應可追溯至一次具體的失敗事件。

***

### 4. 從行為反推框架設計 [設計方法]

> **核心概念：行為驅動框架設計（Behavior-First Harness Design）**

以「我想要什麼行為」為起點，推導框架組件：

- **檔案系統 + Git**：賦予代理人持久狀態，支援多代理協作與版本回滾
- **Bash + 程式碼執行**：通用問題解決策略，讓代理人即時構建所需工具
- **沙盒**：隔離執行環境，支援並行代理人、命令白名單、網路隔離
- **記憶與搜尋（AGENTS.md + MCP）**：跨會話知識注入，填補訓練截止時間空缺

***

### 5. 對抗情境腐化 [技術細節]

> **核心概念：情境腐化（Context Rot）**

情境窗口填滿後，模型推理品質顯著下降。三種框架層對策：

- **壓縮（Compaction）**：智慧摘要舊情境，讓代理人持續工作而非報錯中斷
- **工具輸出卸載**：超過閾值的大型輸出（如 2000 行日誌）保留頭尾，完整內容寫入檔案系統
- **技能漸進揭露**：只在任務真正需要時才載入對應工具，避免啟動時即降低效能

對於超長任務，Anthropic 建議**完整情境重置**：拆除舊會話，從一份結構化交接文件重建——類似讓新工程師透過 onboarding 文件快速接手。

***

### 6. 長時程執行：Ralph 迴路與規劃器拆分 [進階架構]

> **核心概念：規劃器／生成器／評估器拆分（Planner-Generator-Evaluator Split）**

- **Ralph 迴路**：鉤子攔截模型的「退出」行為，將原始提示詞注入新情境窗口，強制代理人繼續工作，透過檔案系統讀取前次狀態——將單會話代理人變成多會話代理人的簡單技巧
- **衝刺契約（Sprint Contract）**：生成器與評估器在寫程式碼前，先協商「完成」的定義
- **為何拆分**：代理人評估自己的輸出時系統性偏向正面；獨立評估器能消除這個偏差

***

### 7. 鉤子與 AGENTS.md 的實作原則 [實作指南]

> **核心概念：強制執行層（Enforcement Layer）**

鉤子的黃金原則：**成功時靜默，失敗時詳細。** 通過則代理人無感知；失敗則錯誤文本自動注入迴路，代理人自行修正。

AGENTS.md 兩大來之不易的教訓：
- **保持簡短**（建議 60 行以內）：規則越多，每條規則的注意力權重越低
- **讓每行有所依據**：可追溯至具體失敗的規則才是真正的信號，其餘是噪音

***

### 8. 框架不縮小，只移動 [長期視野]

> **核心概念：框架假設遷移（Harness Assumption Migration）**

每個框架組件都編碼了一個「模型獨立無法做到的事」的假設。模型進步後：
- 舊假設失效 → 對應組件變成死程式碼，應移除
- 模型解鎖新能力 → 更高天花板的任務出現 → 需要新的框架組件

例：Opus 4.6 消滅了情境焦慮失敗，舊的焦慮緩解鷹架成為死程式碼，但取而代之的是多日記憶策略與多代理協調框架的新需求。

***

## 結論與行動建議

**啟發金句**

> 「今日模型實際能做到的，與你看到它所做到的，之間的差距，很大程度上是**框架差距**。」

**核心法則：R-E-H 法則**
- **R（Ratchet）棘輪**：每次失敗都轉化為永久規則
- **E（Enforce）強制**：用鉤子取代「告訴模型」，讓系統強制執行
- **H（Harness-first）框架優先**：出了問題先問框架，再問模型

**生活實踐建議**

- **立即行動**：審視你的 AGENTS.md，刪除無法追溯至具體失敗的規則，保持在 60 行以內
- **本週建立**：為你最常遇到的代理人失敗類型，新增一個預提交鉤子（如：阻擋 `.skip(` 測試、強制型別檢查）
- **下個迭代**：嘗試將長任務拆分為「規劃器代理人」和「執行器代理人」，並在開始前用衝刺契約定義完成條件
- **長期習慣**：每季度審查框架組件，移除因模型能力提升而成為死程式碼的部分

# 代理人框架工程（Agent Harness Engineering）

> **作者：Addy Osmani｜2026 年 5 月 15 日｜預計閱讀時間：17 分鐘**
>
> 一個程式碼代理人，等於模型加上你圍繞它建構的一切。框架工程將這些鷹架視為真正的交付物，並在每次代理人出錯時加以強化。

---

> *本文最初發表於 [Addy Osmani 的部落格](https://addyosmani.com/blog/agent-harness-engineering/)，已獲作者授權在此轉載。*

簡單來說：每當你發現代理人犯了錯誤，你就花時間設計一個解決方案，讓代理人永遠不再犯同樣的錯誤。

過去兩年，我們一直在爭論模型。哪個最聰明、哪個寫出最乾淨的 React、哪個幻覺最少。這個討論本身沒什麼問題，但它遺漏了系統的另一半。模型只是一個運行中代理人的輸入項之一。其餘的都是**框架（harness）**：包裹在模型外部的提示詞、工具、情境策略、鉤子（hooks）、沙盒、子代理、回饋迴路和恢復路徑，讓模型真正能夠完成任務。

**一個普通的模型配上一個出色的框架，勝過一個出色的模型配上糟糕的框架。** 我在自己的工作中反覆印證了這一點。而且越來越多有趣的工程挑戰，不在於選擇哪個模型，而在於設計圍繞它的鷹架。

這門學問現在有了名字。Viv Trivedy 創造了「框架工程（harness engineering）」這個術語，他的文章〈[解剖代理人框架](https://x.com/Vtrivedy10/status/2031408954517971368)〉最清晰地推導出框架究竟是什麼、以及每個組件為何存在。[Dex Horthy](https://x.com/dexhorthy/status/1985699548153467120) 一直在追蹤這個模式的浮現。[HumanLayer](https://www.humanlayer.dev/blog/skill-issue-harness-engineering-for-coding-agents) 將多數代理人失敗歸結為「技術問題（skill issues）」，源於配置而非模型權重。[Anthropic 的工程團隊](https://www.anthropic.com/engineering/harness-design-long-running-apps) 發表了我認為目前最佳的公開說明，解釋如何為長時間執行的任務設計框架。而 [Birgitta Böckeler](https://martinfowler.com/articles/exploring-gen-ai/harness-engineering.html) 則從使用者視角概述了這看起來是什麼樣子。

這篇文章是我嘗試將這些觀點整合起來的成果。

---

## 框架究竟是什麼？

Viv 的一句話道盡了核心：
> 代理人 = 模型 + 框架。如果你不是模型，你就是框架。

框架是所有非模型本身的程式碼、配置和執行邏輯。原始模型不是代理人。一旦框架賦予它狀態、工具執行、回饋迴路和可強制執行的約束，它才成為代理人。

![模型是板子上的一顆晶片，框架是讓它有用的其餘一切。](https://www.oreilly.com/radar/wp-content/uploads/sites/3/2026/05/image.jpeg)

*圖：模型是板子上的一顆晶片，框架是讓它有用的其餘一切。*

具體而言，框架包含：

- 系統提示詞、CLAUDE.md、AGENTS.md、技能文件及子代理提示詞
- 工具、技能、MCP 伺服器及其描述
- 捆綁基礎設施（檔案系統、沙盒、瀏覽器）
- 協調邏輯（子代理生成、交接、模型路由）
- 用於確定性執行的鉤子與中介軟體（壓縮、延續、語法檢查）
- 可觀測性（日誌、追蹤、成本與延遲計量）

[Simon Willison](https://simonwillison.net/2025/Sep/30/designing-agentic-loops/) 將迴路部分化繁為簡：代理人是一個「在迴路中執行工具以達成目標」的系統。技巧在於工具與迴路的設計。

如果這聽起來覆蓋面很廣，的確如此。而且這是**你的**覆蓋面，不是模型供應商的。Claude Code、Cursor、Codex、Aider、Cline：這些都是框架。**底層模型有時是相同的，但你所體驗到的行為，主要由框架決定。**

```
程式碼代理人 = AI 模型群 + 框架
```

這個等式由 Viv 提出，也被 HumanLayer 認可，是工作真正所在之處。關於等式左側的爭論喧囂不已。然而，絕大多數真正的槓桿點，坐落於右側。

## 「技術問題」的重新框架

有一個模式我一直在觀察工程師反覆踩坑。代理人做了件蠢事，工程師責怪模型，然後這個責怪被歸檔為「等待下一個版本」。

框架工程的思維方式拒絕這種預設。失敗通常是可解讀的。代理人不了解某個規範，所以你把它加進 AGENTS.md。代理人執行了破壞性指令，所以你加一個阻擋它的鉤子。代理人在 40 步的任務中迷失了，所以你把它拆分成規劃器和執行器。代理人一直「完成」有錯誤的程式碼，所以你在迴路中接入型別檢查的反壓信號。

HumanLayer 說：「這不是模型問題，是配置問題。」框架工程就是你認真對待這句話時所做的事。

Viv 的文章和 HumanLayer 的文章中都出現了一個引人注目的數據點。在 Terminal Bench 2.0 上，Claude Opus 4.6 在 Claude Code 中執行的分數，遠低於同一模型在自定義框架中執行的分數。Viv 的團隊只更改了框架，就將一個程式碼代理人從前 30 名移動到前 5 名。模型在訓練後與訓練時使用的框架耦合在一起。將它們移入不同的框架——針對你的程式碼庫配備更好的工具、更緊密的提示詞和更鮮明的反壓——可以釋放原始框架未能發揮的潛力。

這與「只需等待 GPT-6」的說法截然相反。**今日模型實際能做到的，與你看到它所做到的，之間的差距，很大程度上是框架差距。**

---

## 棘輪機制：每一個錯誤都成為一條規則

框架工程中最重要的習慣，是將代理人的錯誤視為永久信號。不是偶發的笑話，不是需要重試的「不良執行」，而是信號。

如果代理人提交了一個帶有被注解掉的測試的 PR，而我意外地合併了它，那就是一個輸入。下一版本的 AGENTS.md 說：「永遠不要注解掉測試；刪除它們或修復它們。」下一版本的預提交鉤子用 grep 搜尋差異中的 `.skip(` 和 `xit(`。下一版本的審查子代理將注解掉的測試標記為阻擋項。

只有當你見過真實的失敗後，才添加約束。只有當一個有能力的模型使其冗餘時，才移除它們。**一個好的 AGENTS.md 中的每一行，都應該可以追溯回一個具體出錯的事情。**

這也是框架工程是一門學科而非框架的原因。適合你程式碼庫的正確框架，是由你的失敗歷史塑造的。你無法下載它。

---

## 從行為反推設計

Viv 的框架中，我在實際設計框架時發現最有用的，是從你想要的行為出發，推導出能實現該行為的框架組件。他的模式是：*我們想要（或想要修復）的行為 → 幫助模型實現此目標的框架設計*。

![每個框架功能都是跨越模型無法獨立完成之事的橋樑](https://www.oreilly.com/radar/wp-content/uploads/sites/3/2026/05/image-1.jpeg)

*圖：每個框架功能都是跨越模型無法獨立完成之事的橋樑*

這種推導方式的好處在於，每個框架組件都有一個具體的任務。**如果你無法說清楚一個組件存在是為了實現什麼行為，它可能就不應該存在。**

本節其餘部分按照 Viv 的順序逐一說明，加上我認為值得借鑒的具體模式。

---

## 檔案系統與 Git：持久狀態

檔案系統是最基礎的原語，而且因為它無趣，往往被低估。模型只能直接操作能放入情境窗口的內容。沒有檔案系統，你就是在聊天視窗裡貼上貼下，那不是一個工作流程。

一旦有了檔案系統，代理人就獲得了一個讀取資料、程式碼和文件的工作區；一個可以卸載中間工作而不必佔用情境的地方；以及一個多個代理人和人類可以通過共享文件協作的介面。在上面加入 Git，你就免費獲得了版本控制，讓代理人可以追蹤進度、回滾錯誤並建立分支實驗。

其他大多數框架原語最終都需要向檔案系統索取某些東西。

---

## Bash 與程式碼執行：通用工具

今天主要的代理人迴路是 ReAct 迴路：模型推理，通過工具調用採取行動，觀察結果，然後重複。但框架只能執行它有邏輯的工具。你可以嘗試預先為每一個可能的動作構建一個工具，或者你可以給代理人 bash，讓它即時構建所需的工具。

Willison 的看法是，代理人已經擅長 shell 命令；大多數任務都歸結為幾個精心挑選的 CLI 調用。框架仍然提供專注的工具，但 bash 加上程式碼執行已成為自主解決問題的預設通用策略。這就像是教人使用一個廚房小工具和把整個廚房交給他們之間的差別。

---

## 沙盒與預設工具

只有在安全的地方運行，bash 才有用。在你的筆記型電腦上運行代理人生成的程式碼有風險，而且單一本地環境無法擴展到多個並行代理人。

沙盒為代理人提供隔離的運行環境。框架連接到沙盒來運行程式碼、檢查文件、安裝依賴項並驗證工作，而不是在本地執行。你可以將命令加入白名單、強制網路隔離、按需啟動新環境，並在任務完成後拆除它們。

一個好的沙盒自帶良好預設：預裝的語言執行時和套件、Git 和測試 CLI，以及用於網頁互動的無頭瀏覽器。瀏覽器、日誌、截圖和測試執行器讓代理人能夠觀察自己的工作，從而形成自我驗證迴路。

模型不配置自己的執行環境。決定代理人在哪裡運行、有什麼可用，以及如何驗證其輸出，都是框架層面的決策。

---

## 記憶與搜尋：持續學習

模型除了權重和當前情境中的內容之外，沒有額外的知識。在無法編輯權重的情況下，添加知識的唯一方式是通過情境注入。

檔案系統再次成為原語。框架支持像 AGENTS.md 這樣的記憶文件標準，每次啟動時都會注入。當代理人編輯該文件時，框架重新加載它，一個會話中的知識就帶入了下一個會話。這是一種粗糙但有效的持續學習形式。

對於訓練時不存在的知識（新的函式庫版本、最新文件、今天的數據），網頁搜尋和 Context7 等 MCP 工具彌補了訓練截止時間的空缺。將這些有用的原語烘焙進框架中，比留給用戶自行處理要好。

---

## 對抗情境腐化

情境腐化是指，隨著情境窗口填滿，模型在推理和完成任務方面變得更差。情境是稀缺資源，框架在很大程度上是良好情境工程的傳遞機制。

三種技術反覆出現：

**壓縮（Compaction）**。當窗口接近滿載時，必須作出取捨。讓 API 報錯對生產框架來說不是選項，所以框架智慧地摘要並卸載較舊的情境，讓代理人能夠繼續工作。

**工具調用卸載**。大型工具輸出（想象一個 2000 行的日誌文件）在不增加多少信號的情況下會佔用情境。框架在超過閾值的情況下保留頭部和尾部令牌，並將完整輸出卸載到檔案系統，代理人可以按需讀取。

**具有漸進式揭露的技能**。在啟動時將每個工具和 MCP 都加載到情境中，會在代理人採取第一個行動之前就降低性能。技能讓框架只在任務真正需要時才揭露指令和工具。

Anthropic 的框架文章為真正長時間的任務增加了一種技術：完整情境重置，框架拆除會話並從一個緊湊的交接文件重建它。他們明確表示，*僅靠壓縮對於長任務來說是不夠的*；有時你需要用一份結構化的簡報重新開始。這更接近於人類讓新工程師入職的方式，而不是我們通常想象「記憶」的方式。

## 長時程執行：Ralph 迴路、規劃與驗證

自主的長時程工作是聖杯，也是最難做好的事情。今天的模型存在提前停止、對複雜問題分解不佳，以及在跨越多個情境窗口的工作中出現不一致的問題。框架必須圍繞這些問題進行設計。

我之前在[自我改進代理人](https://addyosmani.com/blog/self-improving-agents/)和我的 [2026 趨勢文章](https://beyond.addy.ie/2026-trends/)中寫過像 Ralph 迴路這樣的自主程式碼迴路，但在這個框架下值得重述：一個鉤子攔截模型嘗試退出的行為，並將原始提示詞注入到一個新的情境窗口中，迫使代理人繼續針對完成目標工作。每次迭代都從乾淨狀態開始，但通過檔案系統讀取前一次的狀態。這是一個將單會話代理人變成多會話代理人的出人意料的簡單技巧，而且這種原語是你永遠無法從「只需使用更智慧的模型」中推導出來的。

**規劃**是模型將目標分解為一系列步驟，通常分解到磁碟上的一個計畫文件中。框架通過提示詞和關於如何使用計畫文件的提醒來支持這一點。每個步驟之後，代理人通過自我驗證來檢查其工作：鉤子運行預定義的測試套件，並將失敗的錯誤文本循環回給模型，或者模型根據明確標準審查自己的輸出。

**規劃器/生成器/評估器拆分**。Anthropic 的長時程框架工作明確指出，將生成與評估拆分為不同的代理人，勝過自我評估，因為代理人在評分自己的工作時可靠地偏向正面。這就像是散文的對抗生成網路（GAN）。相關模式是**衝刺契約（sprint contract）**，生成器和評估器在寫程式碼之前協商「完成」實際意味著什麼。在我自己的工作流程中，在開始之前寫下完成條件，比我做過的任何提示詞更改都更能發現範疇蔓延問題。

---

## 鉤子：強制執行層

鉤子是將「我告訴代理人做 X」與「系統強制執行 X」分開的東西。

鉤子是在特定生命週期點運行的腳本：工具調用前、文件編輯後、提交前、會話啟動時。它們是放置那些代理人應該永遠記住但經常忘記的事情的正確位置。每次編輯後運行型別檢查、linting 和測試，並呈現失敗。阻止破壞性 bash（`rm -rf`、`git push --force`、`DROP TABLE`）。在開啟 PR 或推送到主分支之前要求審批。自動寫入時格式化，這樣代理人就不會在空白格式上浪費令牌。

HumanLayer 強調並且我已認同的原則是：**成功時靜默；失敗時詳細**。如果型別檢查通過，代理人什麼都聽不到。如果失敗了，錯誤文本就被注入到迴路中，代理人自行修正。這使得在常見情況下，回饋迴路幾乎是免費的，而在出現問題時直接可採取行動。

## AGENTS.md 與工具選擇

放在你倉庫根目錄的扁平 Markdown 規則手冊，仍然是單一最高槓桿的配置點，因為它每次都進入系統提示詞。規範放在這裡：套件管理器、測試框架、格式化規則、「永遠不要碰 `/legacy`」、「始終使用我們的日誌記錄器」。兩個來之不易的教訓：

保持簡短。HumanLayer 保持在 60 行以內。每一行都在競爭注意力，規則越多，每條規則的重要性就越低。**飛行員清單，不是風格指南**。

讓每一行有所依據。規則應該可以追溯到過去特定的失敗或外部硬性約束。如果不能，它們就是噪音。棘輪機制；不要頭腦風暴。

同樣的原則適用於工具。每個工具的名稱、描述和模式（schema）都會在每次請求時被戳入提示詞。十個專注的工具勝過五十個重疊的工具，因為模型能將這份菜單記在腦子裡。HumanLayer 也指出了一個真實的安全顧慮：工具描述填充提示詞，因此你安裝的任何 MCP 伺服器都是模型將要讀取的受信任文本。一個草率或惡意的 MCP 可以在你輸入任何內容之前就對你的代理人進行提示詞注入。

## 在生產環境中是什麼樣子

我見過的最清晰的成熟框架公開圖景，是 Fareed Khan 對 [Claude Code 架構](https://levelup.gitconnected.com/building-claude-code-with-harness-engineering-d2e8c0da85f0)的（估計）拆解。

前幾節的幾乎每個概念都以具名組件的形式出現在這個圖表中。情境注入是知識層。迴路狀態存在於記憶存儲和工作區隔離器中。破壞性動作鉤子位於權限閘後面。子代理情境防火牆就是整個多代理層。工具分發登錄表是 MCP 伺服器和 bash 都能接入的地方。Khan 的論點與 Viv 的相同，只是通過一個出貨產品來驗證：**Claude Code 的發展軌跡，至少與框架有關，就和與底層模型有關一樣多。**

## 框架不會縮小；它只是移動

Anthropic 文章中較好的觀察之一是，隨著模型的改進，有趣的框架組合空間並不會縮小，它只是移動。

這個天真的故事是，更好的模型讓框架過時。如果模型能夠規劃，就不需要規劃器。如果模型在長時程上是連貫的，就不需要情境重置。是的，Opus 4.6 基本上消滅了情境焦慮失敗模式（Sonnet 4.5 過去在接近情境限制時會提前結束工作），這意味著我六個月前寫的整整一類焦慮緩解鷹架現在是死程式碼了。

但天花板隨著模型一起移動了。以前無法到達的任務現在已進入視野，它們有自己的失敗模式。焦慮鷹架消失了，取而代之的是你需要一個多日記憶策略，或一個協調三個專業代理人的框架，或生成 UI 的設計品質評估器。假設發生了改變，編碼這些假設的鷹架也隨之改變。

Anthropic 說得清楚：「框架中的每個組件都編碼了一個關於模型獨立無法做到什麼的假設。」當模型在某件事上變得更好時，那個組件就不再承重，應該移除。當模型解鎖了新的能力時，就需要新的鷹架來達到新的天花板。

## 模型-框架訓練迴路

另一件正在發生的事，Viv 明確提到了，是框架設計和模型訓練之間的回饋迴路。

![框架不會縮小，它只是移動](https://www.oreilly.com/radar/wp-content/uploads/sites/3/2026/05/image-2.jpeg)

*圖：框架不會縮小，它只是移動*

今天的代理人產品是在框架迴路中進行後訓練的。模型針對框架設計者認為它應該擅長的動作特別改進：檔案系統操作、bash、規劃、子代理分發。這就是為什麼 Opus 4.6 在 Claude Code 內部的感受與在其他人的框架內部不同，也是為什麼更改工具的邏輯有時會導致奇怪的回歸。一個真正通用的模型不會在乎你使用 `apply_patch` 還是 `str_replace`，但協同訓練產生了過擬合。

實際含義是雙重的。**框架是一個活系統，不是你一次性設置的配置文件。** 而且「最好的」框架不一定是模型在其中訓練的那個；而是為你的任務設計的那個。Viv 在 Terminal Bench 上從前 30 名躍升到前 5 名是我見過的最清晰的佐證。

## 框架即服務（HaaS）

Viv 的另一個貢獻是 [HaaS](https://www.vtrivedy.com/posts/claude-code-sdk-haas-harness-as-a-service) 框架：框架即服務。觀察是，我們正在從構建在 LLM API 之上（提供完成）轉向構建在框架 API 之上（提供執行時）。Claude Agent SDK、Codex SDK 和 OpenAI Agents SDK 都指向同一個方向。你可以開箱即得迴路、工具、情境管理、鉤子和沙盒原語，然後自定義它們。

這種轉變很重要，因為過去的預設路徑是：構建你自己的迴路，接入你自己的工具調用，處理你自己的對話狀態，設計你自己的審批流程。現在的預設路徑是：選擇一個框架，沿著四個支柱（系統提示詞、工具、情境、子代理）配置它，並將其餘精力放在領域特定的提示詞和工具設計上。

這就是為什麼「技術問題」是可解決的。你不是每次出問題時都從頭重建代理人，你在調整一個已經結構良好的配置介面。

Viv 在這方面的論述也是支持從混亂開始的最佳論據：「好的代理人構建是一個迭代練習。如果你沒有 v0.1，你就無法進行迭代。」

## 這一切通往何方

並排看看頂尖的程式碼代理人（Claude Code、Cursor、Codex、Aider、Cline），**它們彼此之間的相似程度，超過了它們底層模型之間的相似程度。** 模型各不相同。框架模式正在趨同。我不認為這是偶然的。這是業界在緩慢找到將生成模型變成能夠交付成果的東西的承重鷹架組件。

Viv 對開放問題的框架是我認為最令人興奮的：協調許多代理人並行在共享程式碼庫上工作；分析自己追蹤記錄以識別並修復框架層面失敗模式的代理人；以及能夠即時動態組裝正確工具和情境的框架，而不是在啟動時預先配置。

最後一個，尤其感覺像是**框架停止成為靜態配置，開始成為更接近編譯器的東西**的臨界點。
