## [核心摘要]

本影片指出：成本與品質並非只能二選一，多數應用其實落在**帕雷托前沿**內側，只因幾個可立即修正的設定錯誤而多花冤枉錢。解方是三個基本功：稽核提示詞（移除舊世代模型遺留的反模式）、最大化提示快取命中率、以及設計結構良好的評估讓 Claude 自主爬坡優化——同時改善成本與表現。

## [詳細重點整理]

### 1. 你可能根本不在帕雷托前沿上

成本與品質的取捨構成一條**帕雷托前沿**（Fable &gt; Opus &gt; Sonnet &gt; Haiku 由貴到便宜排列），但多數應用落在前沿內側——明明可以站上前沿，卻因小型設定錯誤而同時損失成本與表現。修正這些錯誤後，表現與成本可同時改善。

### 2. 提示詞技術債：舊反模式正在傷害新模型 [00:01:22]

提示詞像程式碼一樣累積**技術債**。幾代模型前的慣用寫法已成反模式：

- 「一步一步思考」（chain-of-thought 指令）
- 驗證儀式（「再檢查一次你的成果」）
- 強化語（booster，如「盡可能做到最周全」）
- 草稿區（scratchpad）指示

前沿模型已非常擅長判斷何時該思考、如何自我驗證，這些指令只會增加 token 消耗甚至降低表現。更關鍵的是：舊模型遇到矛盾規則會直接忽略其一（結果堪用），前沿模型反而會被矛盾規則搞糊塗。

**實作指令**：在 Claude Code 執行 `checkup prompt audit`（稽核 Claude Code 自身設定）或 `Claude API prompt audit`（稽核呼叫 API 的程式碼），兩者連到同一份技能程式碼，會自動找出並移除這些反模式。

### 3. 提示快取：嚴格的前綴比對

代理跨多輪運作時，大部分上下文逐輪重複。**提示快取**計費約為基本 token 費率的十分之一，且快得多。但快取是**嚴格前綴比對**——前綴中哪怕改動一個位元組，快取即失效。

正確的提示詞組織層級：

- 系統指令、工具 → 跨所有工作階段全域快取
- [CLAUDE.md](http://CLAUDE.md) 記憶 → 按專案快取
- 工作階段狀態 → 按工作階段
- 訊息 → 每輪遞增

在 Claude Code 執行快取診斷指令後，Anthropic 內部基準測試找到最多 **72% 的成本降低空間**，且完全不影響表現。Claude Code 團隊將提示快取命中率視為極重要的追蹤指標。

### 4. 評估設計：給 Claude 一個能爬坡的目標 

好的評估有四個特徵：模型升級時表現提升、增加思考量時表現提升、前沿仍有進步空間（未飽和）、執行間變異低。常見陷阱是評估含大量**模稜兩可案例**——看起來還有 20% 可拿，實際上無任何模型做得，結果浪費大量 token 爬坡。

**實作指令**：`Claude API build eval` 對資料來源沒有預設立場，可指向任何追蹤方案，一步步引導建立評估集、檢查評分器與評分標準。

### 5. 爬坡優化與過擬合防護

前沿 Claude 非常擅長**爬坡**——在無人參與下自主檢視評估並改進。最大風險是對評估分布**過擬合**（例如為基準測試中的 OCR 任務加入執行框架裡正式環境用不到的工具）。`Claude API hill climb` 指令採用經典的**測試／訓練集切分**：每輪只看訓練集決定修改方向，測試集與訓練集分數出現背離即是過擬合早期訊號。

實例：以 Anthropic 文件建立的 Claude API 技能評估，起點僅 66% 正確率，經爬坡迴圈讓 Claude 自主修正技能文字後大幅進步。

爬坡也可用於降成本：`hill climb` 指令可設定「表現至少持平、成本必然下降」，搜尋努力程度、模型與提示詞的組合。

## 6. Managed Agents：大腦與雙手解耦

隨任務長度從 Opus 3 的約 4 分鐘自主工作（METR 曲線）成長到如今超過一至兩天，執行框架設計考量大幅改變。Claude Managed Agents 的核心原則是**把大腦和雙手解耦**：執行框架（大腦）與沙箱（雙手）分開，工作階段日誌是獨立的、只能附加、可復原的物件——沙箱或執行框架任一方掛掉都能復原。安全性上，機密資訊存放在**保管庫（vault）**，Claude 能引用 API 金鑰但實際看不到內容。

## 7. 問答精華：努力程度與評分標準

- **努力程度（effort）** ：通則是「較強的模型 + 低努力程度」優於「較弱模型 + 高努力程度」——更聰明的模型不必費力，思考 token 更少因此更便宜。建議從 Opus 5.5 low 起測，需要時再調高。
- **評分標準設計**：避免任意量表（0-10 打分雜訊極大），偏好**二元分類**（好/壞）；多面向就用多個二元分類器。健全性檢查：跨模型測試（Sonnet、Opus、Fable 意見需一致）、重複實驗變異需低。
- **成對比較**：比較兩個成品比替單一成品打分容易得多，是處理模糊評分的有效方法。
- **對抗式取樣陷阱**：只把某個模型的失敗案例放進評估集，會產生形狀貼合該模型能力低谷的奇怪分布，模型升級後即失效。案例應從第一原理與正式環境資料判斷。
- **卡住不等於模型不行**：爬坡器連續卡住時通常是評估結構不良（評分器有問題、指令模糊），技能內建分群失敗案例、找出模稜兩可範例並改寫的備援機制。
- **情境工程**：提升可靠性的關鍵是情境物件獨立於執行框架之外（源自**遞迴語言模型 RLM** 研究）——一般訊息歷史被壓縮後內容即消失，但獨立保存的情境物件隨時可回頭查詢。
- **評估迴圈**：部署的代理產生追蹤紀錄 → 線上評估器評分 → 分數差的追蹤紀錄提升進離線評估集 → 爬坡 → 通過後放入回歸測試。

## [結論與行動建議]

**啟發金句**：與其叫不夠聰明的模型拼命思考，不如讓最聰明的模型輕鬆作答——「強模型 + 低努力程度」才是成本效能的甜蜜點。

**具體行動建議（P-C-E 法則）**：遷移到任何新模型時，依序執行三件事——**P**rompt audit（稽核並清除舊反模式）、**C**ache（最大化提示快取命中率）、**E**val + Hill climb（建評估、讓 Claude 自主爬坡同時優化表現與成本）。

**生活實踐建議**：

1. 在你的 Claude Code 專案（MCP、webhook、Actions 工作流）上立刻執行 `checkup prompt audit`，清除「一步一步思考」這類遺留指令——這對長時間跑的代理工作流省 token 效果最明顯。
2. 多輪 agent 應用（如 Gitea 自動化、排程工作流）部署前先跑快取診斷，確認提示詞按「全域 → 專案 → 工作階段 → 逐輪」層級組織，避免動態內容（如時間戳）插入前綴弄壞快取。
3. 為你的 LLM gateway 或內部工具建立小型評估集：從失敗案例取樣、用二元分類評分標準、切分測試/訓練集，再讓 `hill climb` 指令自主搜尋「強模型 + 低努力程度」的成本甜蜜點——即使評估已飽和，也能專門用來壓低成本。
