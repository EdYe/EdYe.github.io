## [核心摘要]

只靠 MCP 即時查詢無法回答跨資料集的分析型問題（如「上週有哪些客戶不高興？」），因為底層 API 不支援語意式即時查詢，且平台沒有誘因提供。解方是建構「情境圖譜」（context graph）：以同步層快取語意資料、以 MCP 處理即時查詢、用技能（skills）封裝公司流程，再透過路由器與摘要器整合，並強制保留資料來源以確保每個決策可追溯。

## [詳細重點整理]

### 1. 情境圖譜的定義與組成元件 [00:00:12]

情境圖譜指的不是圖資料結構中的節點與邊，而是「公司的大腦」。其組成包含：

- 第三方資料（NetSuite、Jira 等外部系統）
- 結構化情境（含每次必傳給 agent 的靜態文件）
- 記憶（使用過程中被要求記住或 agent 自行記住的內容）
- **技能（skills）**：情境圖譜中最關鍵的元件，代表公司專屬的流程與原則

講者背景：Merge 為連接基礎設施公司，擁有 400+ 企業客戶（OpenAI、Ramp、Netflix、Perplexity），三項產品為 Unified、Agent Handler 與 Gateway。

**關鍵概念：情境圖譜（Context Graph）= 公司大腦**

### 2. MCP 的局限：為什麼接上工具還不夠 [00:03:29]

以「客戶 A 上週為什麼不高興？」為例，agent 查 Zendesk 工單即可回答。但當問題變成「上週有哪些客戶不高興？」甚至「過去一年呢？」，agent 必須即時撈取成千上萬張工單直到逾時，根本無法回答。

核心原因有二：

- 底層 SaaS 平台的 API 存取模式不支援大規模即時語意查詢
- 平台沒有誘因提供語意端點——向量化資料要花他們的錢，且會減少你造訪平台的次數

**關鍵概念：即時查詢的逾時天花板（timeout ceiling）**

### 3. 同步層：語意查詢必須本地化 [00:04:49]

判斷準則是「查詢的複雜度」：

- 靜態、單一客戶、單一動作的查詢（如對 Stripe 查特定客戶）→ 用 MCP 即時查詢即可
- 任何語意查詢、跨大資料集的分析 → 必須將資料同步一份副本到本地向量資料庫

向量資料庫本身 AI 就能幫你建好；真正需要人類下功夫的是**策略**——資料如何存入情境層、如何取回。

**關鍵概念：同步快取層（sync/cache layer）**

### 4. 路由器與摘要器：情境的整合機制 [00:06:04]

撈回的大量情境不能直接倒回給 agent，需要兩個元件：

- **路由器（router）**：提示進來時，決定該由誰處理、送往哪裡
- **摘要器（summarizer）**：將同步情境與即時情境的資料整合成摘要，回傳給發問的 agent

**關鍵概念：情境整合管線（context assembly pipeline）**

### 5. 技能：把公司流程編碼進情境層 [00:06:31]

「取得情境」本身就是一套公司原則與流程——「客戶不高興」在不同公司有完全不同的定義：看工單數？看問卷平台 Qualtrics？工單內容是正面還是負面？

因此 agent 的正確執行順序是：

1. 先查是否有相符的**技能或記憶**
2. 技能決定該去同步層的哪裡找、該做哪些 MCP 即時查詢
3. 摘要後回傳

以「所有客戶的未結工單狀態」為例：即時查詢做不到，但本地查詢可蒐集全部客戶的工單數量、摘要後逐一給出狀態。

**關鍵概念：技能優先原則（skills-first lookup）**

### 6. 情境的四個層級 [00:08:20]


| 層級        | 特性                   | 適用場景                |
| --------- | -------------------- | ------------------- |
| 提示、技能、記憶  | 決定資料取得路徑             | 公司流程與偏好             |
| 即時 API 呼叫 | 易建置、易擴充、成本低          | 簡單查詢與取回             |
| 快取（同步）資料  | 設定較複雜、成本較高、需持續同步保持新鮮 | 語意查詢、跨資料集分析         |
| 衍生情境      | 從第三方拉資料時額外產生         | 摘要存入結構化儲存，避免重複查詢與摘要 |


**關鍵概念：衍生情境（derived context）——查詢的複利效應**

### 7. 完整查詢流程圖 [00:09:58]

1. 提示進來 → 有無相符的技能或記憶？
2. 有 → 執行技能；不需要外部資料就直接回應
3. 沒有（或技能需要外部資料）→ 進入資料選擇
4. 先查快取：資料夠新鮮嗎？在 SLA 範圍內嗎？
5. 是 → 用快取情境；否 → 呼叫即時 API
6. 循環直到情境足夠 → 把新發現存成記憶 → 產生回應

**關鍵概念：快取優先、即時備援（cache-first, live-fallback）**

### 8. 可追溯性與資料來源（Provenance）[00:11:30]

千萬不要丟掉資料來源。MCP 本身帶有來源資訊；同步進向量資料庫的資料，來源要存在 metadata 中與資料綁定。必須記錄：

- 從哪裡抓、什麼時候抓
- 用什麼 ID、什麼權限範圍（scopes）、誰存取的
- 資料有無被轉換、原始長什麼樣
- 失效條件（例如資料超過一個月就永不採用）

這不只是為了前端呈現「三個來源」的引用連結，更是為了出問題時能夠調查——因為一定會出問題。

**關鍵概念：來源繫結（provenance binding）**

### 9. 實戰範例：客戶狀態更新 [00:12:47]

查詢「給我客戶 Acme 的狀態更新，包含續約風險與最近客服互動」：

1. 快取查帳戶摘要（假設無可用技能）
2. 資料過時或不存在 → 即時 API 查 CRM
3. 查工單系統取最近互動——SLA 內用快取，否則即時拉，但只拉五張工單，因為即時查詢有逾時風險
4. 產生衍生摘要、可能存起來、回傳

### 10. 關鍵重點總結 [00:13:33]

- 工具不等於情境：情境圖譜是資料、同步的資料，以及你身為企業所擁有的流程（技能）
- 資料不是越多越好：要新鮮、高品質、只拉需要的
- 同步時要妥善結構化，讓它以正確方式被存取
- 每個答案都必須可追溯

## [結論與行動建議]

**啟發金句**：「工具不等於情境——你的公司大腦不是你接了多少工具，而是你的資料、你的流程、和你追蹤每一個答案的能力。」

**具體行動建議——S-S-P 法則**：

- **Skills**（技能優先）：先編碼公司流程，再決定資料取回路徑
- **Sync**（策略性同步）：語意查詢的資料才同步本地，簡單查詢走 MCP 即時
- **Provenance**（來源繫結）：每筆資料綁定來源、時間、權限與失效條件

**生活實踐建議**：在個人 AI 工作流（例如 Claude Code + MCP）中套用同一原則——把「我做事的方式」寫成技能檔（如專案說明、codebase 慣例），將需要反覆語意搜尋的大型文件集（如 API 文件、會議紀錄）本地索引成向量庫，而一次性查詢（查天氣、查單一筆資料）保留給即時工具；每次引用資料時養成標記來源與日期的習慣，避免 AI 用過時資訊做出錯誤決策。

所以你有提示、技能和記憶，我們談過它們會真正決定要去哪裡取得資料。你有即時 API 呼叫，這些比較容易建置、容易擴充，執行成本也比同步情境低。所以當你知道只是簡單的查詢、簡單的取回時，應該優先用它們。如果你想要語意資料、複雜查詢、針對任何資料提出深入的問題，快取資料就絕對不可或缺。但要記住，它的設定與建置稍微複雜一點，執行成本也比較高，因為你得有一個向量資料庫，還得不斷同步資料，所以比較難保持最新。

[00:09:24](https://youtu.be/cSz7aL2nl2U?t=564)
最後是我們還沒真正討論的衍生情境（derived context），基本上就是你從第三方拉資料時額外產生的任何情境。例如在我們即時拉取所有工單時，每當某位客戶的完整工單進來，我們就做摘要，並把我們拉進來的資料的摘要存進儲存情境，也就是結構化的儲存情境。這樣將來遇到常見問題時，就不必重新查詢、重新摘要一遍。

[00:10:22](https://youtu.be/cSz7aL2nl2U?t=622)
可惜事情不總是這麼簡單。如果沒有符合的技能或記憶呢？那就直接進入資料選擇。技能需要外部資料時也一樣。如果需要，我們第一件事是檢查快取，也就是同步資料庫，問：這裡的資料夠新鮮嗎？在我們的 SLA 範圍內嗎？這份資料是否新鮮到可以使用？

好，最後一部分，差不多到尾聲了：可追溯性與資料來源。一開始看起來好像不重要，但千萬不要丟掉資料的來源，一定要存下來。MCP 本身就有這些資訊；對於任何同步進向量資料庫的東西，也有所謂的中繼資料（metadata），你要把來源存在那裡，跟資料綁在一起。這非常關鍵。就像 ChatGPT 或任何你在用的介面，當它告訴你一個事實或說了什麼，最後會標示「三個來源」並附上連結。當你要根據這些資料做出攸關業務的決策時，這點更加重要：資料有版本之分、資料可能過時，你可能讓它根據一年前同步的資料做決定，你不會想要這樣。所以你必須知道資料從哪裡來：從哪裡抓的？

[00:12:16](https://youtu.be/cSz7aL2nl2U?t=736)
