## [核心摘要]

本集以麥納馬拉謬誤為引，剖析軟體團隊最常見的衡量陷阱：過度依賴容易取得與歸因的**產出指標**（output metrics，如程式碼行數、DORA、故事點數），而忽略真正驅動商業價值的**成果指標**（outcome metrics，如流失率、啟用率）。核心主張：在 AI 已能自動化「需求→程式碼」的時代，工程團隊的價值必須重新錨定在成果而非產出，否則將淪為可被取代的**功能工廠**。

## [詳細重點整理]

### 1. 麥納馬拉謬誤：量化信仰的陷阱 

Robert McNamara 於 1961 年進入美國國防部，將福特時期的數據化系統分析帶入越戰決策。他衡量後勤網路、部隊人數、控制區域等可量化項目，並據此宣稱戰事進展順利，最終卻戰敗。失敗根源在於：他衡量的只是「剛好拿得到的數據」，忽略了士氣與民心等難以量化卻更關�的因素。

- **關鍵概念：麥納馬拉謬誤（McNamara fallacy）** — 過度看重容易衡量的東西，最終僅因某些事物難以衡量而忽略它們。

### 2. 工程工具的數據陷阱 

工程師日常使用的工具天然供應大量產出數據：Jira 提供週期時間（cycle time）、燃盡速度、故事點數；GitHub 提供 pull request 數量、審查停留時間、程式碼行數。這些數據唾手可得且讓人感覺良好，因此極易讓工程主管誤把它們當作衡量團隊的預設標準。

- **關鍵概念：可得性偏誤（Availability Bias）的衡量版** — 因為指標就在工具裡，就以為它們是正確的衡量標準。

### 3. 產出指標的本質：生產線效率 

產出指標衡量「從功能定義變成可運作程式碼」的效率與品質，包括程式碼行數、DORA 指標（變更成功率、部署頻率、回滾頻率）、故事點數與 Sprint 指標。這套邏輯在製造業極為有效——福特造車前，設計早已定案且測試完成，剩下純粹是效率問題。

- **關鍵概念：確定性 vs 不確定性工作** — 遷移與平台更換專案屬於可預測工作（適用產出指標），但多數產品開發充滿未知，無法事先確定打造的東西能帶來商業成果。

### 4. 成果指標：連結商業價值

成果指標源自希望從產品獲得的商業價值，包含 SaaS 指標（流失率、營收、淨營收留存率）與產品指標（採用率、NPS、顧客回饋、功能使用率、啟用率）。產出與成果兩者衡量方式截然不同——你無法靠程式碼行數衡量流失率，兩者各司其職、缺一不可。

- **關鍵概念：成果指標的歸因難題** — 啟用率上升可能是客戶賦能、產品設計或工程團隊任一方之功，難以拆解；產出指標卻可輕易細分至五、六人團隊層級進行比較。但「難以歸因」絕非「不該衡量」的理由。

### 5. 實例對照：兩個團隊、兩種命運 

兩個團隊同時執行為期約兩週的專案：一隊負責 React 從 class-based 元件遷移至 hooks，另一隊負責重新設計 UI 導覽。遷移團隊估算精準、DORA 指標乾淨漂亮、目標明確可驗證，順利結案。導覽團隊準時交付所有被要求的工作，使用者卻強烈反感——改動人們已建立肌肉記憶的導覽，初期必然引發負面成果。導覽團隊被迫再跑一輪迭代修正。

- **關鍵概念：功能工廠（Feature Factory）** — 團隊存在的唯一目的，是把需求變成可運作的程式碼；只慶祝效率，就不會慶祝真正對業務重要的改變。

### 6. AI 時代的功能工廠警訊

AI 已能極有效率地把需求轉為程式碼。若工程團隊的價值被定義為「程式碼通過工廠流水線的能力」，當機器人進駐流水線時，主管的第一個問題就會是「我為什麼還需要這個團隊」。許多工程師的職業焦慮正源於此。解方是將團隊重新定位為「產品與工程結合、朝成果前進」的單位。

- **關鍵概念：價值錨點轉移** — 把團隊的問責目標從「完成速度」改為「使用者能多容易找到新導覽」，並給予足夠時間直到出現有意義的改善訊號；團隊反而會因更頻繁迭代與實驗而自然加速。

### 7. 衡量的時機與指標時序

成果衡量必須在動工之前就設計好，因為產出指標本來就在工具裡，而成果指標需要前期投入思考：「我們要怎麼衡量這個專案的成功？」且衡量只有在能改變決策時才有意義——從第一天就開始衡量，才能依據數據反應，而非事後回顧。

- **關鍵概念：領先指標 vs 落後指標** — 成果指標（使用者回饋、NPS）通常是落後指標，須上線且使用者充分使用後才浮現，應設法在週期中更早拉取使用者回饋；產出指標則是每日可得的領先指標。理想狀態是每天都能回答「今天我們距離成果還有多遠」。

### 8. 終極問題

所有成果指標最終都在回答一個問題：**產品有沒有變得更好？** 無法單憑衡量改動產品的效率來判斷此事，必須建立衡量產品實際改善程度的機制。

## [技術/數據對比]


| 維度   | 產出指標（Output Metrics）           | 成果指標（Outcome Metrics）       |
| ---- | ------------------------------ | --------------------------- |
| 衡量對象 | 需求 → 可運作程式碼的效率與品質              | 產品帶來的商業與用戶價值                |
| 典型範例 | 程式碼行數、DORA、故事點數、週期時間、Sprint 速度 | 流失率、營收、淨營收留存率、啟用率、NPS、功能使用率 |
| 取得難度 | 低——內建於 Jira / GitHub 等既有工具     | 高——需在動工前刻意設計衡量方式            |
| 歸因難度 | 低——可拆解至個別五、六人團隊層級比較            | 高——多團隊共同貢獻，難以歸因至單一單位        |
| 指標時序 | 領先指標，每日可得                      | 落後指標，需上線後才反映變化              |
| 適用情境 | 遷移、平台更換等可預測工作                  | 充滿未知的多數產品開發                 |
| 風險   | 淪為功能工廠、慶祝錯誤的事                  | 因難衡量而被忽略（麥納馬拉謬誤）            |


## [結論與行動建議]

**啟發金句**

> 產出指標告訴你打造東西的效率有多高，卻完全無法告訴你，那是不是該打造的東西。

**具體行動建議：「先問後做」法則（Ask-Before-Build）**

在每個專案動工前，先完成三個提問：

1. 這個專案的**成果**是什麼（用什麼指標衡量）？
2. 我們**何時**、如何蒐集使用者回饋，把落後指標往前拉？
3. 團隊被問責的是**成果**還是交付速度？

若無法回答第 1 題，先別動工。

**生活實踐建議**

- **AI 開發工作**：使用 Claude Code 或 LLM 產出程式碼時，別用「生成速度」或「程式碼量」評估 AI 協作的價值，改問「這個功能上線後，目標使用者的啟用率/留存有沒有提升」——這也是抵抗功能工廠化焦慮的根本方式。
- **YouTube 內容創作**：影片產量與上架頻率是產出指標；觀眾留存率、訂閱轉換、留言互動才是成果指標。別因為前者容易追蹤（就在 Studio 儀表板上）就用衝片數當目標。
- **產品管理**：為每個功能在 PRD 階段就定義「成功指標」欄位，並在 Sprint 中安排早期可用性測試，把使用者回饋從落後指標轉為週期內可得的訊號。

個別團隊的層級，非常有效。你可以看一組五、六位工程師，把他們的 sprint 指標拿來和另一個團隊比較，然後判斷這個團隊需要一點幫助，或是這個團隊也許可以支援另一個團隊。用成果指標就難多了。如果顧客回饋說「我們覺得這個功能很難用」，你很難把這件事歸到團隊裡的某一個區塊，然後說：「好，這功能很難用，我們去那邊調整一下就好。」

所以這非常困難，成果指標也很難歸因。但再說一次，不要掉進麥納馬拉謬誤，以為它們難以衡量、難以歸因就不該衡量，你絕對應該衡量。這兩種指標都很重要，你需要把兩者放在一起看。產品工程的本質，就是結合產出指標與成果指標，讓你仍然擁有一個有效率的系統。衡量你推出產品的效率依然重要，但你也必須結合另一個問題：我們在產品上達成想要的成果，做得有多好？

[00:08:48](https://youtu.be/7BThiYwCV6g?t=528)
我舉個親身經歷的例子。我曾經管理兩個工程團隊，他們在做兩個非常不同的專案。其中一個團隊在做框架升級，如果我沒記錯，他們在升級 React 的版本。如果你對 React 有些了解，就知道以前建立 React 元件有一種舊寫法，是用類別（class-based）語法來寫元件。

[00:09:12](https://youtu.be/7BThiYwCV6g?t=552)
他們要把整個程式碼庫遷移成使用 hooks。這是一個龐大的遷移專案，花了他們大約一到兩個 sprint。我還有另一個工程團隊，負責修改使用者介面裡的導覽。所以這兩個團隊手上的工作都大約要兩週，而且兩隊都交付得相當不錯。負責 React 版本遷移的團隊，估算得相當準確，我可以追蹤 pull request 進來的效率、重構了多少、改了多少程式碼，也能追蹤這次遷移引發了多少 bug。所以這個團隊的 DORA 指標很容易追蹤，雖然不是每項都完美，但很容易追蹤。

[00:09:54](https://youtu.be/7BThiYwCV6g?t=594)
另一方面，負責修改導覽的團隊，我同樣掌握他們所有的產出指標，看得到他們有在做事。但結果是，我們把導覽的改動上線後，使用者恨透了它，引發了一大群人的反感。每當你改動人們已經養成肌肉記憶的導覽時，至少在一開始，你可能會得到負面的產品成果。所以負責導覽的團隊，雖然準時交付了專案，卻得到了負面的產品成果。這種情況很難讓人釋懷，因為我們原本想要慶祝兩個團隊的成功。做遷移專案的那個團隊，要慶祝他們的成功非常容易：我們知道目標是什麼，我們達成了，測試過了，

[00:10:39](https://youtu.be/7BThiYwCV6g?t=639)
它可以運作。恭喜，遷移完成了，你們可以去做別的事了。而負責導覽的團隊，他們做了所有被要求的事，但大家很討厭它。所以他們沒辦法去做別的事，必須再跑一輪，迭代導覽、修正一堆東西，因為大家不喜歡。這之所以困難，是因為說到底，其中一個團隊在成果上完全做到了該做的事，另一個卻沒有。另一個團隊雖然完全照著要求去做，卻沒有推動正確的成果：他們本來想讓導覽更好用，結果卻讓很多人覺得更難用。所以，單憑他們交付工作的效率來衡量這兩個團隊、慶祝他們的成功，是不對的。

[00:11:27](https://youtu.be/7BThiYwCV6g?t=687)
這就是所有交付指標或產出指標的關鍵：它們告訴你打造東西的效率有多高，卻完全無法告訴你，那是不是該打造的東西。所以如果你只慶祝效率，就不會去慶祝那些對業務真正重要的改變。這就是功能工廠（feature factory）形成的原因。我前面說過，產品工程不像在福特工廠造車。

[00:11:51](https://youtu.be/7BThiYwCV6g?t=711)
說到底，這一點千真萬確。你不能把團隊當成生產線，否則最後就會慶祝錯的事情。你會慶祝一條生產線超級有效率，下午五點前就把所有車造好，大家都能開開心心回家。你不能這樣對待團隊。如果你這麼做，就會落入功能工廠模式：你的團隊存在的唯一目的，就是把需求變成可運作的程式碼。尤其在 AI 的時代，AI 現在可以極有效率地把需求變成可運作的程式碼。所以如果你評判工程團隊的標準，是他們把需求轉成程式碼的能力，那麼當 AI 出現時，你可能會想：「我到底為什麼還需要這個工程團隊？」現在很多軟體工程師正為這件事非常焦慮，因為他們把自己

[00:12:37](https://youtu.be/7BThiYwCV6g?t=757)
全部的價值，都綁在讓程式碼通過工廠流水線的能力上。而這座工廠現在已經自動化了，機器人進駐，開始做那些個別的工序。所以現在比以往任何時候都更重要的是，改變我們慶祝成功與衡量工程團隊的模式，不再把他們當成功能工廠，而是當成產品與工程結合、朝成果前進的團隊，並根據我們要求他們達成的成果來評判他們。我對那個負責導覽的團隊犯的錯誤，是要他們為完成專案的速度負責，但我應該要他們為使用者能多容易找到新導覽負責，那才是該讓他們負責的正確目標。我應該給他們盡可能多的時間，直到我們看到

[00:13:23](https://youtu.be/7BThiYwCV6g?t=803)
他們確實有意義地改善了產品的訊號。就算花了三倍的時間，基本上也沒關係。因為如果你對團隊說：「你們可以多花一點時間，只要達成那個成果就好。」他們自然會設法加快腳步，因為他們會更常迭代、做更多實驗，在投入太多時間之前先試著多了解一些。因為你已經告訴他們：「我不是用你們的週期時間或寫了多少行程式碼來衡量你們，我衡量的是大家什麼時候覺得這東西更好用。」

[00:13:57](https://youtu.be/7BThiYwCV6g?t=837)
這就帶到我關於衡量的下一個重點。當你在衡量成果時，非常重要的是在開始動工之前，就先想清楚要怎麼衡量。產出相對容易，因為你知道你早就有工具可以衡量週期時間或 pull request 吞吐量之類的東西，所以不需要另外決定，你知道那些指標就在那裡。但成果不同，你必須在投入時間之前就先決定：我們要怎麼衡量這個成果？

[00:14:24](https://youtu.be/7BThiYwCV6g?t=864)
因為成果比較難衡量。再說一次，比較難衡量不代表可以忽略，只是需要多花一點心思，需要在前期多花一些時間想清楚：我們要怎麼衡量這個專案的成功？要怎麼衡量這個功能的影響？然後在團隊開始動工時，你就可以把這些衡量帶進來，試著讓團隊更早、更快地迭代，提高他們達成成果的機會。畢竟，衡量只有在能夠改變決策時才真正有意義。

[00:14:55](https://youtu.be/7BThiYwCV6g?t=895)
如果你想回頭對某項工作做回顧，事後衡量也還可以，但你真正想要的是從第一天就開始衡量，因為如果你沒有在整個過程中持續衡量，就無法根據這些數據做出反應。而成果指標往往是落後指標（lagging indicators），變化常常要過很久才會反映在成果指標上，尤其是使用者回饋或淨推薦值調查之類的東西。使用者回饋要等你上線、使用者有足夠時間把玩你做的東西之後才會出現。所以它們是落後指標，或者說可能是落後指標。因此更重要的是把這些落後指標往前拉，在週期中更早取得一些使用者回饋。

[00:15:41](https://youtu.be/7BThiYwCV6g?t=941)
產出指標則通常是領先指標（leading indicators），你每天都能知道當天交付了多少程式碼。你需要設法做到每天都能知道：今天我們距離成果還有多遠？我想用一個問題來結束這一集，這是你應該拿來問你的工程團隊、你的產品與工程團隊的問題，那就是：產品有沒有變得更好？因為大多數成果指標都在試圖回答這個問題。我們都想打造出色的產品，也都希望這些出色的產品被很多人使用，讓他們留下來持續使用，並可能進一步帶動營收。為了做到這一點，產品必須持續變得更好。而你無法單憑衡量改動產品的效率來判斷這件事，你還必須能夠

[00:16:27](https://youtu.be/7BThiYwCV6g?t=987)
衡量產品實際上改善了多少。所以問問自己：你有衡量成果的方法嗎？如果沒有，你可以做些什麼？可以建立哪些機制，幫助你衡量所推出工作的影響？我就把這個問題留給你。希望你到目前為止都喜歡這個 Podcast。前幾集都是我的單人節目，讓我先抓到一點節奏，但未來我們會邀請來賓，一起探討其他人的觀點。所以請繼續收聽。
