# How Anthropic builds software in 2026 with Katelyn Lesse 

## [核心摘要]

Anthropic 平台工程負責人 Katelyn Lesse 揭露 2026 年內部開發實況：一支小團隊以代理驅動的「大躍進式」遷移，在五、六個月內將核心 API 層從 Python 單體改寫成 Rust，靠影子流量與可驗證性取代逐行程式碼審查；招募上逐步淘汰程式面試、PM 可直接推送正式環境，工程師的角色從「寫程式」位移到「定義可驗證的意圖 + 跨團隊協調 + 提高野心」。

## [詳細重點整理]

### 1. Claude 平台架構總覽

請求路徑為：驗證服務（authn/authz）→ 核心 API 服務（多區域、多雲 CPU 叢集，執行 tokenization、計費、安全檢查）→ GPU/TPU 推論層。所有自家人員應用（Claude Code、Desktop）都跑在與外部客戶相同的 Messages API 之上；且 API 允許請求開啟長達約一小時，屬於無狀態、每回合都得回傳整個對話狀態的特殊形態。  
**關鍵概念：吃自己的狗糧**——內部應用與外部客戶共用同一套 API 基礎設施。

### 2. Python CPU 危機與超級盃事件

原 API 是只跑在單一 GCP 區域的 Python 單體（當年因研究團隊生態系全是 Python 而順勢選擇）。超級盃廣告帶來流量暴增，CPU 叢集吃緊；首次出現「想向雲端業者要更多 CPU，卻拿不到」的困境——水平擴展不再是無限的。團隊先做了經典緩解（跨區域分流），但區域間網路頻寬成為新瓶頸。  
**關鍵概念：CPU 稀缺性**——運算資源從「付錢即得」變成談判籌碼。

### 3. 為何選 Rust，而非 Go / C++ 

前期新服務已選 Go（效率與開發者體驗的良好平衡點）。最終走向 Rust 的決定性因素：模型已強到「團隊沒人寫過大量 Rust 也無妨」，實作細節可交給模型。Rust 同時提供 C++ 級效能、記憶體安全，且編譯期檢查多——手寫時令人挫折的借用檢查器，在代理迭代的世界裡反而成為信任的來源。  
**關鍵概念：代理友善語言**——語言選擇的權重從「人的開發體驗」轉向「機器的可驗證性」。

### 4. 大躍進式遷移與影子流量驗證

一位新加入的資深工程師提出「great leap style」：不做逐塊遷移，直接 fork 整個程式碼庫用 Rust 重寫一遍，前面保留極薄的 Python 前門，將同一請求同時送進兩個系統跑影子流量。驗證策略：比對進入推論層前的請求狀態，以及回傳的 token 數量；因隱私限制無法看使用者內容，只能逐日壓低 Python/Rust 輸出差異百分比直到趨近零。期間保留 Python 前門作為退路，直到信心足夠才拆除。中途一度有 beta 功能在 Rust 團隊不知情下於 Python 側 GA，造成影子流量大量報錯——之後加入 linting 與靜態分析，強制周邊團隊在兩邊同步開發。  
**關鍵概念：影子流量驅動開發（Shadow-Traffic-Driven Migration）**——在不看資料內容的前提下，用可觀測的輸出指標對賭新舊系統。

### 5. 程式碼即文件，新人上手就是問 Claude

舊 Python 系統沒有完善文件，也無法「照文件重建」。現在新人第一步是問 Claude「這個系統怎麼運作」，Claude 透過接在所有內部系統上的 MCP server 搜尋程式碼庫、可觀測性資料、事後檢討報告，產出互動式、可點擊深掘的系統說明，取代白板方塊箭頭與過時投影片。  
**關鍵概念：程式碼即文件**——文件不再是維護負債，而是隨程式碼即時衍生的視圖。

### 6. Claude Managed Agents：綠地專案的第一原則重造 

最初做法（API 請求 → 產生沙箱 → 在沙箱內啟動 Claude Code）有四大問題：可靠性（沙箱掛了代理跟著掛）、延遲（等沙箱冷啟動才拿到 token）、安全性（憑證必須放進沙箱）、CPU（每個代理至少佔一顆 CPU）。團隊決定整個丟掉、從第一原則重建：harness 跑在持久伺服器上、只在需要時產生沙箱、獨立工作階段儲存、憑證存放於保險庫並由出口端 proxy 即時注入——憑證永不進沙箱。新架構平均只用原系統約三分之一的 CPU， Messages API 之上僅增加極小延遲。  
**關鍵概念：憑證出口注入**——安全邊界從「沙箱內」移到「出口端」。

### 7. 代理化開發流程與分類器 code review 

工作單位從單一 pull request 拉高到整個專案：與 Claude 發想規劃 → 派出代理（代理再自行調度其他代理）→ 過程中有大量環節人類不再參與。機械化變更（如 SDK 升版）由 Claude 開 PR、另一個 Claude 分類器審查，判定是否需要人類，不需要則直接合併部署；CI 變紅時也有代理自動修復 flaky test。人類剩餘的主要工作：跨團隊協調、對齊目標、處理分類器判定的高風險變更。  
**關鍵概念：變更分類器**——code review 的強制人審制度被「風險分類 + 條件人審」取代。

### 8. AI 先行 on-call 與 PM 推正式環境

告警先送給與值班工程師 shadowing 的 Claude：判斷雜訊或真實問題，雜訊直接吞掉不吵醒人類；真實問題則邊升級給人類、邊自行診斷並提出修復，人類到位時往往只需核准。產品經理也直接建造並推送正式環境功能（開發者控制台的提示快取診斷儀表板，含 cache miss 原因 API），品質足夠高；系統出問題時，負責 on-call 的仍是擁有該系統的工程團隊。  
**關鍵概念：告警第一道關卡**——人類從第一 responder 退居為核准者。

### 9. 軟體工廠與加速團隊 

Anthropic 內部不用「軟體工廠」一詞，但精神正是如此：代理做變更、代理驗證、代理做第一輪 review、代理部署、QA 代理持續在背景對系統反覆測試並開修復 PR。工具來源分三層：中央基礎設施的開發者加速團隊（打造新版控系統 Scion）、平台加速團隊（QA 代理、CI 修復代理）、以及任何工程師自己動手解決煩人瓶頸。後設工作（meta work）佔比反而上升。  
**關鍵概念：加速團隊**——開發者平台的 AI 時代進化形態。

### 10. 招募變革：逐步淘汰程式面試

越來越多候選人在其他每一關都表現亮眼，唯獨程式面試失利——因為他們已不整天手寫程式。現正實驗多種代理驅動的面試形式：審查代理寫的程式碼、審查代理的系統設計、用 coding 代理建置東西，目標是取得「與代理協作完成工作」的訊號；但尚未定案，因為面試還需兼顧可評分性、抗偏見與可規模化。  
**關鍵概念：代理協作能力面試**——面試訊號從「會不會寫」轉向「會不會指揮與審判」。

### 11. 職級衡量與身分認同危機 

職級、晉升、績效評估仍存在，但「工作耗時 = 複雜度」的代理指標失效：原本兩年的遷移現在五、六個月完成，複雜度門檻必須重新校準，最終底線仍是影響力（省下多少 CPU、延遲改善、跨團隊協調的廣度）。對於感到身分危機的工程師：若喜悅來自「解決有野心的問題」，未解的問題只會更多；要讓代理治癒疾病、接管盡職調查流程，安全、驗證（auth）、基礎設施等底層工程問題必須先被解決——深厚專業比以往更重要。  
**關鍵概念：野心重新定義職涯**——從產出程式碼的量，轉向所能指揮的問題規模。


## [結論與行動建議]

**啟發金句**：「在一個充滿非確定性的世界裡，只要你能讓東西可驗證，你就處於非常、非常好的位置。」

**具體行動建議 — A-V-A 法則**：

- **Ambition（野心）**：把目標單位從「一個 PR」拉高到「一個專案」，敢於整個丟掉重造；
- **Verification（驗證）**：與其逐行讀代理寫的程式碼，先把工作化簡成可比對、可量測的驗證訊號（影子流量、token 數、編譯期檢查）；
- **Ambient agents（常駐代理）**：讓代理接管機械化變更、CI 修復、雜訊告警與 QA，人類只留下協調與高風險判斷。

**生活實踐建議**：套用到個人或小團隊的開發流程——(1) 為任何遷移或重構先建立「影子比對」機制（同一輸入跑新舊兩版、比對輸出），用數據差異百分比而非肉眼審查建立信任；(2) 把內部系統（儲存庫、工單、監控）透過 MCP 串接給 Claude Code，讓「問代理」成為唯一的上手文件；(3) 列出每週最耗時的三件機械化工作，各配一個常駐代理處理；(4) 不必為單一問題學新技術，但值得往資安、驗證這類「隨代理規模化而變複雜」的領域深耕，做那個能預見轉角之後問題的人。

此外，Rust 能讓服務達到極致效能，和移植成 C++ 或 C 的水準相當，同時 Rust 還提供記憶體安全，以及給代理用的驗證回饋層，所以整體而言對代理友善得多。另一個有趣的部分，是確認了 Anthropic 現在已經完全放棄演算法程式面試，這感覺像是一個重大里程碑，因為他們是第一家公開證實這麼做的大公司。

[01:49:02](https://youtu.be/9oNvKMd7xJo?t=6542)
Katelyn 說，他們發現有更多候選人在其他每一場面試都表現很好，卻在資料結構與演算法那一場失利，因為他們已經不再親手寫程式了。雖然 Anthropic 放棄了這種面試，但他們還沒有完美的替代方案，正在嘗試圍繞程式代理與代理式寫程式設計的不同面試。我的看法是，多數公司最終都會放棄程式面試，但代價是招聘流程會變得主觀得多。

[01:49:24](https://youtu.be/9oNvKMd7xJo?t=6564)
面試流程會變得越來越像過去工程經理或產品經理的招聘流程，帶有很高的主觀性。另一個稍微令人意外的收穫是，Anthropic 的產品經理（PM）曾把程式碼推上正式環境。我為此四處打聽過，因為在多數公司，把程式碼推上正式環境仍是工程師的職責。話說回來，Anthropic 的 PM 技術能力很強，常常是工程背景出身，所以我很好奇，PM 推正式環境程式碼是否會像在 Anthropic 那樣普遍。我有點懷疑，但值得留意這在 Anthropic 內部是如何發生的。另外別忘了，這些變更的待命（on call）人員仍然是軟體工程師。還有一點很有趣，就是 Anthropic 內部的新人上手流程改變了多少，上手指南基本上就是「問 Claude」。

[01:50:04](https://youtu.be/9oNvKMd7xJo?t=6604)
OpenAI 的 Tido 也說過同樣的話，我們在談 OpenAI 用 Codex 做新人上手時聽到的。一個非常重要的細節是，Anthropic 和 OpenAI 都幾乎把所有系統接入自家內部的 Claude／Codex 實例，因此那些 AI 代理擁有的脈絡，比其他公司內部的多數代理多得多。話說回來，這也可能是另一個理由，讓你把內部系統連接到公司內部的代理。只要確保你沒有把公司的智慧財產洩漏給 AI 供應商。也請查看下方節目說明中，關於工程文化與 AI 工程主題的相關深度報導。
