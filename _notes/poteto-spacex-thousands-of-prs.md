# 🎬 影片重點筆記：Poteto 談如何在 SpaceX 每月交付數千個 PR

---

## [核心摘要]

本片的核心貢獻是提出一套可落地的「**大規模 Agent 協作工程方法論**」：以驗證（Verification）建立信任、以確定性腳本（CLI/codemod）分擔機械工作、以環境護欄（lint 規則、慣例式架構）讓錯誤不可能發生，再透過「外圈＋內圈」自動觸發機制與協調者 Agent，實現每月 2,500 個 PR 的交付規模。它解決的痛點是：開發者淪為 Agent 的微觀管理者與「肉身仲介」，無法真正規模化。

---

## [詳細重點整理]

### 1. 從微觀管理到信任階梯 [00:00]

來賓 Poteto（pstack 作者）因一場「上月交付 2,500 個 PR 至正式環境」的演講在 X 上爆紅（約 300 萬觀看）。本集以該演講的 Q&amp;A 形式展開，核心框架是**信任階梯**：對 Agent 的信任越高，就能委派越複雜的任務、擴大到越多的 Agent。

**關鍵概念：信任階梯**

### 2. 旅程起點：Meta → 副專案 → Cursor [01:58]

離開 Meta React 團隊後的休假期間，用 AI 寫 side project 時驚覺自己整天在**微觀管理單一 Agent**。當時（一月～二月）社群著迷於「編排」概念，人人都在做自訂編排器。這段經驗成了 pstack 的基礎，早期技能仍在 GitHub 開源專案 "potato noodle" 中，其中的 brain 目錄記錄了「如何把自己的能力萃取給 Agent」的早期實驗。三月加入 Cursor 後負責卡頓嚴重的 agents 視窗，整天看火焰圖與堆積快照做效能調校——卻再度發現自己是瓶頸，淪為 Agent 與 Chrome DevTools 之間的「**肉身代理人**」。

**關鍵概念：肉身代理人（Meat Proxy）**

### 3. 領域專業比以往更重要 [06:22]

模型越強，瓶頸不再是 Agent 本身，而是你能否清楚表達意圖與目標。醫生、律師等非工程領域的專家，只要略懂技術並摸索出 Agent 用法，腦中有清晰願景就能打造出色的產品。

**關鍵概念：意圖表達瓶頸**

### 4. 語言即程式：單一詞彙壓縮大量意圖 [08:23]

自然語言與程式語言在 Agent 時代交會。找到一個讓 Agent 緊抓不放的關鍵詞（如 **tautological tests／同義反覆測試**），能將大量意圖壓縮進一個字，讓 Agent 在思考軌跡中反覆強化它。TDD 的價值也在於此：讓 Agent 用不同方式排定優先順序，而非形式本身。

**關鍵概念：語意壓縮**

### 5. 米其林廚房：比軟體工廠更好的比喻 [10:47]

「軟體工廠」讓人聯想到缺乏品質與工藝，故改用**米其林廚房**。家庭廚師是「一人樂隊」；隨著加入副主廚，分工必須讓整體大於部分總和。主廚＝廚房的 Tech Lead／CEO，不煮菜而是統籌訂料、儲存、備料時程——工程師的新角色正是如此：不寫程式碼，但為最終成果與聲譽負責。技能、環境、程式碼庫就是新時代的食材。

**關鍵概念：米其林廚房**

### 6. 驗證：工具箱中最重要的技能 [15:16]

驗證＝替 Agent 裝上「**手和眼睛**」：自己執行程式碼、像真人一樣互動、擷取 trace 與快照。Agent 看不到自己的成果就無法迭代——這正是「迴圈」成立的最關鍵條件，也把你從流程中移除。第一個應用案例是 Cursor agents 視窗的**爬山法**效能優化：有了評分機制＋迴圈，Agent 能持續自我改進。如今 Cursor／SpaceX AI 的每個應用程式都有一個自動維護的驗證技能，成為團隊關鍵基礎設施。

**關鍵概念：驗證迴圈**

### 7. 客製 CLI：確定性與判斷的光譜 [19:28]

Agent＋技能是一道光譜：一端是完全依賴判斷的工作，另一端是機械化的確定性轉換。把確定性部分（如 Playwright／Chrome DevTools Protocol 的膠水程式碼）編碼成 CLI 放進技能中，好處有三：節省上下文視窗、避免每個 Agent 重新發明輪子、成果可被所有後續 Agent 重複利用。遷移同理：codemod 走訪 AST 做機械轉換，交給腳本而非 Agent。

**關鍵概念：確定性／判斷光譜**

### 8. 環境經營：工程師的新工作 [24:52]

不花時間建立信任、打造技能與工具，就會卡在信任階梯最底層，只能全程微管理——如同從沒磨利刀具的廚師陷入惡性循環。內部框架 **Dune**（非開源，類比 Electron 內的 Next.js）透過嚴格 lint 規則＋慣例式目錄結構，讓每件事「只有一種做法」，很難寫出爛程式碼。Grockbot 早期由約八個一萬行以上的上帝檔案組成，被迫拆分成功能目錄。觀察 Agent 在哪裡失敗，將錯誤轉成 lint 規則，讓問題在環境中**不可能發生**。

**關鍵概念：慣例優於配置的護欄設計**

### 9. 2,500 個 PR 的機制：外圈與內圈 [32:42]

規模化的前提是環境已建好（開連鎖餐廳，主廚搭直升機巡視各店）。核心是**外圈／內圈**分離與連結：

- **外圈**：Grogbots 等個人代理訂閱 Slack、X、Email、Linear，持續監看（如「留意 Grockbot 桌面版 bug，發現就送進 Cursor 專案」），把外部脈絡自動拉入。
- **內圈**：Cursor「專案」＝雲端協調者 Agent，自帶電腦、管理任務清單、派生子 Agent，可自行選擇拓撲最有效率地分派。

Netflix 的「給脈絡，而不是控制」原則在 Agent 世界同樣適用。一次湧入 30 個相關議題時，交給單一協調者比一個任務一個 Agent 更好——多份 bug 回報放在一起反而能看清問題其實在更上層。

**關鍵概念：外圈／內圈**

### 10. 園藝與佇列：模式識別勝於逐項修復 [45:51]

2,500 個 PR 大多是**園藝式整理**而非新功能。一個 Agent 持續掃描 React 不良模式，但先不修，而是把發現**附加到文件形成佇列**，每隔幾天由人檢視——因為發現的其實都是同一件事。純執行模式會錯過大局；緩衝區迫使你辨識模式，避免多個子 Agent 重複修同一個根因。

**關鍵概念：園藝式整理**

### 11. 審查：抽樣而非把關 [49:27]

規模化後不可能每個 PR 都親自審。改為每天抽樣 PR 品質、嚴格檢視 Agent 的無效率之處，然後**修正環境而非糾正單一 Agent**。多個 Agent 走同樣捷徑、複製同樣變通做法，才是該調整技能、lint、型別系統的訊號。

**關鍵概念：抽樣式品管**

### 12. 黑燈工廠：全自動駕駛與事後審查 [51:55]

pstack 的「**全自動駕駛**」為每個 PR 產生一批驗證 Agent 並進行**模糊測試**——真的執行應用程式、四處點擊、像真人一樣使用、尋找回歸問題，自己修好再重複，直到可合併。耗費大量 token（可調整數量），但「驗證＋環境」的結合讓 Agent 能在 PR 合併後才被人審查。目前相當於 10 位以上幕僚長（chief of staff）分掌效能、修 bug、實驗性重寫等領域，24 小時運作，人類睡覺時 Agent 自行合併程式碼。

**關鍵概念：黑燈工廠**

### 13. 單向門與可驗證性 [55:29]

雙向門 PR（可 revert）可放手；單向門（資料遺失等）的解法是**領域可驗證性**：若工作成果能被嚴格驗證，單向門某種意義上就變成雙向門。數學證明與形式化驗證（Lean、TLA+）是範例；未來預測是出現更多 Agent 導向的新語言，如 **Bend**——把寫程式與證明結合在同一語言中，能編譯＋證明正確就沒理由不合併。

**關鍵概念：可驗證性**

### 14. 技能即流程：pstack 與其他技能互補 [59:42]

技能本質就是語言、就是 Markdown，彼此高度相容。實踐法：回頭挖掘**過去的對話紀錄**——找出你糾正 Agent、必須介入的地方，轉成 lint 規則或新技能。過去的對話是「情境的寶庫」，因為它是流程的具體化，而非腦中抽象想法。pstack 的 **recall** 技能即源於此（Cursor 虛擬化 bug 修復時，把上個對話的好脈絡帶到新對話）。趨勢：模型越強，技能越精簡——刪掉實作細節，專注編碼工作流程本身。

**關鍵概念：recall／對話即流程檔案**

## [結論與行動建議]

### 啟發金句

> 「讓『最容易的事』就是『正確的事』——模型永遠傾向走捷徑，你的工作是把捷徑鋪成正確的路。」

### 具體行動建議：T-V-E 法則

- **T**rust（信任）：用驗證技能給 Agent 手和眼睛，爬上信任階梯
- **V**erify（驗證）：每個 PR 觸發驗證迴圈＋模糊測試，做到事後審查
- **E**nvironment（環境）：把 Agent 的每次失敗轉成 lint 規則與慣例，讓錯誤不可能發生

### 生活實踐建議

- 每天花 15 分鐘「園藝」：掃描自己工作流程中的不良模式，累積到佇列再批次處理，而非逐項救火
- 對任何重複做的任務自問：「這是判斷性還是確定性？」確定性的部分今天就腳本化
- 翻閱過去與 AI 的對話紀錄，找出自己反覆糾正之處——那是提煉個人技能與自動化規則的寶庫
