## [核心摘要]

AI coding agent 已讓「寫程式」近乎免費，但瓶頸並未消失，只是不斷後移：先卡在 code review，接著將移向維運與資安。Laurie Voss（npm 共同創辦人、Arize AI 開發者關係負責人）論證：agent 無法取代的最終瓶頸，是「找出人們真正要什麼」與「定義什麼叫做好」。他將這個倖存的職位命名為**產品工程師（Product Engineer）**——懂使用者、會寫 spec、讓 agent 負責打字的人 。

## [詳細重點整理]

1. 超越 AI 工程師 [00:00]

Swyx 三年前提出「AI 工程師的崛起」，主張打造 AI 產品需要的是工程師而非研究員。但真正的變革不只發生在 AI 工程師身上——**所有**工程師職位都正在被一種新職位取代，而這不是所有人都樂見的消息。核心驅動力：agent 讓寫程式的成本崩塌至近乎零，但寫完程式之後的所有環節（review、部署、維運）並未同步變快，瓶頸因此移轉 。

關鍵概念：**AI 工程師**（AI Engineer）此一框架已不足以描述正在發生的全面性職位重組。

2. 程式碼免費化，瓶頸移轉至 Code Review [01:19]

- 啟用自主 coding agent 的開發者，產出**多出 741%（約 8 倍）的程式碼**，但交付速度只提升 **30%**。8 倍的產出只換來 1.3 倍的速度，代表卡住了。
- 卡住的地方是 code review：根據 Cisco 二十年前的經典研究，人類審查程式碼的能力在**每小時約 450 行**後急劇下降。一個 10,000 行的 diff 需要約一週才能合理審完——而現在沒有人真的這樣做。
- 核心矛盾：**產出「看似合理」程式碼的成本已崩塌，但判斷「是否可信賴」的成本完全不變** 。

關鍵概念：**審查成本不對稱**（cost asymmetry between producing and trusting code）。

3. 機器審查的現況與失敗案例 

- GitHub Copilot 上月已完成 GitHub 上超過五分之一（&gt;1/5）的 code review，甚至可授權其作為上線前的最終核准者；OpenAI 內部人類審 PR 是「可選」而非必須。
- 但機器審查者還不夠好：一份研究讓**四個 AI reviewer** 各自跑分，它們都找到了真實 bug，但**沒有在任何一個 bug 上彼此同意**——代表要認真用就不能只跑一個。
- 跳過審查的下場：Dexter Horty 花六個月倡導「不讀程式碼」，最後承認錯誤、被迫整組重寫系統；Amazon 因 coding agent 產出的「slop」造成一連線服務中斷，事後檢討規定**資深工程師必須簽核 code review**；Anthropic 也公布過同時騙過人類與機器審查者的 bug 事後報告。
- 基準測試落差：模型在標準 coding benchmark 的 pass rate 約 87%，但 Cognition（Devin 開發商）改問「身為 repo 維護者，你會 merge 這個 PR 嗎？」，pass rate 立即跌到 **54%**。因為 merge 的判斷包含 code style、副作用、外部系統、以及只存在於維護者腦中的專案歷史 。

關鍵概念：**「通過測試」≠「值得 merge」**——維護者真正貢獻的是尚未餵給 agent 的**「好」的判斷標準（sense of what good means）**。

4. 約束理論與下一批瓶頸 

物理學家出身的管理大師 Eliyahu Goldratt 在 1984 年的小說《The Goal》提出**約束理論（Theory of Constraints）**：每個系統只有一個瓶頸，加速非瓶頸環節毫無用處；而且修好一個瓶頸後，它不會消失，只會移動到下一處堆積。推論未來的瓶頸序列：寫程式（已崩塌）→ code review（現在）→ **維運/部署/擴展** → **資安**。演講者大膽假設這些終將被解決（約需 5–10 年，而非「AGI 2027」式的跳躍），並搭配另一個假設：**軟體需求 effectively 無限**——爛網站到處都是不是因為沒人會做好它，而是做好它太貴、會做的人太忙 。[[youtu](https://youtu.be/kspZP5BgkEU)]

關鍵概念：**約束理論**。

5. Agent 吃不掉的：定義什麼是「好」 

把軟體開發工作拆解並按「被 agent 吃掉的時間序」排序：


| 階段                 | 狀態     |
| ------------------ | ------ |
| 寫程式                | 已崩塌    |
| 審查與維護              | 即將崩塌   |
| 上線部署與擴展            | 下一個    |
| 決定做什麼、定義「好」、做到令人愉悅 | 可能永遠安全 |


倖存的工作是**找出人們真正想要什麼**。「我要管理我的訂單」這個需求有一萬個軟體可以滿足，但對麵包店、汽車材料行、大型製造業而言，「好」的定義完全不同——這個知識不在訓練資料裡、不在模型權重裡，只在經營者的腦中，唯一的萃取方式是**跟人對話**。且此知識有個關鍵特性：**不可轉移（doesn't transfer）**——行事曆 app 與排程 app 解決幾乎相同的問題，卻是完全不同的軟體。任何有千百個設定選項仍不能滿足你的軟體（如 Jira）正是試圖通吃一切卻失敗的例證 。

關鍵概念：**需求知識的不可轉移性**。

6. 本質複雜度與規格

Fred Brooks（《人月神話》作者、IBM System/360 主持人）1986 年將軟體難度分為兩種：**意外複雜度**（工具、語法、打字）與**本質複雜度**（問題本身的難度），並預言沒有單一工具能帶來 10 倍生產力——因為難的從來是本質部分。現在的數據驗證了他：程式碼快了 8 倍，交付只快了 30%。OpenAI 的 Shawn Grove 進一步指出：**程式碼是規格（spec）的有損投影（lossy projection）**——誰寫下 spec，誰就是真正的程式設計師。警訊：任何能被便宜驗證的東西，模型廠都能訓練到突破（Cognition 嘗試把「可 merge 性」寫進 benchmark；Cursor 的 BugBot 把每個 thumbs down 轉成規則，已累積 44,000 條規則）。因此維運與資安終將被吃掉；但「麵包師傅腦中的判斷」一旦沒被寫下來，就永遠是瓶頸 。

關鍵概念：**本質複雜度**、**規格的有損投影**。

7. 產品工程師的誕生

Andrew Ng 團隊有人提議 PM 人數是工程師兩倍，他生平首見；但他的答案不是多雇 PM，而是**把兩個職位融合**——當工程師理解使用者、能決定做什麼並直接做出來，執行速度會極快。1960 年代的 **systems analyst**（不寫程式、專門跟業務方對談找出問題）後來演化成今日的 PM，兩個職位正在合併回一個。這個職位被命名為**產品工程師（Product Engineer）**：找出人們需要什麼、定義「好」的樣貌、並交付——**打字的部分交給 agent**。市場已經在為此付費：Forward Deployed Engineer（與其高度相似的職位）職缺在 2025 年的 9 個月內暴漲 **800%**，平均薪資 **$240,000**，等同資深工程師。軟體開發者與程式設計師的身分在 2026 年正式離婚 。

關鍵概念：**產品工程師**。

8. 初級工程師的困境 

傳統訓練 junior 的方式——給他們規格明確的 ticket、收回程式碼、告訴他哪裡錯——**正是現在大家對 coding agent 做的事**，因此這個職位消失了。美國勞動統計（2023 年 1 月起）顯示：22–25 歲工程師就業率**崩跌中**（已持續兩年），而 41–49 歲工程師需求大增。Google 的 APM（Associate Product Manager）計畫每年只培養 50 人，全業界同類計畫合計約 1,000 人，但需求至少是每年 **10,000 人**。大學教資料結構、bootcamp 教 React，沒有人教「去跟麵包師傅坐一週、回來寫出 spec」。IBM 已開始將入門職位重新設計為「對談客戶與撰寫規格」而非寫程式 。

關鍵概念：**訓練梯斷裂**（junior ladder collapse）。

9. 給熱愛技藝的人

很多人因熱愛技藝（乾淨的抽象、難纏的 bug 終於投降）而入行，他們沒報名去訪談麵包師傅，且已在大聲抱怨。沒有安慰獎，但有一個觀察：**你以為你愛的是打字，其實你愛的可能是開始打字前的那一刻——想通問題的瞬間**。那個創造性火花不會消失。程式設計的技藝會像木工在傢俱工廠出現後存活下來一樣存活——像歌手唱歌，在無人房間裡唱，只因熱愛。只是它不再是有人付你數十萬年薪去做的事。編譯器、框架、開源都曾淘汰一整個世代的打字工作，每次軟體開發都變大變強。10 年後的專業人數更多、薪資相當、但形狀是產品工程 。[[youtu](https://youtu.be/kspZP5BgkEU)]

關鍵概念：**問題想通的瞬間**（the moment before typing）。

10. 現在該做什麼 

- 為「人類幾乎不參與程式碼生產」的世界做準備：只審查**高爆炸半徑（high blast radius）**的程式碼，其餘交給自動審查。
- 委派所有**可便宜驗證**的工作：花時間思考「如何自動判斷這東西好不好」，把這個機制餵給 agent，而不是去優化人工審查流程。
- 把最優秀人才的判斷力**寫進 spec、rubric 與 eval**——把只存在腦中的知識變成程式碼，這就是產品工程師的工作。
- 衡量對的指標：741% 的程式碼從來不是重點；要衡量**實際交付量**、審查意見被採納率、以及「測試通過」與「維護者願意 merge」之間的落差。記住：**最後的審查者是 production**——用另一個模型在線上監看並評分行為，那就是 eval 。

關鍵概念：**Eval 即產線**。

## [結論與行動建議]

**啟發金句**：「程式碼是規格的有損投影——誰寫下 spec，誰就是真正的程式設計師。」

**具體行動建議（S-D-E 法則）**：

- **S**pec：把你腦中對「好」的判斷寫下來——變成 spec、rubric、規則檔（如 Cursor 的 44,000 條規則）。
- **D**elegate：可便宜驗證的工作全數委派給 agent，把人力集中在 high blast radius 程式碼的人工審查。
- **E**val：衡量真正交付的東西，用 production + 模型評分建立 eval 迴圈，而非追蹤程式碼產量。

**生活實踐建議**：對身兼 PM 與 AI 應用架構師的你而言，這支影片直接驗證了你正在走的方向——工程師與 PM 的合併不是職涯風險，而是最大機會。下次啟動 side project 時，刻意練習「產品工程師」循環：先與目標使用者（例如你的 YouTube 觀眾或寵物照護社群）深度對談，把他們口中模糊的需求（「我想要記錄毛孩狀況」）翻譯成有驗收標準的 spec，再讓 Claude Code 等 agent 打字實作，最後用 eval（模型評分 production 行為）代替人肉審查收斂品質。這正是 Laurie Voss 定義的下一個十年的工作方式。
