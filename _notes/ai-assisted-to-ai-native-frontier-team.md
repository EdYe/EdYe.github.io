# 從 AI 輔助到 AI 原生：打造前沿開發團隊

**講者：Clare Liguori（AWS 資深首席工程師，Kuro/Kiro Agent 編碼助理）｜2026.08.28｜20:57**

***

## [核心摘要]

AWS 資深首席工程師 Clare Liguori 揭示 Amazon 內部「**前沿開發（Frontier Development）**」實踐：50 個團隊長達一年的對照實驗證明，90% 使用相同工具，卻只有半數達到 4.5 倍以上部署速度提升。關鍵差異不在工具，而在是否刻意改變工作方式。她提出五大習慣——投資 Agent 上下文、先慢後快、餵養而非保姆式協作、意圖先行、測試左移——將 AI 從輔助提升為原生開發模式，並指出決策速度已取代寫程式碼成為新瓶頸。

***

## [詳細重點整理]

### 1. AI 編碼的四階段演化 [00:00]

AI 編碼助理經歷四個階段：行內程式碼補全（寫下一行/下一個函式）→ 聊天問答（對程式碼提問）→ Vibe Coding（自然語言驅動生成）→ **前沿開發（Frontier Development）**。Liguori 坦言在前三個階段，她個人僅感受到 10–20% 的生產力提升。但進入前沿開發階段後，Amazon 內部試點觀察到中位數 4.5 倍、最高超過 10 倍的生產力躍升。

**關鍵概念：前沿開發（Frontier Development）**——以行為定義的開發模式，而非特定工具。

### 2. 前沿開發者的三個行為定義 [01:22]

Liguori 以三個可觀察行為定義前沿開發者：

- **放手編碼（Hands-off Coding）**：工程師僅親手撰寫 1–2% 的程式碼，其餘交由 Agent 生成
- **低頻互動**：讓編碼助理連續運行數小時無需人工介入
- **最小化空閒時間**：同時並行多個 Agent，處理任務積壓佇列

這三個行為共同指向一個核心——**將人類從執行迴圈中抽離**，讓工程師的角色從「寫程式碼的人」轉變為「指揮多個 Agent 的決策者」。

**關鍵概念：放手編碼（Hands-off Coding）**

### 3. 三場實驗：從神話到真實團隊 [02:34]

Amazon 進行了三場層層遞進的實驗，驗證前沿開發的可重現性：

**Bedrock Mantle 團隊 [02:34]**：Bedrock（模型託管服務）需建構新推論資料層，原估 30 人/18 個月。最終以 6 人、76 天完成，展現最高 20 倍改善。但問題在於——這 6 人包含 2 位傑出工程師（Distinguished Engineer），皆為分散式系統與 LLM 架構頂尖專家，故事雖震撼全 Amazon，卻對多數團隊不具可複製性 [03:43]。

**Prime Video 十天衝刺 [04:51]**：6 名工程師在無 on-call、無會議干擾的環境中密集使用 Kiro，10 天內將專案交付預估從 90 週降至 24 週。但資深工程師已提前 3 週拆解出細粒度、範圍明確的任務——這並非日常工程生活的真實樣貌。

**Amazon Stores 50 團隊試點 [05:57]**：這是最接近真實的實驗。50 個團隊涵蓋初階到資深工程師的正常分佈，皆在既有程式碼庫（非綠地開發）上工作，觀察近一年。以「部署至生產環境的速度」為指標（非單純 commit 數），發現明顯的兩極分化。

**關鍵概念：部署速度（Deployment Velocity）**——以交付至生產環境的速度衡量，而非程式碼提交量。

### 4. 50 個團隊的真正分歧：工具不是變數 [05:57]

試點最關鍵的發現：90% 的團隊都使用 Kiro（及其他內部工具），工具並非區分變數。真正造成分歧的是**工作方式**：

- 高產出組（半數團隊）：中位數 4.5 倍，部分超過 10 倍——這些團隊**刻意改變了工作方式**
- 低產出組（半數團隊）：低於 3 倍——這些團隊只是**將 Kiro 撒在既有工作流程之上**

這是 Liguori 的「aha moment」：為何過去 AI 生產力承諾未兌現？因為關鍵不在工具，而在是否改變工作方式。她特別強調使用「習慣（habits）」一詞，因為這不是一次性衝刺的成果，而是日常累積的行為改變。

**關鍵概念：刻意改變工作方式（Intentional Workflow Change）**

### 5. 習慣一：投資並修剪 Agent 上下文 [08:14]

工程師腦中有大量未文件化的知識——過去透過 Slack 對話、onboarding 師徒制、Code Review、Stand-up 會議傳遞。前沿團隊的習慣是**將這些全部寫入 skills files / steering files**。

雙向操作原則：
- **向上投資**：每次 Agent 犯錯或未如預期行事時，自問「我的 steering file 缺了什麼？」並補充
- **向下修剪 [09:21]**：隨模型能力躍升（如 Sonnet 3.7 需大量「不要做」指令，但 Opus 4.5 後已不需），定期檢視「這條規則還需要嗎？還是在膨脹上下文？」

舊的工作繞行（workaround）若不清理，會持續佔用上下文窗口，降低 Agent 效能。

**關鍵概念：上下文投資與修剪（Context Investment & Pruning）**

### 6. 習慣二：先慢後快 [10:31]

幾乎所有受訪團隊都回報：刻意採用新工作方式後，生產力**先下降**。這反直覺但符合邏輯——在既有程式碼庫（brownfield）中，必須先完成真實的工程投資，Agent 才能成功運作：

- 改善現有工具的錯誤訊息，讓模型理解失敗原因
- 建構新工具、新 MCP Server，擴展模型能力邊界
- 重構程式碼庫結構，讓 Agent 更易導航
- 極端案例：**更換程式語言**——從 Python/JavaScript（無型別、難測試、無編譯器錯誤）遷移至 TypeScript 或 Rust（Amazon 內部熱門，編譯器提供優質錯誤訊息）

這段投資期可能長達數月，但之後才會出現曲棍球棍式的生產力爆發。

**關鍵概念：先慢後快（Slow Down to Speed Up）**

### 7. 習慣三：餵養 Agent 而非當保姆 [12:50]

Liguori 指出這是理解生產力躍升的關鍵洞察。Vibe Coding 的典型模式是與 Agent 進行全天來回對話——每 30 秒到 1 分鐘等待生成、Review、再修正。這種模式下人類始終在迴圈內，無法離開去做其他事，也無法並行多個 Agent。

前沿做法的核心轉變：

- **保姆模式（左）**：持續對話、逐次修正、人類在迴圈內等待
- **餵養模式（右）**：提供 Agent 完成任務所需的全部資訊與自我驗證機制，讓它能**自行修正**，僅在達到品質門檻（通過編譯、通過測試、高覆蓋率）後才回報

進階做法：將自我驗證的標準寫入 steering file，讓 Agent 每次自動執行，無需重複提示。

**關鍵概念：餵養非保姆（Feed, Don't Babysit）**

### 8. 習慣四：意圖先行 [13:58]

Amazon 內部實踐**行為驅動開發（BDD）**，已內建至 Q 產品中。Liguori 觀察到一個常見反模式：給予高層級提示 → Agent 生成大量程式碼 → 來回修正「這不是我想要的」。在意圖本身不正確時，與 Agent 迭代程式碼的效率極低。

正確做法：針對模糊複雜的功能，先撰寫規格文件（Specification）。在 Kiro 中可讓模型協助生成規格，但**在文件上來回迭代，遠比在散佈於程式碼庫的變更上迭代更高效**。

**關鍵概念：意圖先行（Intent-First / Specification-Driven Development）**

### 9. 習慣五：測試左移 [15:09]

快速回饋迴圈是讓 Agent 能長時間自主運行與自我修正的關鍵。Agent 會犯錯，但若有正確信號就能自行修正。具體實踐：

- 加入 linter、單元測試、整合測試、效能測試、安全測試（皆為既有工程最佳實踐，但如今 ROI 終於夠高）
- **關鍵做法：Mock 服務**——以本地確定性回應的 Mock 服務取代端對端整合測試中的即時服務，讓 Agent 能完全在本機完成所有驗證，無需啟動外部服務或連接雲端

本機回饋越快 → Agent 能執行的迭代越多 → 生產力越高。

**關鍵概念：測試左移（Shift Testing Left）與本地確定性 Mock（Local Deterministic Mocks）**

### 10. 職業倦怠與認知負荷 [16:15]

前沿開發仍處早期採用階段，伴隨真實挑戰：

- **Flow Mat 職業倦怠**：工程師熬夜調校「完美提示詞」以讓 Agent 整夜運行，醒來就有程式碼變更可 Review
- **認知負荷攀升**：並行多個 Agent 時，需在終端機分頁間不斷切換
- **Review AI 產出比撰寫更難**：尤其對初階工程師——資深工程師職涯已大量累積 Code Review 肌肉，初階工程師尚未建立這項能力

**關鍵概念：Flow Mat 倦怠（Flow Mat Burnout）**

### 11. 組織變革與決策瓶頸 [17:23]

組織層面必須同步改變，否則前沿開發無法落地：

- **接受先慢後快**：領導者常犯的錯誤是質疑「有了 AI 工具和強大模型，為何沒有更快？」——必須容忍 2 個月的程式碼庫投資期。若每月仍要求出貨功能，團隊無法建立習慣
- **避免過快擴散**：若一開始就要求大規模組織所有團隊成為前沿團隊，將錯失從 Pathfinder、衝刺實驗、試點團隊中累積的學習。2026 年 Amazon 的挑戰是從 50 個團隊擴展至 2,000 個團隊
- **新瓶頸浮現 [19:41]**：手動寫程式碼不再是瓶頸，**決策速度**取而代之。當程式碼只需 1–2 個月完成，產品決策審查（2 個月決定是否建造 + 2 個月批准上線）反而成為長桿。前沿團隊花在決策上的時間已超過寫程式碼。可逆決策應盡可能加速

**關鍵概念：決策速度瓶頸（Decision Speed Bottleneck）**

## [結論與行動建議]

### 啟發金句

> **「工具不是變數，工作方式才是——把 AI 撒在舊習慣上，只會得到舊速度。」**

### 具體行動建議：FIRST 法則

將五大習慣濃縮為 **FIRST 法則**：

- **F**eed（餵養）：餵養 Agent 而非當保姆，賦予自我驗證能力，讓其僅在達標後回報
- **I**ntent（意圖）：在生成程式碼前，先在文件中固定意圖與規格
- **R**efactor（重構）：先慢後快，為 Agent 重整程式碼庫、改善錯誤訊息、建構 MCP 工具
- **S**hift（左移）：測試左移，以本地確定性 Mock 打造秒級回饋迴圈
- **T**rim（修剪）：投資 Agent 上下文並持續修剪，隨模型進步淘汰過時指令

### 生活實踐建議

針對你正在探索的 AI SDLC 架構（Gitea + MCP + Actions + LLM Gateway）：

1. **立即可做**：將你腦中關於專案架構、編碼規範、已知陷阱的知識，全部寫入 steering file / skills file。每次 Agent 犯錯時，不是手動修正，而是問「我的上下文缺了什麼？」並補充
2. **短期投資**：為你的程式碼庫建構本地 Mock 服務與確定性測試，讓 Agent 能在本機完成完整驗證迴圈，無需依賴外部服務。這是讓 Agent 能長時間自主運行的前提
3. **工作模式轉變**：停止與 Agent 逐行對話的保姆模式。改為一次提供完整任務描述 + 驗證標準，讓 Agent 自行迭代，你則在並行的多個 Agent 間切換決策。這正是你 MCP 工具鏈的價值所在——讓 Agent 透過 MCP Server 自主存取所需資源
4. **組織層面**：若推動 AI 諮詢與架構 Review 服務，向客戶強調「先慢後快」的預期管理——前 1–2 個月生產力會下降，需要投資程式碼庫，之後才會出現倍數成長。這個預期設定本身就是諮詢價值
