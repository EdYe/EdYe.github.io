# 🧠 階層式記憶體：AI Agent 的上下文管理實戰

**影片資訊：** AI Engineer 研討會演講，2026年5月10日 
**講者：** Sally-Ann DeLucia，Arize AI 產品負責人

***

## [核心摘要]

當 AI Agent 面對海量 trace 資料時，**上下文視窗爆滿**是導致失敗的根本原因，而非提示詞品質。Arize 團隊在打造自家 AI agent「Alex」的過程中，歷經「截斷→摘要→智慧截斷＋記憶體」三個演進階段，最終以 **頭尾保留 ＋ 可檢索記憶體倉庫 ＋ 子代理人分工** 的架構，成功突破上下文困境。 

***

## [詳細重點整理]

### 1. 問題起源：惡性循環 [00:00]

Alex 以 Arize 自身的 trace/span 資料為輸入分析對象，但每次執行都會產生更多 span，導致上下文不斷膨脹，觸碰 token 上限後失敗，失敗紀錄又寫回 span，形成無法逃脫的迴圈。 

**關鍵概念：** **上下文惡性循環（Vicious Context Loop）** — 分析資料的系統，被其所分析的資料所束縛。

***

### 2. 失敗方案一：暴力截斷 [05:16]

只保留前 100 個字元，其餘丟棄。短期看似可行，但追問（follow-up）時 agent 完全遺忘前文，每次回覆像全新對話。 

**關鍵概念：** **過度截斷（Over-Truncation）** — 破壞推理連貫性，等同讓 agent 失憶。

***

### 3. 失敗方案二：LLM 摘要 [06:12]

交由 LLM 自動摘要壓縮上下文，看似聰明卻高度不穩定，因為模型自行決定「什麼重要」，缺乏可控性，結果不可靠。 

**關鍵概念：** **摘要不確定性（Summarization Inconsistency）** — 將知識篩選權完全交給 LLM，等同放棄系統控制權。

***

### 4. 有效方案：智慧截斷 ＋ 記憶體倉庫 [07:12]

真正解決問題的三要素：

- **頭尾保留（Head/Tail Preservation）：** 保留最前 100 字元與最後 100 字元，截去中間部分
- **可檢索記憶體倉庫：** 中間段落不刪除，而是存入附有 ID 的資料庫，agent 隨時可以取回
- **不重置系統提示（System Prompt Preservation）：** 維持 agent 的角色與任務連貫性
- **工具呼叫去重：** 僅保留最新一次的 tool call 結果，避免重複資料累積

**關鍵概念：** **上下文與記憶體分離（Context ≠ Memory）** — 上下文決定模型「現在看到什麼」，記憶體決定「什麼能被保留」。

***

### 5. 長對話的隱形殺手：長期 Session 問題 [08:19]

使用者不重啟對話，導致 session 越來越長，而失敗往往在**第 20 輪以後才爆發**，很難即時發現。 

**關鍵概念：** **長對話延遲失效（Late-Session Failure）** — 錯誤不是立即出現，而是隨上下文累積悄悄惡化。

解決方法：**長對話評估（Long Session Evals）** — 預載前 10 輪對話，測試第 11 輪的表現，讓 bug 變得可測試而非靠使用者回報。

***

### 6. 架構升級：子代理人分工 [09:33]

單一 agent 架構下，主對話、搜尋任務、資料推理全擠在同一個上下文，無法擴展。重構後：

| 架構 | 主 Agent | 子 Agent |
|------|----------|----------|
| **舊架構** | 對話 ＋ 重資料 ＋ 搜尋全在一起 | — |
| **新架構** | 僅保留輕量對話與輸出 | 承擔重資料處理與搜尋 |

**關鍵概念：** **上下文委派（Context Delegation）** — 重型任務下放子代理人，主 agent 保持輕盈可靠。

***

### 7. Claude Code 彩蛋：驗證策略正確性 [13:24]

Arize 團隊在 Claude Code 原始碼開放後，發現 Anthropic 採用的也是**類似的截斷加壓縮策略**，間接驗證了他們的設計方向正確。 

***

## [結論與行動建議]

**啟發金句：**
> **「Agent 的失敗不來自提示詞，而來自上下文。」** 

**具體行動建議（三層記憶法則：H-S-E 法則）：**
- **H（Head/Tail）：** 永遠保留頭尾，截去中間並存入可索引記憶體
- **S（Sub-Agent）：** 將重資料任務委派子代理人，主 agent 保持輕量
- **E（Eval）：** 建立長對話評估機制，主動測試 10+輪後的表現

**生活實踐建議：**
- 設計 AI 產品時，**先問「agent 看到什麼」再問「prompt 怎麼寫」**
- 建立對話長度監控儀表板，當平均對話超過 15 輪時，應觸發重新評估上下文策略
- 任何需要跨越大量資料的查詢任務（如搜尋、報告生成），優先考慮設計專屬子代理人
