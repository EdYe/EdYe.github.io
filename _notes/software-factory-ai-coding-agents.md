# 如何為 AI 編碼代理打造軟體工廠 

## [核心摘要]

本片提出「軟體工廠」的四層技術堆疊：**運算資源**、**開發環境**、**執行框架（harness）**、**控制平面／編排層**，每一層都可以獨立選擇自建或採購。核心主張是：與其全押單一廠商的垂直整合雲端代理方案，工程師應該保有選擇權，在開放介面上混搭組合（composition over inheritance）。痛點在於：測試變快了，但審查與人力時間仍是瓶頸，必須靠「重現案例優先、垃圾 PR 當規格、95% 自動化」等方法論壓縮瓶頸。

## [詳細重點整理]

**1. 自建 vs 採購的光譜 [00:00]**  
軟體工廠的設計選項落在一條光譜上：一端是全部內部自建（Boundary 的做法），另一端是全部向廠商購買（Cursor Cloud Agents、Cognition、Devin 等全端雲端代理）。真正的答案是工程師要能在開放系統中把各層組合起來，而不是被迫連坐式採購。  
關鍵概念：**組合優於繼承（Composition over Inheritance）**

**2. Codex vs Claude 的模型選擇實戰 [02:32]**  
頂尖代理式開發者在一年前就已大規模轉向 Codex。兩位講者的實測結論：**工程執行任務 Codex 明顯較好**（會自己讀更久，不需前期研究儀式來彌補模型差距）；UI 與內容寫作則 Claude/Opus 略勝或較易調教。模型選擇高度因人而異，取決於你落在「前期規劃派」還是「快速迭代派」——換模型的成本就像換鍵盤，會先損失數月生產力換直覺。驗證方法：**貼出 token 用量，不然不算數**。  
關鍵概念：**模型直覺養成期（Model Switching Cost）**

**3. 講者的個人工作流程：PRD → 連夜自動迭代 → 拆 PR [11:08]**  
與模型來回討論產出 PRD 與 HTML 互動模型（mock，不求精確只抓方向）→ 排程約 15 個提示詞讓 Soul、Fable、Codex 整夜互相「實作 → 審查 → 壓縮上下文 → 再審查」→ 隔天人工潤飾 → 請模型把兩萬行成果拆成 1,000–3,000 行的可審 PR，一次合併一個。原型（slop PR）的價值是驗證願景，真正的工程發生在「把它當規格、假設從零重做怎麼拆階段」這一步。沒人應該審查兩萬行的 PR。  
關鍵概念：**垃圾 PR 當規格（Slop PR as Spec）**

**4. 意見回饋流水線：不信任任何回饋 [16:03]**  
使用者回饋本質上不可信，因此 issue 不是直接從回饋建立，而是處理完回饋之後才建立：先檢查最新版本是否已修 → 判斷是既有重現案例還是新案例（去重）→ 燒自己的 token 產出乾淨的 **重現案例（repro）** → 才建立 issue → 指派負責人（shepherd）在 Slack 收到「bug 修正 + repro + 修補內容」或「困難案例 + 計畫」。每個 PR 都跑全套檢查，量測只花 CPU 時間。去重代理再爛也值得，因為能省一半時間。難度分類目標約 60% 準確率，超過 60 行的修正強制重新分類。  
關鍵概念：**重現案例優先（Repro-First Pipeline）**

**5. Boundary 的實作架構 [23:08]**  
一群預先裝好工具鏈的 MacBook/Mac mini 組成資源池（避免沙箱開機啟動時間）→ Claude Code / Codex 以無頭模式跑，輸出 stream-json 的 JSONL 對話逐字稿直接被讀取 → 外層是真正的 **while 迴圈**：「修到 CodeRabbit 滿意才通知人類，最多迭代三次否則踢給人」；人類確認後再讓代理持續把 main 合併進來、顧到 merge queue 完成 → 雲端自架的 REST「派發器」監聽 Slack、Linear、GitHub 的 webhook 再跟機器溝通。不做沙箱、不做容器，因為只執行自己產出的可信 repro。追求 **95% 自動化**而非全自動——全自動難度高一個數量級。  
關鍵概念：**外層執行框架（Outer Harness）**

**6. 四層技術堆疊 [33:35]**  
軟體工廠由四層構成，每層都有自建／採購（BYOC）選項：


| 層次   | 自建選項                                                     | 採購選項                          | 講者觀點                                        |
| ---- | -------------------------------------------------------- | ----------------------------- | ------------------------------------------- |
| 運算資源 | EC2、K8s、辦公室疊 MacBook                                     | Daytona、E2B、Freestyle 黑盒子 API | 成熟領域，BYOC 彈性任選                              |
| 開發環境 | 預裝工具鏈的本機／雲機器                                             | 廠商 Docker 基底映像                | 除非是小型 Next.js 玩具，否則應自己掌握這層；含身分佈建（API 金鑰、權限） |
| 執行框架 | 內層：Claude Code、Codex、OpenCode、Pi；外層：自建 while 迴圈 + skills | 買厚的內層（附瀏覽器、測試），外層做薄           | 各家 hooks 標準互不相容，是整合失敗點                      |
| 控制平面 | 自建 REST dispatcher                                       | HumanLayer、Devin、Claude 自動化   | 最缺乏解決方案的一層：派發、追蹤、排程、權限、預算、複利工程              |


關鍵概念：**軟體工廠四層堆疊**

**7. Google Cloudtop 類比 [37:10]**  
Google／Meta 工程師從不把程式碼簽出到本機：每次都重建一台全新的 **Cloudtop**，程式碼庫大到不可能放本機、也不准帶出公司；每個 Web 服務自動綁一個可分享的內部子網域。我們正在集體重新發明這套「黃金堆疊」。如果你不是 Google，一個全端雲端代理可能就夠了。  
關鍵概念：**寵物與牲畜（Pets vs. Cattle）**——開發環境應該像牲畜（隨建隨棄、腳本佈建），Boundary 的 MacBook 目前還是寵物模式，但已用啟動腳本半自動化 [00:42:38]

**8. 多儲存庫協調 [45:30]**  
處理大量 repo 時不建議 Tailscale 蔓延；解法是建一個**協調儲存庫（coordination repo）**，只放一份 [CLAUDE.md](http://CLAUDE.md) 告訴模型其他 repo 在上一層目錄（source/repo1、repo2…），不需要 submodule、subtree 或 symlink，也不用雙向參照。明確警告：**不要用 git submodule**（釘死 commit、要兩處 commit），subtree 勉強可行。  
關鍵概念：**協調儲存庫模式**

**9. 介面層的未來 [51:22]**  
軟體工廠會走向普及，但不會有通用一套方案，因為每家公司的內部環境都有怪癖。現有介面（ACP 太窄、AG-UI 不支援 hooks）都不夠用；每個執行框架本質上都是自己量身打造的 UI，hooks 標準難以統一。類比：React 發明了「狀態」才解決網頁難題，這裡還在等那個等級的抽象。MCP 的價值在於引爆生態系、讓各層開發者能混搭；未來會出現軟體工廠版的 LAMP stack。廠商競合（如 Claude 不支援 [AGENTS.md](http://AGENTS.md)）是最大變數，猶如**瀏覽器大戰**。  
關鍵概念：**可擴充軟體（Extensible Software）**——軟體最終的擴充方式就是讓代理寫程式碼（code mode），使用者自訂欄位與工作流程，直接 live reload；向廠商購買的應該是可靠性，而不是訂閱別人允許你寫的工作流程 [01:06:33]

## [結論與行動建議]

**啟發金句**：貼出你的 token 用量，不然不算數——真實的工具信仰，是用行為證明的，不是跟風喊出來的。

**具體行動建議（R-P-R-95 法則）**：

- **R**epro first：issue 建立之前，先燒自己的 token 產出可信的重現案例
- **P**hase it：原型可以巨大，但合併前一律拆成 1,000–3,000 行、人類可消化的 PR
- **R**epeatable loops：把外層 harness 寫成真正的 while 迴圈（修到機器人滿意才叫人）
- **95%**：只追求 95% 自動化，最後 5% 交給人類，難度反而低一個數量級

**生活實踐建議**：對你目前的工作流程做一次「四層盤點」——你今天用的運算資源、開發環境、執行框架、控制平面分別是買的還是自建的？至少把控制平面（一個監聽 webhook、派發任務、追蹤狀態的 REST 服務）自己掌握，這是最便宜、最難被取代、也最能累積團隊複利的一層。內容創作上也適用「小增量法則」：不要讓 AI 一次寫三頁垃圾，一次兩三句、來回四五輪抓到語氣，比事後修爛稿快得多。
