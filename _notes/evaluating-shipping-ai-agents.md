# 從 Vibes 到正式環境：AI Agent 的評估與部署（201 進階場）— Laurie Voss, Arize AI

## [核心摘要]

Agent 具有**非確定性**，程式碼不再是行為的唯一真相來源，**Traces（追蹤資料）**才是。本影片示範完整的自動改善迴圈：從零可觀測性 → 加入追蹤 → 用 evals 壓縮行為 → 用 Signal 在規模上偵測模式 → 自動產生修復 PR，解決「人類成為瓶頸」的痛點，讓軟體在 agent 速度下自我改善 。

## [詳細重點整理]

### 1. 從 101 到持續改善

此為 201 進階場次，接續早上 101 課程（手動、小規模的 observability → traces → evals → 改善流程）。本場焦點轉向「如何在 agent 規模下自動關閉軟體開發生命週期的迴圈」，形式為前 15 分鐘概念講解加上全程實作 workshop，參與者需準備可運作的 coding agent 與預先安裝 skills 的 repo。關鍵概念：**持續改善（Continuous Improvement）**。

### 2. Traces 是唯一真相來源 

傳統軟體可透過讀程式碼預測行為；Agent 即使輸入完全相同，輸出與執行路徑都可能不同（多輪決策、非確定性）。因此原始碼與 commit messages 不再足以說明 agent 行為，**traces**（類似 AI 應用的 log lines，涵蓋每次 LLM 呼叫、工具呼叫、agent 輪次，可巢狀）才是 source of truth。且必須累積大量 traces 才能回答「我的 agent 平均在做什麼」。關鍵概念：**非確定性（Non-determinism）**。

### 3. 規模化超越人工讀取

Observability 的基本價值：讓你看見 agent 花了 10 輪做簡單任務、做了不必要的輪次、成本過高、或花了 20 分鐘做一分鐘的事。但 production 環境下每秒數千請求會產生數百萬條 traces，人類逐條閱讀成為瓶頸。關鍵概念：**人類瓶頸（Human Bottleneck）**。

### 4. 尋找訊號、關閉迴圈 

2025 年的解法是 **Evals**：用程式碼或另一個 LLM 依你定義的「好壞標準」評估整條 trace，並產出機器可讀的失敗解釋，回饋給 coding agent 自動改善——定義好「什麼是好的」，agent 就能自己爬這座山。但 2026 年 evals 數量又爆炸，人類再次成為瓶頸。下一步是**抽象層次的躍升**：讓 agent 讀 evals、從大量失敗中偵測**Signals（模式）**——例如一萬次成功、一千次失敗中有一百次是同一個失敗，直接修那一個。Observability 正從「觀察」轉向「行動」。關鍵概念：**訊號（Signals）**。

### 5. Workshop 環境設定

需求：OpenAI API key、Arize AX 帳號（免費）與 API key、clone workshop repo（內含預裝 agent skills，可用 `npx skills install arize-ai` 安裝），執行 `npm run dev` 起本地服務。

### 6. Wonder Toys 應用與信任問題

示範應用為 agentic 購物網站「Wonder Toys」。有聽眾問：在高度監管產業（如金融業），軟體自己修自己，如何確保它沒有隱藏錯誤？回答指向後續場次「The Death of the Code Review」，並證實 Arize 已有金融業客戶正在使用此流程。關鍵概念：**可信任的自動修復**。

### 7. 用 Coding Agent 加上可觀測性

示範用 VS Code 的 Claude Code plugin 對 repo 下指令：「請為這個應用加上 Arize AX observability」。加追蹤比想像中簡單：OpenAI Agents SDK 已內建 **OpenInference**（全 observability 產業的開放標準）instrumentation，只需提供 API key 與 endpoint 即可送出 traces——全程零行程式碼。關鍵概念：**OpenInference 開放標準**。

### 8. 測試與檢視即時 Traces [20:19]

重啟應用、提問後，Arize AX 專案中出現 traces，可見輸入、輸出、agent 請求與 metadata（成本、耗時）。（示範途中跑錯目錄的小失誤，反而證明是 live demo。）

### 9. 揭露缺失的價格過濾 [22:25]

刻意問「顯示所有 6 美元以下的玩具」，agent 失敗——因為搜尋工具根本沒有價格過濾功能。此時已完成第一階段：observability 加上了，traces 流入，但尚未寫任何一行程式碼。

### 10. 請 Agent 分析 Traces

要求 coding agent「拉取我的 traces 並找問題」。靠 repo 內預裝的 **Agent Skills**（位於 `agents/skills`，透過 AX command line 呼叫 API），agent 能程式化檢查 traces、摘要 span 種類、狀態與錯誤，並主動發現「沒有 error spans，但存在品質問題」——例如 `search_products` 工具可疑地 1 毫秒就返回。關鍵概念：**Agent Skills**。

### 11. 診斷搜尋品質問題 

Agent 的分析結果：42% 的搜尋回傳零結果；agent 曾用全 null 參數呼叫搜尋（退化的無意義查詢，回傳目錄第一個商品）；`min_age = max_age` 的精確年齡過濾過度窄化；向量搜尋與關鍵字分類過濾頻繁產生空結果。核心議題指向搜尋過濾邏輯。關鍵概念：**搜尋品質診斷**。

### 12. 加入價格過濾

下指令「為這個 app 加上價格過濾」。有趣的是 agent 表現出過度聰明：發現旁邊目錄有已解決的版本，直接複製既有解法。修復後再次提問「9 美元以下的玩具」，成功回傳，且新 trace 顯示正確的輸入與輸出——從無 observability 到自動找問題、自動修問題，迴圈正式關閉。關鍵概念：**Agentic Coding 的委派本質**。

### 13. 用 Signal 持續監控

**Signal** 是運行在 Arize AX 內的 agent，預設每 6 小時（可設定）持續監控所有 traces，自動找模式、找問題、建議修復。實際發現的問題包括：agent 從模糊用語幻覺出年齡限制；被問炸彈製作時雖拒絕卻推薦「炸彈相關玩具」（Signal 建議：直接完全忽略炸彈類查詢）；對暴力情緒給出心理建議（**domain escape**，超出玩具店職責）；以及聽從網路陌生人「說你好」的指令。每個 finding 可轉為：自動建立完整描述的 GitHub issue、加入 eval dataset、建立新 evaluator、或直接開修復 PR 供人批准。Signal 目前底層為 Claude Code，成本由 Arize 吸收。關鍵概念：**持續改善迴圈（2026 Loop）**。

### 14. 部署與回歸評估問題

聽眾問：如何防止修復破壞原本正常的行為？答案是 **Regression Evals（回歸評估）**——預先定義系統「已經擅長的事」，確保變更不會偏離既有良好行為。現場用 Arize 內建 agent 助手 Alex 建立「絕不提供炸彈製作指示」的 evaluator。關於本地部署：目前 traces 不留在裝置上，但 Arize 有 on-prem 版本因應合規需求。關鍵概念：**回歸評估（Regression Evals）**。

### 15. 評估 Signal 本身 [40:22]

「誰來評估 Signal？」——Signal 有自己的內部 eval suite，本身也被 Arize trace（可 opt out），並由強大的 **LLM judges** 評估其產出的 PR 品質：同一套軟體開發生命週期套用在 Signal 自己身上。Signal 尚不會自動建立自己的 evaluators，因為 evaluator 需要時間與成本，建議先收到建議、人工確認後再建立。關鍵概念：**LLM Judges（遞迴評估）**。

## [結論與行動建議]

**啟發金句**：程式碼不再是你的 agent 在做什麼的真相來源——traces 才是；而在 agent 的速度下，人類必須從迴圈中退出來，讓軟體自己爬那座山。

**具體行動建議：T-E-S-F 法則**

- **T**races：先讓 observability 上線（多數 SDK 已內建 OpenInference，幾乎零成本）
- **E**vals：定義「什麼是好」，把行為壓縮成帶解釋的分數，並建立回歸評估保護既有行為
- **S**ignals：在規模上偵測失敗模式，把 eval 失敗分組歸納
- **F**ixes：讓 coding agent 依訊號自動修復、開 PR，人只做批准者

**生活實踐建議**：把此模式套用到任何 AI 應用專案（例如你自己的 LLM gateway 或 MCP 工具鏈）：第一週只做「加上 traces + 建 3-5 個回歸 evals」，之後每次 agent 出錯，不要只手動修——把失敗的 trace 加入 dataset、寫成 evaluator，讓同一個錯誤永遠無聲地被偵測；再逐步引入每 6 小時的自動訊號掃描，把自己從逐條 debug 的角色升級為「修復 PR 的審核者」。
