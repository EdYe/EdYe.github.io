# Coding Agents Don't Scale Themselves. Neither Do Your Teams.

**講者：** Patrick Debois（Tessl）
**來源：** AI Engineer
**日期：** 2026-08-22

---

## [核心摘要]

本演講核心論點為：Coding Agent 的 harness 與 loop 終將商品化，真正的競爭優勢不在技術本身，而在**團隊、平台與組織的變革能力**。Patrick Debois 以 2009 年推動持續交付時遭遇的質疑為類比，指出「在我們這裡行不通」的抗拒訊號，實際反映的是組織尚未準備好，而非技術不可行。他提出從「修復 Agent 產出的程式碼」轉向「改善系統本身」的思維範式轉移，並追蹤兩個關鍵指標——**人類觸碰次數**與**共享複用率**——來衡量團隊在 Agent 時代的成熟度，最終指向將組織知識轉化為可複用資產，從持續交付邁向持續學習。

---

## [詳細重點整理]

### 1. 「在我們這裡行不通」的訊號解讀 [00:00]

2009 年推動持續交付（Continuous Delivery）時，多數人認為這個想法瘋狂。如今推動**黑暗工廠**（Dark Factory）——即組織內自主運作的自動化開發流程——聽到一模一樣的抗拒：「在我們這裡行不通」。

這句話的真正訊號不是「技術做不到」，而是「我們還沒準備好」。問題出在組織的結構與協作方式，而非技術可行性。

目前的研討會大量聚焦於優化 Agent 的 loop 與 harness，但這些終將商品化——可能變成前沿實驗室直接販售的服務。因此，這些技術堆疊不會是任何組織的差異化優勢。真正的改變發生在**團隊、平台與組織**三個層面。

依循**康威定律**（Conway's Law）：組織的溝通結構會決定其產出的系統架構。Agent 時代同樣適用——工具與組織結構之間存在相互塑造的關係。

> **關鍵概念：黑暗工廠（Dark Factory）** —— 組織內自主運作的自動化開發流程，從「完全人類介入」到「自主審核通過」的光譜。

---

### 2. 開發者不願只做 Prompt 工程 [02:46]

主流敘事認為開發者將演變為 Agent 的指揮者（conductor）與編排者（orchestrator）。但實務上，開發者反映：「我們沒有報名做這個。我們沒有報名寫更好的 prompt、更好的 spec。我們是工程師。」

這種身分認同的摩擦是真實的。**上下文工程**（Context Engineering）的出現稍微緩解——它不只是寫 prompt，還包含測試 prompt、評估 prompt、分發與優化 prompt，讓開發者感覺到工程成分。但單純操作 prompt 與 spec 仍讓許多開發者感到空洞。

轉折點在於：當組織開始引入 harness、loop 與更自主的工作流程時，一條新的技術路徑打開了——開發者開始為 Agent 建構工具（building tooling for the agent）。這重新點燃了那些原本覺得「這不是我的工作」的開發者的熱情，因為他們可以用程式化的方式協助 Agent。

對於組織中最懷疑、最抗拒的人，Patrick 的建議反直覺：這些人正是最適合投入**上下文撰寫**的人選，因為他們對產出品質的不滿，正是改善系統的驅動力。將他們的憤怒與懷疑轉化為改善 Agent 的動力。

> **關鍵概念：上下文工程（Context Engineering）** —— 超越單純 prompt 撰寫，涵蓋測試、評估、分發、優化上下文的完整工程流程。

---

### 3. 停止修復程式碼，改善系統 [05:20]

核心心態轉變：**停止修復 Agent 產出的程式碼，轉而改善系統本身**。

引用 Swyx 的觀點：「停止建造東西，建造那個建造東西的東西」（Stop building the thing, build the thing that builds the thing）。這是一層抽象的提升——透過上下文、harness 與 loop 來建構系統，而非持續手動修正產出。

目標是**最小化人類觸碰**（minimize human touches），同時維持良好的工程實踐。一個常見的誤區是：開發者拿到 Agent 產出後直接使用，跳過測試與文件更新（yoloing）。應該要求 Agent 遵守與人類工程師相同的標準——寫測試、更新文件、遵循工程規範——因為這些實踐不僅維持系統品質，也讓 Agent 持續變得更好。

> **關鍵概念：系統思維勝於產出修復（System Thinking over Output Fixing）** —— 將改善的焦點從「修正這一次的產出」提升到「優化產出的系統」。

---

### 4. 回顧會議、規劃與下游擠壓 [07:04]

先進團隊的儀式正在改變：

**回顧會議（Retro）**：不再討論「程式碼出了什麼問題」，而是討論「系統出了什麼問題」。當 Agent 反覆撞上同一面牆，回顧會議的焦點是修復系統，而非修補單次產出。

**規劃會議（Planning）**：出現明確的分類——
- **充分定義的工作**：可直接交給 Agent 處理
- **未充分定義的工作**：仍需團隊對話討論

團隊負責人的角色是設定步伐與約束：不是說「去自己摸索」，而是明確指令「停止只做 prompt，讓上下文可複用」，然後推進到下一個層次。

**下游擠壓效應**：當團隊產出加速，下游的 GTM（Go-to-Market）團隊與使用者跟不上。因此 harness 不應止於程式碼，也要延伸到下游的自動化。同時，需求收集的速度也可能跟不上團隊的產出，需要整合到工作流中。

> **關鍵概念：系統層級回顧（System-Level Retro）** —— 將回顧會議的焦點從程式碼品質轉向系統品質，識別 Agent 重複遭遇的障礙。

---

### 5. 兩個關鍵指標：人類觸碰次數與複用率 [09:38]

Patrick 追蹤兩個核心指標來衡量團隊在 Agent 時代的生產力：

| 指標 | 定義 | 期望趨勢 |
|------|------|----------|
| **人類觸碰次數**（Human Touches） | 讓 Agent 產出正確結果所需的人類介入次數 | 隨 harness、context、guidelines 改善而下降 |
| **共享複用率**（Reuse） | 從單人使用轉為共享系統後，一次改善惠及所有人的倍增效應 | 隨共享程度提升而上升 |

第二個指標尤其重要：這不是讓一個人變成 10x 開發者，而是讓一次改善影響所有使用該系統的人。從單人 → 團隊共享 → 組織級多人系統，是一個乘數效應的飛輪。

> **關鍵概念：觸碰-複用雙指標（Touches-Reuse Dual Metric）** —— 衡量 Agent 成熟度的兩個維度：介入頻率下降與改善共享擴散。

---

### 6. 平台團隊的新課題 [10:29]

當 Agent 使用從單一團隊擴展到整個組織，平台團隊需要承接新的職責：

- **技能註冊表**（Skill Registries）：管理可複用的 Agent 技能
- **評估系統**（Eval Systems）：為上下文與 guardrails 建立評估機制
- **身份管理**（Identities）：為 coding agent 建立專屬身份與權限
- **MCP Gateway**：模型上下文協議的閘道管理

但平台團隊目前可能還在關注基礎設施與雲端，尚未意識到這些新需求。且中央化的角色定位模糊——是平台團隊？開發者體驗團隊？兩者都不完全擁有這些職責。需要一個明確的 owner 來驅動這個中央化的職能。

> **關鍵概念：鋪設道路（Paved Roads）** —— 跨團隊可複用的標準化上下文、harness 與 guardrail，類似雲端時代的鋪設路徑。

---

### 7. 蔓延、鋪設道路與花費可見化 [12:12]

如果任由每個人自行建立技能與 harness，會導致**蔓延**（Sprawl）：同一個功能有多個 fork 版本，難以判斷該選哪一個，也無人維護。

解法是中央化的**鋪設道路**機制：
- 有明確 owner 負責維護
- 確保可測試、模組化、可被他人擴展
- 經過安全掃描
- 不是隨意分享的腳本，而是工程級的共享元件

共識形成困難——有時像 tabs vs spaces 的爭論。最終可能不是一條路，而是一個目錄中提供 3-4 條鋪設道路供選擇，團隊仍可自建但須自負預算。

**花費可見化**：平台團隊應讓各團隊知道 Agent 使用成本。當成本可見時，團隊才有動力優化——例如減少 Agent 的迭代次數。如果只看到最終結果而看不到過程成本，就無法進行優化。

> **關鍵概念：鋪設道路目錄（Paved Road Catalog）** —— 標準化、可維護、安全掃描的共享元件目錄，避免無序蔓延。

---

### 8. 不靠 Champions Program 啟用組織 [14:43]

VP of Engineering 問：「如何啟用整個組織？」

可預測的標準劇本：Hackathon、Lunch and Learn、分享成功案例、Slack 頻道、Champions Program——這些是通用的轉型手法，無論是 Agile 還是 DevOps 都適用。另一端，「讓千朵花綻放」（let a thousand flowers bloom）的放手策略則已知無效。

Patrick 主張的方式是：給團隊負責人與平台團隊**明確的授權**（mandate），讓他們在各自的層級推動這項工作，而非依賴單一開發者的自發行動。

> **關鍵概念：授權式轉型（Mandate-Driven Transformation）** —— 透過明確授權團隊負責人與平台團隊驅動變革，而非依賴自發的 Champions Program。

---

### 9. 職缺標題無意義時的招聘策略 [15:36]

新興職缺標題氾濫：AI Product Engineer、Forward Deployed Engineer、Agentic Engineer、AI Engineer——這些標題不代表任何成熟度，因為沒有人真正成熟。但職缺標題是信號，能吸引具備新意圖的人才。

招聘流程的三階段評估：

1. **AI 能力測試**：給予練習題，鼓勵候選人全力使用 AI 解決。評估的是 AI 槓桿能力，而非禁用 AI 的原始编码能力。
2. **工程品味測試**：通過後進行 walkthrough，要求候選人解釋「為什麼這樣做是好的」。這裡測試的是品味與工程判斷力。
3. **協作意願測試**：是否願意分享？是開放的團隊玩家還是獨行俠？這對應組織中「讓成果可分享、可複用、工程級」的文化需求。

不尋找 ML/AI 專家或編碼專家，而是尋找三項能力的綜合。找不到三項兼備的人也沒關係，但要清楚知道在哪一項需要輔導與培訓。不要把三項能力混為單一的「資深/初階」判斷。

> **關鍵概念：三維招聘法（Three-Dimensional Hiring）** —— AI 槓桿力、工程品味、協作意願三個獨立維度評估候選人。

### 10. 優化花費而非限制花費 [18:07]

VP of Engineering 需要為 Agent 投資辯護：
- 可量化的：授權數量、人類觸碰次數下降、改善複用率
- 難以證明的：更快交付、品質提升

相較於「有無 Agent 的生產力對比」這種難以量化比較，觸碰次數與複用率是更容易展示的指標。

當供應商收費瘋狂時，不要直覺地「限制所有花費」。正確的反思是**優化花費**（optimize the spend）：
- 選擇正確的模型，教育團隊模型選擇
- 提供更好的上下文與 harness，減少迭代次數，從而降低成本

團隊規模的辯論：一個人能做全部是終極夢想，但實際上需要互補技能（PM、設計），加上備援（度假時的替補），還需要處理生產環境工單的人，以及需要培養的初級成員。因此組織層面不太可能縮減到每隊 1-2 人。

> **關鍵概念：花費優化勝於花費上限（Spend Optimization over Spend Cap）** —— 透過模型選擇與系統改善降低成本，而非粗暴設定預算上限。

### 11. 暗淡工廠與知識護城河 [20:38]

黑暗工廠實際上是一座**暗淡工廠**（Dim Factory）——不是全自動，而是根據風險等級決定哪些功能可以自主。

自主化的光譜：
- 微觀管理（Micro Manager）：每一步都需人類確認
- 自主審核（Autonomous Approval）：系統驗證通過即可自動放行
- 中間地帶：投資於審計（誰改了程式碼）、驗證器（程式碼是否有用）、情境感知（失敗時的感知能力）

**真正的護城河是知識**：你投入在技能、上下文、harness 與業務情境中的知識，是難以被複製的資產。這將**持續交付**（Continuous Delivery）延伸為**持續學習**（Continuous Learning）。

關鍵問題不是「系統有多可靠」，而是「在持續改變系統的同時，能否維持可靠」。快速替換新組件的能力（swap in/out）是反應模式的基礎。

最終結論：**不是單一超級開發者會贏得比賽，而是在不同組織層級持續改善的團隊。**

> **關鍵概念：持續學習（Continuous Learning）** —— 從持續交付延伸，將組織知識固化為可複用資產，形成難以複製的護城河。

## [結論與行動建議]

### 啟發金句

> 「停止建造東西，建造那個建造東西的東西。」—— 不是單一超級開發者會贏得比賽，而是在不同組織層級持續改善的團隊。

### 具體行動法則：S-S-O 法則

- **S — System over Output**：停止修復 Agent 的產出，轉而改善產出系統。每次 Agent 撞牆，不是修程式碼，而是修 harness、修 context、修 guardrail。
- **S — Share over Solo**：從單人使用走向共享系統。一次改善惠及所有人，才是真正的乘數效應。追蹤「人類觸碰次數下降」與「複用率上升」兩個指標。
- **O — Optimize over Outsource**：面對花費不要設上限，而是優化——選對模型、改善上下文、減少迭代。面對人才不要只看標題，而是三維評估（AI 槓桿力、工程品味、協作意願）。

### 生活實踐建議

1. **建立個人「系統改善」習慣**：每當 AI 工具產出不理想時，不要直接手動修正結果。退一步思考——是上下文不夠？是 harness 缺少限制？將每次挫折轉化為系統層的改善。
2. **將重複工作「鋪設道路化」**：盤點日常工作中的重複性任務（報告格式、資料彙整、郵件模板），將其標準化為可複用的範本或流程，建立個人的「技能註冊表」。
3. **追蹤自己的「人類觸碰次數」**：在使用 AI 輔助工作時，記錄需要人工修正的次數。當這個數字持續下降，代表你的上下文工程與工作流正在成熟。
4. **知識沉澱為護城河**：將你的業務知識、決策邏輯、領域 expertise 固化為結構化的 context 與 prompt，這些才是難以被複製的個人競爭優勢——對應組織層面的「知識護城河」。
