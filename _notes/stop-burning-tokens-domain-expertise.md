# Stop Burning Tokens: Why self-improvement needs domain expertise first

## [核心摘要]

本研究在 Langfuse 平台上設計了一個**自動優化迴圈（Auto-Improvement Loop）**，以學術論文分類任務作為具備清晰目標函數的測試案例，驗證 AI Agent 能否透過反覆分析錯誤、提出假設並更新 Prompt 來自動提升準確率。實驗結果顯示，從基線 68% 到最終約 83% 的準確率提升中，**首次迭代即貢獻了 10% 的躍升**，證明高信號回饋（yes/no 對錯判定）與足夠資料量是驅動自動改善的基石。更關鍵的發現是：在缺乏「程式碼能否編譯」這類確定性目標函數的領域中，必須由領域專家協助定義**高信號評估器（High-Signal Evaluators）**，將抽象的「品質」轉化為具體可量化的 yes/no 判定，才能避免無意義地消耗 Token。

***

## [詳細重點整理]

### 1. 迴圈時代的來臨與程式碼領域的優勢 [00:00]

2026 年中，整個 AI 社群聚焦於「迴圈（Loops）」概念——Boris Journey 宣稱不再手寫 Prompt 而改用迴圈，Peter Steinberger 主張設計迴圈而非 Prompt Agent，Karpathy 的自動研究與自動改善話題也引爆討論。然而這些觀點多來自開發者視角，程式碼領域之所以成為自動改善的成功案例，原因在於擁有一個清晰的目標函數：**程式碼能否編譯**。雖然能編譯不等於品質優秀，但至少確保交付的成果「能用」。

**關鍵概念：目標函數**

### 2. 非程式碼領域的目標函數困境 [01:17]

在醫療合規、健康照護或聊天機器人等領域中，目標函數遠不如「程式碼能否編譯」般清晰。給定 Agent 的目標往往是不完整的——你可能以為該往一個方向走，但實際最佳目標在另一個方向。Langfuse 觀察到：**在目標函數與評估器上投入最多心力的團隊**，才能持續升級應用並有信心地部署，因為確知系統如預期運作時，即便推送程式碼變更也能安心。

**關鍵概念：不完整目標函數**

### 3. 實驗設計：單標籤分類作為最清晰目標函數 [02:36]

研究團隊尋找最清晰的目標函數，最終選定**單標籤分類任務**：給定一個項目與一組標籤（如：訂單、投訴、詢問），分類器指派一個標籤，可明確判斷預測標籤是否等於真實標籤，並計算準確率。實驗以學術論文分類為任務——根據論文標題與摘要，預測作者指定的主標籤。資料集劃分為：200 筆訓練集、100 筆驗證集、300 筆測試集，以防止過擬合。

**關鍵概念：單標籤分類任務**

### 4. 最小自我優化迴圈架構 [03:33]

迴圈由三個核心元件構成：

- **Agent**：基於 GPT-5 nano 的簡單 Prompt，使用扁平標籤列表，刻意選用小型低成本模型以測試自動改善效果。
- **優化器**：透過 Claude Code 運行，調用 Claude Opus 4.8 前沿模型，參考 GPT-5 提示指南與描述迴圈的 task.md 檔案，提出 Prompt 更新建議。
- **目標函數**：在 Langfuse 平台上管理，包含輸入欄（標題+摘要）與預期輸出欄（標籤）。

迴圈流程：基線評估 → 在訓練集上分析錯誤與錯誤聚類 → Opus 提出最大錯誤類別的更新假設 → 發布新 Prompt → 重新運行 → **僅在驗證集也改善時才接受更新**。停止條件為 15 次迭代或達到 92% 準確率，最終在測試集上評估泛化能力。

**關鍵概念：自我優化迴圈**

### 5. 實驗結果與首次迭代效應 [07:02]

整體準確率提升 15%：首次運行為 68%，第三至第四次迭代衝上 83%，之後在 80% 左右穩定。改善成功泛化至 300 筆未見測試資料，達到 **80.2%**。最引人注目的是：**首次迭代立即獲得 10% 的提升**，後續僅有小幅波動。深入檢視後發現，即使這看似「完美」的目標函數也存在雜訊——作者在選擇標籤時有主觀裁量空間，即使描述上看似該歸類為某一類，作者可能因當下判斷而選了另一類，且這些考量未被記錄。

**關鍵概念：首次迭代效應**

### 6. 優化器實際做了什麼 [08:33]

原始 Prompt 僅是扁平標籤列表加上「分類這篇論文」的簡單指令。優化器的首次更新做了四件事：

- 加入**通用分類策略**——模型應如何思考選擇標籤的行為，核心目標是什麼。
- 加入**相似類別的判別規則**——在兩個相近類別間如何抉擇。
- 加入**混淆模式說明**——何時選哪個、在何種條件下該如何處理，傾向選擇更具體的標籤而非更寬泛的標籤。
- 加入**常見誤分類項目的範例**。

令人意外的是，優化器選擇加入**規則與範例**而非標籤描述——模型結合提示指南自行判斷出正確策略，且確實有效。

**關鍵概念：規則與範例注入**

### 7. 首次 10% 躍升的推理剖析 [09:56]

Claude Opus 4.8 在從 68% 跳至 78% 的推理過程中展現了清晰的資料驅動假設形成：

- 識別出 64 個錯誤，歸納出主導錯誤模式與第一名錯誤對。
- 找出最常混淆的兩個標籤組合。
- 基於此提出假設：「本次迴圈將精確解決此模式」。

成功因素在於：**清晰的對錯信號**提供了可量化、可靠的失敗模式分析；**充足的資料量**（200 筆訓練集、10 個標籤確保每個類別有足夠樣本）讓模型能從中提取規律。事實上，僅憑首次迭代的清晰信號即可建立良好的基線。

**關鍵概念：資料驅動假設**

### 8. 從清晰信號到其他領域的轉譯 [11:30]

「對/錯」高信號回饋在分類任務上效果極佳，但大多數真實場景缺乏確定性的 yes/no 目標函數。LLM-as-Judge 本身具非確定性——同一次評估重新運行可能得到不同結果。市場上流行的評估器如正確性、有用性、幻覺檢測等，在自動改善場景中實為**低信號回饋**，尤其當評分置於 0-1 或 1-5 的量表上時，若未定義每個數值的具體含義與適用情境，信號品質極低且跨運行不一致。

**關鍵概念：低信號評估器**

### 9. 高信號評估器的設計原則 [13:15]

有效的替代方案是將抽象品質標準轉化為具體的 yes/no 判定：

- **知識庫依據性**：「答案是否基於知識庫？」——檢查回答中的內部資訊是否也存在於前一檢索步驟的上下文中。
- **品牌語音一致性**：「品牌名稱是否拼寫正確？」——甚至檢查「是否意外將英文名稱翻譯成西班牙文？」
- **失敗模式分類**：「本次發生了五種已知失敗類型中的哪一種？」——將分類式的 yes/no 思維延伸至失敗模式歸類。

這些評估器的建立方式是：深入檢視資料、理解「好」的定義、掌握領域專家認為重要的事項，從而構建高信號回饋迴圈。在無法使用「程式碼能否編譯」的情況下，必須換一種方式定義「好」與「不好」。

**關鍵概念：高信號評估器**

### 10. 資料量與領域專家協作 [14:35]

資料量是另一基石：實驗使用 200 筆訓練、100 筆驗證、300 筆測試，已能提供充足的高信號回饋。取得高信號回饋與資料量的核心方法是**與領域專家協作**：

- 利用專家建立期望輸出的範例，一起檢視樣本運行結果。
- 詢問「為什麼這裡是 A 而那裡是 B？」——從中挖掘專家心中視為理所當然的隱性知識。
- 據此識別應用的失敗模式並定義「好」的標準。
- 用專家協助找出高信號評估器。

**關鍵概念：領域知識編碼化**

### 11. 上線後的人類審查與系統泛化 [15:52]

進入生產環境後，必須以**人類視角審查資料**，而非僅仰賴程式碼 Agent。原因在於：

- 應用範疇會隨時間漂移，失敗模式會改變，使用者行為可能延伸出新需求與功能擴展機會。
- 理解系統在生產環境中如何運作與失敗，才能在客戶之前攔截典型失敗模式。

最終，應將整體視為**一個需要泛化的系統**：建立代表性範例集，內建驗證機制防止過擬合（類似傳統機器學習的驗證方法），並為系統設置**逃生艙（Escape Hatch）**——避免 Agent 無止境地撞牆消耗 Token，確保人類與 Agent 在持續改善的系統中協同合作。

**關鍵概念：系統泛化與逃生艙**

## [結論與行動建議]

### 啟發金句

> 「如果你無法用『程式碼能否編譯』來判斷好壞，就必須重新定義什麼是『好』——而這個定義，只有領域專家能給你。」

### 具體行動建議：H-E-L 法則

- **H**igh-signal：將所有評估器設計為 yes/no 判定，拒絕未定義的量表評分。
- **E**xpert：與領域專家共同建立範例、挖掘隱性知識、識別失敗模式。
- **L**oop with escape hatch：為迴圈設置停止條件與逃生艙，避免無限消耗 Token。

### 生活實踐建議

在日常 AI 應用開發中，與其追求「模型是否正確」（模糊且低信號），改為設定具體可驗答的檢查點：例如「回覆中是否包含產品定價頁面的 URL？」「是否使用了禁用詞彙列表中的任何一詞？」「回覆長度是否在 50-200 字之間？」將每一個品質維度拆解為可被 yes/no 判定的原子級規則，再以領域專家的知識填充這些規則的內涵，即可建立一套持續自我改善的迴圈系統，而非盲目燒 Token 等待奇蹟。
